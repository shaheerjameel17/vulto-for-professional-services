## 24. Stage 23 — Local-First Search (`VPS-F002`)

`VRS-001`'s Feature Register confirms `VPS-F002` (Local-First Search) as the correct next MVP-order feature after `VRS-F014` (Stage 22, merged `--no-ff` as `cd17db0`): `VRS-F015` is permanently vacant, promoted to the suite as `VPS-F002`, and the MVP order runs `VRS-F014`, `VPS-F002`, `VPS-F003`, `VPS-F004`. It is the `Cmd+K` palette's data layer — one local index over every nameable Tier 0 entity, a command group, and delegation of skill-shaped queries to `VRS-F013`'s existing ad-hoc match. Checked directly against the code before writing this brief: `packages/graph` has no search index of any kind (the device cache holds `cache_nodes`, `cache_edges`, `cache_tags` and the local tables only); `Employee`'s identifying fields (`full_name`, `preferred_name`, `job_title`) are all in the operational Tier 0 half; `Skill`, `Project` and `Client` are registered fixed-Tier-0 node types with real rows and `READ_ANY()` for every role; `Document` is registered with inherited protection and no field schema, `Policy` and `Deliverable` have no field schema for `title`; and `skillMatcher.adHocSearch` is a live server-side `protectedProcedure` (F286), not a local function.

Four findings surfaced checking this feature directly against the code, all closed the same day:

- **F297** — The spec's whole mechanism is SQLite FTS5, but the pinned `wa-sqlite@1.0.0` has no FTS module in either shipped build: `CREATE VIRTUAL TABLE … USING fts5(…)` fails with `no such module: fts5` (and likewise `fts3`, `fts4`, `rtree`), while `json_extract` and `LIKE` work — verified by running it, not read off documentation. **Genuine architectural fork — no precedent — put directly to the founder** with three options: a trigger-maintained derived table (works in the shipped dependency, keeps every guarantee the spec actually states, loses only ranking and tokenizers the spec's Out of Scope already excludes); a custom `wa-sqlite` build with FTS5 (keeps the spec literal but adds a WASM build pipeline and a re-pinned dependency to `VPS-A001`, and native React Native SQLite would need separate verification); or `json_extract` scans of `cache_nodes` with no derived table (smallest, but degrades against the 30ms budget as a workspace grows). **Decided by the founder: the first.** A derived `cache_search` table inside the existing cache, maintained by SQL triggers on `cache_nodes` generated from a single registry, queried by prefix and substring; the mechanism was probed directly — `putNode`'s `ON CONFLICT DO UPDATE`, `deleteNode` and `resetTemplate`'s bulk delete all fire ordinary triggers, including the soft-delete and hard-delete cases — and normalization is SQLite's own `lower()` on both sides so index and query cannot disagree on a character (a JavaScript `toLowerCase()` on one side would silently diverge on non-ASCII text). `CACHE_SCHEMA_VERSION` goes to 3 and `cache_search` joins `REPLICATED_TABLES`; erasure needs nothing new since `eraseDatabases` deletes the whole per-workspace IndexedDB database.
- **F298** — `search.query` is specified as entirely local yet returning `skillMatcher.adHocSearch`'s output unmodified, with offline skill delegation as an acceptance criterion; since F286 that function is a server read. Ruled on F286's and F199's precedent, no founder consultation: `search.query` returns `skillMatched: boolean` instead of `skillMatches`, and the palette calls the existing server function unmodified when it is true, degrading to `requires-connection` offline. No server change.
- **F299** — Only `Employee`, `Skill`, `Project` and `Client` are registered; `Document`, `Policy` and `Deliverable` are forward dependencies added by the stage that gives each a field schema; `search.queryProtected` is deferred until a built node type has a Tier 1–3 searchable name (no built node type has one — `Contract`, `Departure`, `Document` are all unbuilt), owned by whichever of `VRS-F020`/`VRS-F022`/`VRS-F023` builds one first.
