## Finding raised

### F288 — a Manager cannot attach a Project skill requirement under the current edge policy

**Ruled and merged from `main` before implementation resumed.** The Stage 21 brief requires a project Manager to call `project.attachSkillRequirement` and, when nobody matches, trigger a system-authored `SkillGap` in `afterCommit`. The corrected `VRS-F013` specification likewise says a project manager attaches the requirement. The existing `Project` policy row grants Manager `READ_ANY()`, while the proposed `Skill` row grants Manager `FULL_ANY()`. In `edgeRoleDecision`, writing `requires_skill` requires Full on **both** endpoints unless its edge registration declares an endpoint in `readSufficientEndpoints`. The `requires_skill` registration originally declared only the F285 `governingPartitions` fix. The reviewer ruled by F262's identical `assigned_to`/Project precedent: `requires_skill` now declares `readSufficientEndpoints: { Project: true }`, without widening Project's policy row.

### F289 — `has_skill`'s required proficiency metadata is discarded by the graph store

**Ruled and implemented at the store boundary.** Stage 21 item 1 requires `employee.attachSkill` to persist `has_skill.proficiency_level` and server-derived `verified`, `verified_by`, and `verified_at`, with duplicate attachments updating the existing edge in place. The matcher in item 7 must read that proficiency to decide whether an Employee qualifies. But `has_skill` has Employee as an endpoint, and Employee has a protected compensation partition. The old `insertEdge` check tested whether either endpoint had *any* protected partition and discarded all metadata; its integration test even asserted that for `managed_by` despite its declared Tier 0 `Employee:operational` governing partition. The reviewer ruled by the existing `edgeRoleDecision`/F136 partition precedent: classify edge metadata by its registered governing partition, failing closed if missing or non-zero. `insertEdge` now does so, and the new `graph.updateEdgeMetadata` generic Tier 0 mutation uses the same store-level classification for in-place updates. A focused live-Postgres store suite passes all 25 tests, including preservation for `managed_by` and stripping for undeclared `originated_from`/Pitch.

### F290 — SkillGap severity has no governing working calendar for a Project

**Ruled by founder; implemented and tested.** `VRS-F013` G07 and Stage 21 item 6 require `SkillGap.severity` to count working days until `Project.start_date` through `VRS-F004`'s working-day helper. That helper (`resolvedDayOn`/`countWorkingDays`) requires a specific Employee because calendars come from that Employee's Entity assignment and potentially personal WorkingPattern. Project is only a minimal `VRS-F005` bootstrap node (`name`, lifecycle; this stage adds nullable `start_date`). The registry has no Project→Entity or Project→WorkingCalendar edge. The ruling is deterministic earliest-staffed Assignment's Employee Entity, else the workspace's sole Active Entity, else severity Low. `resolveProjectCalendarEntity` and `countWorkingDaysForEntity` now implement the graph/calendar primitives, and the evaluator uses them. A live test proves an Assignment-selected Entity calendar yields 20 working days and High severity; the ambiguous multi-Entity fallback yields Low. Multi-entity support in `VRS-F064` is an explicit forward dependency.

### F291 — generic edge writes can bypass skill verification and uniqueness

**Ruled by feature-owned-node precedent; guard implemented and tested.** F289 correctly makes `has_skill` metadata survive `insertEdge` when its registered Employee governing partition is Tier 0. That exposed the generic create/update bypass for server-derived verification and duplicate edge identity. The ruling adds `FEATURE_OWNED_EDGE_TYPES` for `has_skill` and `requires_skill`; generic create, metadata update, and close reject them with `requires-feature-mutation`, while named mutations retain their store-level write path. Live tests prove both generic create and metadata-update rejection while the named writes succeed. This also intentionally reserves the other four `requires_skill` pairings until their owner builds a named mutation. The F285 Pitch proof is an interceptor/store-level test, not a generic-mutation test.

### F292 — workspace-wide matcher decision conflicts with Employee's current policy row

**Ruled by founder and implemented.** `PolicyCell.readScope` now gives Manager and Team Member workspace-wide Employee:operational Read when their narrower ordinary scope fails, without changing node or edge write authority. The matcher uses `filterReadable` under that ordinary decision. A live integration test proves both roles see an outside candidate while both their node and `has_skill` edge writes to that Employee remain denied. This is also the mechanism that exposes the F294 interaction below.

`VRS-F013`'s Decisions Recorded requires Employee operational data to be readable by every workspace member, while the old single-scope policy cells dropped outside-report/team rows from `filterReadable`. The founder chose a general read/write split rather than a matcher-only carve-out because the plain directory and Bench Forecast hit the same gap. The existing write scope is retained as the narrower ceiling.

### F293 — the system gap evaluator has no read grant for its own match cohort

**Ruled by direct precedent and implemented.** `skill-gap.read-cohort` now targets only Employee:operational in the system operation table. The reactive integration test confirms a qualifying Employee is visible to `skill-gap-evaluate` and no false Active gap is written; another test confirms an existing gap resolves after `employee.attachSkill` commits.

Stage 21 item 8 requires `skillGap.evaluate` to call the shared matcher, which filters Employee rows. A system principal holds no `PolicyRole`; `decideRead` allows only its named operation's closed target list. The originally briefed write-only grant would have made every match cohort appear empty. F293 follows the existing `utilization-snapshot.read-cohort` precedent, with no new Skill or Assignment target: Assignment coverage already uses the trusted derived-day read, and matching never reads Skill fields to compare proficiency.

### F294 — workspace-wide Employee read widens older derived queries beyond their explicit security contracts

**Ruled by direct precedent and implemented.** F292's `Employee:operational` `readScope: "any"` correctly gives every workspace member the operational Employee read required by the matcher and the plain directory. But two older read procedures used the former row scope as their *only* admission check for a different disclosure. `pitch.listStaffedFor` could reveal another Employee's staffed Pitch and client name to an unrelated Team Member, contrary to `VRS-F009`/F264. `conflictResolution.sweepOvercommitted` could reveal overcommitment outside the caller's team or direct reports, contrary to `VRS-F008`/F263. A new `withinRoleScopedReach` interceptor primitive evaluates the named policy cell's original narrow scope, ignoring `readScope`, with the candidate Employee as its trusted subject. Both queries now use it against `Employee:operational`, so F292's directory and matcher reads remain wide while these derived disclosures retain their own contracted boundary. Their existing real-Postgres tests pass again.

The earlier `verify:full` run had seven failures: three audience and one matrix-fidelity expectation still reflected pre-F292 Employee scope; the other three were the older Pitch and sweep security assertions. The audience and matrix tests now recognize F292's intentional wider Employee read, while retaining their conformance assertions. The corrected full run passes.

### F295 — timesheet compliance status used Employee scope instead of its own row

**Ruled by direct precedent and implemented.** The post-F294 caller audit found `listSubmissionStatus` also used `filterReadable(Employee)` as its only cohort gate. This predated F292: `TimesheetEntry:record` has always given Team Member own-only access, narrower than Employee operational's own-plus-team scope, so a Team Member could learn a teammate's compliance status. The same `withinRoleScopedReach` primitive now evaluates each candidate Employee against `TimesheetEntry:record`. A new real-Postgres test gives another Employee the same manager, proves that Employee is operationally readable, and proves `listSubmissionStatus` nevertheless returns only the caller's own status; Owner still sees the broader cohort.

## Completed build and code checks

- `employee.attachSkill` is the `VRS-F002` named mutation: proficiency is validated against the one exported `Beginner` → `Expert` ordering. A duplicate updates the same `has_skill` edge's metadata and preserves its edge ID. The server derives `verified`, `verified_by` and `verified_at` from the acting user's linked Employee and rejects a caller-supplied `verified` field. The corrected store classifies edge metadata by its registered governing partition, so Tier 0 `has_skill` metadata survives while undeclared or non-zero governing partitions still fail closed.
- `project.attachSkillRequirement` updates an existing `requires_skill` edge in place or creates exactly one; Manager's `READ_ANY()` on Project counts through F288's declared `readSufficientEndpoints` without broadening Project write access. `Skill` and `SkillGap` have explicit policy rows, Skill has its full schema and generic create/deprecate path, Project accepts nullable `start_date`, and the generic `has_skill`/`requires_skill` edge paths reject `requires-feature-mutation` while both named paths succeed. An interceptor/store-level test proves the Pitch-paired `requires_skill` declaration from F285 authorizes and persists metadata under a real Owner principal, without reopening the generic path.

It reads Employee/Ghost candidates through the interceptor; uses `bench-forecast-queries.ts`'s own `assignmentsFor` and `assignmentCovers` helpers; filters end dates beyond the requested window; and ranks availability, proficiency, then real before Ghost at equal availability. A live test covers two Project requirements yielding three and one matches, including a `VRS-F007` Ghost, and excludes a later Assignment. Ad-hoc matches and non-matches write neither `SkillGap` nor a skill edge.

Zero matches create or retain one Active gap; a real qualifying candidate resolves it with `resolved_at` and `resolved_by: "system"`. The evaluator reads the real Employee cohort under F293's grant rather than mistaking an authorization-empty cohort for a gap. F290 severity uses the Project's earliest-staffed Assignment Entity, else sole Active Entity, else Low, and counts with `VRS-F004`'s shared `resolveWorkingDay` rather than a second calendar algorithm.

F294/F295's `withinRoleScopedReach` is in the interceptor and checks the original named cell scope: `Employee:operational` for `listStaffedFor` and `sweepOvercommitted`, `TimesheetEntry:record` for `listSubmissionStatus`. The existing Pitch and capacity tests plus the new same-team timesheet test prove the three older disclosure boundaries.
