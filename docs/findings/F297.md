### F297 — the pinned `wa-sqlite` has no FTS5, so `VPS-F002`'s index mechanism cannot be built as specified

Checking `VPS-F002` (Local-First Search) directly against the code before writing its Stage 23 brief, per standing practice, surfaced this before any product code existed. The spec's mechanism is stated in five places — sub-feature S01 ("FTS5 index schema and trigger maintenance"), G01 and G05 ("FTS5 tables are maintained by triggers", "adding an FTS table"), the Technical Architecture ("SQLite FTS5 virtual tables, one per searchable node type") and the Security Considerations ("never written into a search index") — and `VPS-A001` pins the device cache as `wa-sqlite@1.0.0` (`packages/graph/package.json`), used through `packages/graph/src/sync-client/database.ts` with the IndexedDB VFS in the browser. A probe run directly against that package's two shipped builds (`dist/wa-sqlite-async.wasm`, which the cache uses, and `dist/wa-sqlite.wasm`) on SQLite 3.44.0: `CREATE VIRTUAL TABLE … USING fts5(x)` fails with `no such module: fts5`, and so do `fts3`, `fts4` and `rtree`; `json_extract(...)` and `LIKE` work. No index of any kind exists in `packages/graph` today — only `cache_nodes`, `cache_edges`, `cache_tags` and the two local tables — so nothing already built constrains the choice.

**Genuine architectural fork — no precedent to trace to — put directly to the founder.** Three options reasoned through. (1) A trigger-maintained derived table inside the existing cache, queried by prefix and substring: works in the shipped dependency, preserves every guarantee the spec actually states (Tier 0 identifying fields only, trigger maintenance riding the same writes that populate `cache_nodes`, an open registry, the 30ms budget at the spec's own scale of 150 employees and 50 projects), and loses only FTS5's ranking and tokenizers — which the spec's own Out of Scope already excludes ("typo-tolerant fuzzy matching beyond prefix and substring"). (2) A custom `wa-sqlite` build with `SQLITE_ENABLE_FTS5`: keeps the spec literally as written but adds an Emscripten build pipeline and a re-pinned dependency to `VPS-A001`'s stack, and native React Native SQLite would need FTS5 verified separately. (3) No derived table, `json_extract` over `cache_nodes` at query time: smallest change, but it parses JSON on every keystroke and degrades against the 30ms budget as a workspace grows. **Decided by the founder: the first option.**

The ruling, in full. A derived table `cache_search` (`node_id` primary key, `node_type`, `label`, `lifecycle_status`, `search_text`) lives in `CREATE_REPLICATED_SCHEMA`, added to `REPLICATED_TABLES` so a cache-version change drops and refills it with the rest, and `CACHE_SCHEMA_VERSION` is bumped to 3. SQL triggers on `cache_nodes` (insert, update, delete) maintain it, generated from a single registry of searchable node types and their identifying fields (F299); `putNode`'s `ON CONFLICT DO UPDATE`, `deleteNode` and `resetTemplate`'s bulk `DELETE` all fire the ordinary triggers — verified directly against a probe of exactly those statements, including the soft-delete and hard-delete cases. Normalization is SQLite's own `lower()` on both the index side and the query side, never JavaScript's, so the two can never disagree about a character; the user's text is bound as a parameter with `%`, `_` and the escape character escaped. Erasure needs nothing new: `eraseDatabases` deletes the whole per-workspace IndexedDB database, index included. A registry change alters the generated trigger SQL, so a pinned fingerprint of the registry fails a test until `CACHE_SCHEMA_VERSION` is bumped alongside it. `VPS-F002`'s S01, G01, G02, G05 and Technical Architecture text corrected to match.

**Status: closed.**
