### F282 — `VRS-F012`'s spec still describes the dropped local-first architecture

Raised 25 September 2026, checking `VRS-F012` directly against the code before writing its Stage 20 brief, per standing practice. This document was decided at founder level on 31 July 2026 and never revisited since — unlike `VRS-F005` (corrected at its own Stage 13 briefing, F236) and `VRS-F006` (corrected at Stage 14, F244) — so it still carries the pre-pivot local-first architecture throughout: its Depends-On section cites `VPS-A001` for "the Web Worker the engine runs inside"; the monitoring-engine section states "Both run inside the Web Worker boundary... This engine is a consumer of the materialized index, not a second thread with its own connection"; the API contracts say `revenueGapAlert.listActive` "Resolves entirely from the local graph"; the System States table's Syncing row says "Cards render from local state; alerts are computed locally and do not wait on sync"; and the Non-Functional Requirements include "Alerts written offline sync within 1 second of reconnection" and a sweep that runs "entirely from the local graph." None of this matches the server-authoritative architecture every other built feature now runs on.

**Closed by direct precedent, 25 September 2026.** No founder consultation needed — this is the identical class of correction F236 and F244 already made for two sibling specs. `docs/Vulto_Specs/VRS-F012_Revenue_Gap_Alert.md` corrected throughout: the Depends-On `VPS-A001` citation removed (the engine is an ordinary server-side mutation and query pair, like every reactive engine this project has built since Stage 18); the "Web Worker boundary" paragraph replaced with the real shape — `revenueGapAlert.evaluate` runs server-side, reactively from `afterCommit` hooks on Assignment-changing mutations, plus a manually-callable sweep procedure (Stage 16's `conflictResolution.sweepOvercommitted` precedent) pending `VPS-A006`'s still-unbuilt job scheduler, which the Depends-On section already correctly names; `listActive`'s "Resolves entirely from the local graph" corrected to an ordinary server-side `protectedProcedure` query; the System States table's Syncing row and the two offline/local-graph NFRs removed, since `RevenueGapAlert` reaches the client the same way `UtilizationSnapshot` and `TimesheetAnomalyFlag` already do — Electric's own shape sync, no device-side computation.

**Status: closed.**
