### F262 — F255 authorizes the Assignment node but not the two edges a Manager override must create

Raised 24 September 2026 while running Stage 16's first real `overrideAndProceed` PostgreSQL integration test through the permission interceptor, after product implementation had begun.

**The gap.** Stage 16 Do item 6 requires a target employee's Manager to invoke `conflictResolution.overrideAndProceed`, and requires that mutation to reuse `assignment.create`'s complete write path. F255 corrected `MATRIX_OVERRIDES["Assignment"].manager` from Read to unscoped Full so the new Assignment node itself can pass the write interceptor. Reusing the complete write path also creates two mandatory edges, however, and the interceptor evaluates them independently before any validation or apply step:

1. `assignment_of` joins the new Assignment to the target Employee and declares `Employee:operational` as its governing partition.
2. `assigned_to` joins the new Assignment to its Project.
3. `edgeRoleDecision` in `services/api/src/permission/interceptor.ts` requires unscoped Full on both endpoint node types. Its own comment states that no row is named during this gate, so a row-qualified grant never authorizes an edge write.
4. Manager has `Full (direct reports)` on `Employee:operational`, which is deliberately row-qualified, and only unscoped Read on Project. The Manager therefore cannot authorize either required relationship even though F255 now authorizes the Assignment endpoint.

The integration test establishes the failure through the real pipeline. A Team Member is linked to a Manager Employee, the target Employee is connected to that manager through an active `managed_by` edge, and the manager submits a valid override against a real Project. The server-side application gate accepts the caller as the target's manager, but `applyMutation` returns `{ status: "rejected", reason: "role" }` during the plan's edge checks. No Assignment is written because authorization correctly precedes validation and apply.

There is no mechanical implementation choice left by the corrected brief. Widening Manager to unscoped Full on Employee or Project would change unrelated permissions far beyond this feature. Treating a direct-report scope as sufficient for every Employee-bearing edge would require the edge interceptor to gain row context and define which endpoint establishes that scope. Omitting either edge would violate `VRS-F005`'s Assignment graph shape and Do item 6's reuse requirement. Bypassing the interceptor for mutation-derived edges would contradict `VPS-A004`'s single enforcement boundary. Restricting the override to Owner would contradict `VRS-F008`'s explicit Manager flow.

A ruling must define how a Manager-authorized Assignment creation may create its required `assignment_of` and `assigned_to` edges while preserving the interceptor's endpoint rules and the existing Employee and Project permission cells. Until then, the product implementation cannot make the promised Manager override pass without inventing a permission exception.

**Closed by founder-delegated decision, 24 September 2026 — put directly to the founder rather than traced to a single existing precedent.** Unlike F255–F261, no prior ruling decides this: `edgeRoleDecision`'s row-blind, both-endpoints-unscoped-Full rule is itself deliberate, founder-reviewed architecture (FDN-92's design memo: "the natural analogue... Full write permission required on both endpoint node types"), spanning roughly ninety registered edge types, none of which — before this feature — was ever written by a role holding anything less than unscoped Full on both its endpoints. Four alternatives were surveyed and rejected before this one: widening `Employee:operational`'s or `Project`'s Manager cell to unscoped Full changes access far beyond this feature's need, and for Employee directly contradicts `VPS-A004`'s own Role Definitions ("Full access to direct reports' operational data"); teaching `edgeRoleDecision` row context while leaving Manager's Project grant at Read would still refuse `assigned_to` outright, since Read never satisfies a Full requirement regardless of row; reusing F206's system/support principal mechanism does not fit — `SYSTEM_PRINCIPAL_OPERATIONS` is a narrow, per-job whitelist for background maintenance work (audience recompute, retention sweep, erasure, key rotation), not a general elevation path, and a support principal would misattribute a Manager's own in-product action in `AuditEntry.actor_kind`; and bypassing the interceptor for these two edges specifically would contradict `VPS-A004`'s A004-T17 three-gate sequence and the "single enforcement boundary" F138 and F206 both already treated as inviolable.

**Ruled — two additive mechanisms, one per edge, neither widening an existing grant:**

1. **`assignment_of`'s Employee endpoint: row context, not a wider grant.** `WriteTarget`'s edge variant (`services/api/src/permission/interceptor.ts`) gains optional `readonly fromNodeId?: string | null` and `readonly toNodeId?: string | null`. `edgeRoleDecision` builds a `RowScopeContext` per endpoint when an id is supplied — the identical `{ tx, principal, nodeType, nodeId, context }` shape `decideRead` already builds for reads — and passes it into `bestCell`, instead of calling `bestCell` with no row at all as it does today. Every existing edge-write call site (`managed_by`, `pattern_for`, all ~88 others) supplies no id, so its behavior is byte-for-byte unchanged. `services/api/src/mutations/assignment.ts`'s `buildAssignmentCreatePlan` — the single plan builder both `assignment.create` and `overrideAndProceed` already share (Do item 6) — already resolves `employee`/`project` as real `StoredNode`s before building `checks`; its `edgeTarget` helper gains a `toNodeId` argument, supplied as `employee.nodeId` for `assignment_of` and `project.nodeId` for `assigned_to`. With real row context, Manager's already-documented `Employee:operational` cell — `cell("full", "direct-reports", ...)`, unchanged, not widened — now correctly resolves `rowScopeSatisfied("direct-reports", row)` against the actual target employee via the same `managerOf` closure the interceptor already uses for reads: true for that employee's real manager, false otherwise. This is the interceptor's own existing machinery working for the first time in a write context that needed it, not a new privilege.
2. **`assigned_to`'s Project endpoint: read-sufficient by declaration, not a wider grant.** `Project`'s `manager` cell stays `READ_ANY()` — untouched; a Manager still cannot write a Project's own fields. `packages/schema/src/registry/edges.ts`'s `EdgeGroupShape` gains an optional `readSufficientEndpoints?: Readonly<Partial<Record<NodeType, true>>>`, declared and reviewed per edge type exactly as `governingPartitions` already is (F136/F208/F235's own precedent for this registry's opt-in, conservative-by-default style) — absent for every edge type but one, so the other ~89 are unaffected. `assigned_to` is the first and only declaration: `readSufficientEndpoints: { Project: true }`. `edgeRoleDecision` accepts an endpoint whose declared-read-sufficient cell resolves to `"read"` as well as `"full"`. This mirrors `VPS-A004`'s own already-accepted Graph traversal rule for reads — "Read on Node A, on Node B... and on the edge type" — applied here to exactly one write, not a new standard for edge writes generally.

Neither mechanism touches `Assignment`'s own endpoint (F255's `FULL_ANY()`, unchanged) or `assignment_of`'s declared governing partition (F208's `Employee: "operational"`, unchanged) — `rowScopeSatisfied("any", ...)` is unconditionally true regardless of row context, so the FROM side of both edges (Assignment, in both cases) needed neither change. This resolves F262 without reopening F255–F261.

**Status: closed.** Stage 16 is unblocked; `codex/stage-16-capacity-conflict-resolution` resumes on the corrected brief — no branch restart.
