### F225 — Holiday confirmation is not, in fact, `VPS-F004`-audited

Raised 22 September 2026 while briefing Stage 12 (`VRS-F004`, Working Calendar and Working Patterns). `VRS-F004`'s Security Considerations states plainly that "Holiday confirmation is audited per `VPS-F004`, because it changes computed figures retroactively across the product." Checked directly against `VPS-F004_Silent_Audit_Log.md`'s own Technical Architecture: `AuditEntry.event_type` is a closed enum of exactly five values — `PermissionDenied`, `SensitiveAccessGranted`, `AuthorizedOperationFailed`, `PrivilegedProjectionAuthorized`, `CryptographicErasureExecuted` — and creation "happens exclusively within `VPS-A004`'s interceptor. No feature calls a create endpoint for this node type" (G02). An HR Admin confirming a provisional holiday's actual date is an ordinary, permitted Tier 0 write; it is not a denial, not a grant of Tier 1/Tier 3 access, not an operation failure, not a privileged projection and not an erasure. This is the identical shape of gap F221 already found and ruled for `VRS-F003`'s claim that Entity transfer is `VPS-F004`-audited.

**Ruling — closed 22 September 2026, on F221's own precedent.** `VPS-F004`'s taxonomy is not extended for holiday confirmation, for the same reason it was not extended for Entity transfer: the record already exists elsewhere. `Holiday`'s own schema carries `confirmed_at: timestamp, nullable` and `confirmed_by: user_id, nullable`, alongside the retained `estimated_date` that shows the shift — exactly the who/when/what-changed record an `AuditEntry` would otherwise supply, already present on the node itself with no additional write. The same reasoning covers `ReducedHoursPeriod`, which the spec gives an identical `is_provisional`/`estimated_start_date` confirmation shape but no dedicated audit fields of its own; since it is held inline on `WorkingCalendar` rather than as its own node (no independent lifecycle), its confirmation is likewise not a `VPS-F004` event — the superseding `WorkingCalendar` version's own `updated_at`/`updated_by` (per `VPS-A002`'s Universal Node Conventions) is its record. `VRS-F004`'s Security Considerations, its acceptance criterion for holiday confirmation, and its Decisions Recorded section are all corrected to match.

**Status: closed.** No `VPS-F004` `AuditEntry`-writing call is added anywhere in Stage 12's `holiday.confirm` or `calendar.update` implementations. Stage 12 is unblocked on this point before it starts.
