### F280 — no authorized principal exists for `utilizationSnapshot.compute`'s reactive write

Raised 25 September 2026 by Codex, immediately after F279, still before any product code. `VRS-F011`'s own design (mirroring `VRS-F010`'s `timesheetAnomaly.evaluate`) computes `UtilizationSnapshot` reactively, inside `saveCell`/`submitWeek`/`unlockWeek`'s `afterCommit` hooks, under whichever ordinary principal triggered the edit — usually the Team Member editing their own timesheet. F278's own ruled policy row gives Team Member `Read (own only)` on `UtilizationSnapshot`, deliberately never `Full`: a Team Member correctly cannot overwrite their own utilization figure directly, since it must only ever be derived from their actual logged hours. But that same restriction means the triggering principal has no write authority over the row the reactive computation needs to create or update, and the write is refused.

**Closed by direct precedent, 25 September 2026.** No founder consultation needed — this is F270–F272's own system-principal mechanism, which those findings' own rulings explicitly predicted would recur for future system-authored writes, applied a second time rather than reasoned from scratch. A new system principal, `utilization-snapshot-compute` (display name "Utilization Snapshot"), is added to `packages/schema/src/policy/principal-policy.ts`'s `SYSTEM_PRINCIPAL_NAMES`, and a new operation, `utilization-snapshot.compute`, to `SYSTEM_OPERATIONS`, granted to it in `SYSTEM_PRINCIPAL_OPERATIONS`. `utilizationSnapshot.compute`'s own mutation runs under this principal rather than the triggering caller's, the same substitution F270's `timesheetAnomaly.evaluate` already established. The concrete authorization wiring for this operation — and a second operation this same principal needs — is generalized together with F281's own ruling into a single closed table; see F281's own detail section for the full design.

**Status: closed.**
