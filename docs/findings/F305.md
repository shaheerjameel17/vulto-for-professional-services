### F305 — the sync browser suite has been red since Stage 11, and Stage 23's gate could not be satisfied

Stage 23's F301 ruling made the full `pnpm test:sync-browser` a required gate. Codex ran it after migrating (`set -a; source .env; …`) on the F304 build and reported 18 passed, 9 failed, the new `cache_search` assertions in the role-removal test among the passes. It stopped on the failures: most begin at `seedEntities` (`packages/graph/sync-browser-tests/helpers.ts`), which submits an `Entity` node to `graph.createNode` and expects `applied`, but `services/api/src/mutations/foundation.ts::createNode` returns `requires-feature-mutation` for every type in `FEATURE_LIFECYCLE_NODE_TYPES`, and that set has contained `Entity` since Stage 11 (`82c0b31`, 22 September 2026; the schema test pins `FEATURE_LIFECYCLE_NODE_TYPES.has("Entity")` to true). The browser suite was last modified by Stage 10 (`c99f2bf`, the same day) and has not been repaired since. The two-tabs test's separate count failure is the same fixture path — `newEntity` drives a browser-side `graph.createNode` on `Entity` — though Codex did not root-cause it.

Three consequences, in order of weight. First, the slow lane's `sync-browser` job, which the workflow describes as required for merge, has presumably been red on every push since Stage 11 (this shell has no GitHub access to confirm; the founder should check the Actions history on `main`). Second, the A003-T56 test — the repository's one real-browser proof that no Tier 1 or Tier 2 value reaches the device — calls `seedEntities` and has therefore not run green for eleven stages; only its unit-level and structural counterparts have. Third, Stage 23's own brief demanded a full pass that could never have been achieved, and the reviewer had written that requirement (F301) without running the suite on `main` to see its baseline. This is the fifth brief-versus-reality defect of this stage (F301 to F304 before it), and the first that is not the brief's alone: a pre-existing regression the brief inherited.

**Ruled by the reviewer, 25 September 2026: repair deferred to its own issue, Stage 23's gate corrected. Left open, not closed.** Repairing the suite is not Stage 23's job and cannot be settled by precedent: the fixture must seed something that `graph.createNode` may create, and the candidates differ in what they mean for every test that reads it (a genuine `entity.create`, which needs its own required fields and a jurisdiction; or a non-feature-owned Tier 0 type such as `Client`, which changes what `listEntities`, `entityQuery` and the offline-replay tests assert on). A Linear issue in the Vulto Foundation team carries the repair, and the founder should treat it as a merge-gate health problem, not a nicety. Stage 23's gate becomes a baseline comparison, following Part 2's own rule that a pre-existing failure is recorded as a baseline and must not get worse. (1) Baseline: on a clean checkout or worktree of `main` at `11e404a` or later (identical to this branch's pre-Stage-23 code apart from documentation), run the same full `pnpm test:sync-browser` command in the same environment and record the failing tests by exact name and failure message. (2) Comparison: on the Stage 23 branch, run it again. The set of failing tests must be identical by name, each failing for the same reason (the seed or mutate step's `requires-feature-mutation`), and every other test must pass, including the role-removal test with all its added assertions. A test that fails only on the branch, or fails for a different reason there, is a Stage 23 regression and is fixed; a failure identical on `main` is pre-existing and needs no root cause beyond showing the identical message (this is how the two-tabs failure is settled). If the baseline cannot be run, the report says so and the gate is not claimed. (3) Because the A003-T56 test cannot run, the passing role-removal test gains a real-browser sentinel check for the new table: `seedProtected` is called with unique Tier 1 and Tier 2 sentinel strings (not the current `"irrelevant"`), and after the first `Synced` the test asserts that neither sentinel appears anywhere in `JSON.stringify(dump())`, `cache_search` included. (4) Nothing in the fixture, `graph.createNode`, `FEATURE_LIFECYCLE_NODE_TYPES`, the suite's configuration or any gate is changed or skipped in this stage, and no test is tagged or removed to reach a pass.

**Status: open** (raised and ruled deferred; the repair issue, not Stage 23, closes it).

### F305 update, 26 September 2026 — CI history confirms the red gate; repair briefed as Stage 24

F305 was raised with the caveat that the slow lane had "presumably" been red since Stage 11, because the reviewer's shell had no GitHub access. The founder then made the repository public (it had been on a private-repository Actions allowance that ran out), and the public Actions API, readable from the device shell, settles the history. GitHub Actions had in fact been running throughout; the gate was red, not absent. The slow lane's last green run on `main` is `250a60a` (22 September 09:34 UTC, run 35711148145, all five jobs green). The first red is the very next slow-lane push, `e0c05e4` (22 September 12:57 UTC, run 35730337675, the Stage 11 merge): the `sync-browser` job fails at its step "Gate — no protected data on the device (A003-T56)" while `api-integration`, `auth-browser` and `production-build` stay green. Every slow-lane run on `main` after that failed the same way (about forty-five runs over four days), `publish-artifacts`, which runs only when the whole lane is green, was skipped every time, and because the T56 step comes before the full-suite step, CI never reached the rest of the browser suite either. Nobody saw it because nobody read the lane; no gate required it.

A second, independent problem ran alongside from about 24 September 20:34 UTC: every job in both workflows failed without executing a single step (`resolve-image` and the rest report no failed step), which is an Actions-availability failure, consistent with the private-repository allowance being exhausted, and the Stage 23 branch's runs all fail that way (latest 25 September 16:31 UTC). It means the fast lane's `pnpm verify` has not run on CI for the Stage 20 to 23 merges, although each was run locally. It is not a code result and should clear now that the repository is public; the first runs after the change are the evidence.

**Repair ruled and briefed, 26 September 2026 (Stage 24, `FDN-126`).** The fork F305 named — seed the suite with a genuine `entity.create`, or with a type that is not feature-owned — is ruled in favor of a type that is not feature-owned, by the reviewer under standing authority (low stakes, easily reversed, and guarded). The suite exists to test the sync engine's generic paths (`graph.createNode`, `graph.transitionLifecycle`, the outbox, the audience shape); a legal `Entity` needs a jurisdiction and its own required fields for no test benefit, and any type with an owning feature mutation is by design refused by exactly those generic paths. `Client` fits: fixed Tier 0 and not in `FEATURE_LIFECYCLE_NODE_TYPES`, so the server's `graph.createNode` and `graph.transitionLifecycle` and the client's optimistic mutators (which run the identical `isTier0Only` and feature-owned checks) accept it; its lifecycle is `Active`/`Inactive`, which the stale-transition test's `Inactive` needs (`Entity`'s is `Active`/`Dissolved`); the policy table gives the owner `Full` and every other role `Read` on it. Its ownership is provisional (a later Vulto Sales or Projects stage will claim it, as Stage 11 claimed `Entity`), so the repair adds what was missing in the first place: a unit test under `packages/graph/src`, run by `pnpm verify`'s `test:fast` on every fast-lane push, that fails with an instruction the moment the seed type stops being a Tier 0 type with no owning mutation. `packages/graph` type-checks and unit-tests only `src/`, so the browser suite's helpers were invisible to every hermetic gate, which is how the rot went unnoticed; the guard test closes that. The repair also adds a negative control for the A003-T56 test (it must fail when a Tier 1 sentinel is planted in a Tier 0 field, so the gate is proven to bite), and makes CI itself the acceptance gate: the branch's `fast-lane` and `slow-lane` runs must both end green, which the reviewer can read independently through the public API.

F305 stays open until Stage 24 merges and `main`'s slow lane, including `publish-artifacts`, is green.
