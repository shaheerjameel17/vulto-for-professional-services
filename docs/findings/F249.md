### F249 — VRS-F007's promotion API names a second, unspecified path with no defined edge-reconciliation mechanics

Raised 23 September 2026 while checking `VRS-F007` directly against the code before writing the Stage 15 brief.

**The gap.** `ghostResource.promote`'s contract is `promote(ghostId, { fullName, email, employmentType, startDate } | { existingEmployeeId })`. The "Promoting to a real employee" flow names the `existingEmployeeId` branch as "the common case being a candidate hired through `VRS-F028`" — i.e. linking the Ghost to a separate, already-existing Employee node created independently, not through this Ghost's own atomic creation. But G01 fixes the Ghost's own Employee node permanently at creation ("linked permanently by `ghost_employee_id`, set once and never changed"), the promotion transaction as specified "modifies the linked Employee atomically" (singular, the Ghost's own node), and "every Assignment edge, skill edge and piece of graph history is preserved untouched" — none of which says what happens to the Ghost's own placeholder Employee node, or to its Assignment/skill edges, when promotion instead targets a different, pre-existing Employee node. No acceptance criterion exercises this branch; none of G01 through G08 mentions it. Filling it in would mean inventing a cross-node edge-migration mechanism — closing the Ghost's edges and reopening equivalent ones on the target node — that has no precedent anywhere in this codebase, on no more grounding than the phrase "the common case."

**Closed by founder-delegated decision, 23 September 2026.** Stage 15 builds the fully-specified path only: `{ fullName, email, employmentType, startDate }`, which every acceptance criterion, G06 and G07 describe in full — the Ghost's own linked Employee node is filled in place, no second node is involved, nothing needs reconciling. The `existingEmployeeId` variant is deferred rather than invented; `ghostResource.promote` validates its input as the single-branch shape only for now, and a caller who passes `existingEmployeeId` receives a clear "not yet supported" rejection rather than a half-built merge. `VRS-F007`'s API contracts and "Promoting to a real employee" flow gain a note recording the deferral, and Out of Scope gains a line naming it, so the gap is documented rather than silently absent.

**Status: closed.**
