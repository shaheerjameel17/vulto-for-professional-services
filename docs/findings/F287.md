### F287 — `VRS-F002`'s own `employee.attachSkill` mutation was specified but never built

Raised 25 September 2026, checking `VRS-F013` directly against the code before writing its Stage 21 brief. `VRS-F002`'s API contract has read `employee.attachSkill(employeeId, skillId, proficiencyLevel) -> { edgeId }` since that document was decided at founder level, and its G03 fully specifies the edge's semantics: "`has_skill` carries `proficiency_level`, `verified`, `verified_by`, `verified_at`. At most one edge per Skill; a duplicate attachment replaces proficiency rather than creating a second edge." `VRS-F013` depends on this directly — its own persistent and ad-hoc matching, and its SkillGap auto-resolution, all traverse `has_skill` edges on real Employees.

A direct read of `services/api/src/mutations/employee.ts` and its mutation-type registry (`packages/schema/src/mutations/employee.ts`) shows five implemented mutations — `create`, `update`, `transitionStatus`, `linkUser`, `setCompensation` — and no `attachSkill`, no `attachCertification`. Searching the whole repository for either name outside test fixtures returns nothing. The only place `has_skill` is ever written in production code is `services/api/src/mutations/ghost-resource.ts`, as part of Ghost Resource creation — a real human Employee has no path to acquire a `has_skill` edge at all. `VRS-F013` cannot function against real people without this; it was never caught earlier because no feature before Stage 21 has needed to write to a live Employee's skills.

**Closed by direct precedent, 25 September 2026.** No founder consultation needed — the same already-complete-spec, never-built-mechanism pattern F283 closed for `VRS-F005`'s bench computation. `employee.attachSkill` is built in `VRS-F002`'s own module this stage, matching its already-specified contract and G03's replace-on-duplicate semantics exactly, with `verified`/`verified_by`/`verified_at` derived from who calls it — self-attachment is self-reported, an attachment by a caller with independent write authority on that Employee's operational partition is verified — rather than accepted as a caller-supplied flag, since a self-attestation of "verified" would defeat the field's own purpose. `employee.attachCertification`/`holds_certification` is explicitly left untouched: the executable registry names `VRS-F041` as that edge's real owner, not `VRS-F002`, and `VRS-F013` has no dependency on it — recorded here so the mismatch is not lost, not resolved now.

**Status: closed.**
