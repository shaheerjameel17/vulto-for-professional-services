### F250 — Ghost lifecycle transitions omit the required base version, and promotion's stated guard is not concurrency-safe

Raised 23 September 2026 while tracing the corrected Stage 15 brief (`RST-43`) into the mutation registry, before any product code was written.

**The gap.** `VRS-F007` and the Stage 15 brief define `ghostResource.cancel(ghostId)` and `ghostResource.promote(ghostId, { fullName, email, employmentType, startDate })`. Both operations transition `GhostResource.lifecycle_status` (`Active -> Canceled` and `Active -> Promoted`), but neither signature carries the base version the person acted against. That directly contradicts `VPS-A003` A003-T54: "Every state-transition mutation MUST carry the base `version` it was decided against, and the server MUST reject it with `stale-state` if the record's version has changed." The mutation registry encodes the same rule in `MutationDefinition.stateTransition`, and every current `stateTransition: true` definition carries `expected_version`, including `entity.deactivate` (F223), `holiday.cancel`/`calendar.update`/`pattern.set`/`pattern.clear` (F228), `assignment.cancel` (F240), and `rateCard.update` (F245).

Promotion has a second, inseparable concurrency gap. The brief says the ordinary lifecycle guard gives G07's exclusivity "for free": the first request sees `Active`, writes `Promoted`, and the second sees `Promoted`. That is true only for sequential requests. `services/api/src/mutations/pipeline.ts` builds a mutation plan by reading current state and uses the database's default transaction isolation unless the mutation name is explicitly placed on its serializable list. Two concurrent promotion transactions can therefore both read `Active`, both pass the guard, and both attempt the Employee update and `promoted_to` write. No Ghost mutation exists on the serializable list yet, and the brief explicitly says no new concurrency mechanism is needed. The promised one-winner behavior is consequently not defined by the contract as written.

The two requirements also leave rejection precedence unresolved. A003-T54 says a changed base version **must** reject as `stale-state`. G07 and the Stage 15 report checklist say every subsequent promotion must reject with a message naming who promoted the Ghost and when, using the Ghost's provenance. A request that loses a concurrent promotion race satisfies both conditions. The brief does not say whether it returns a generic `stale-state`, an actor-and-time `already promoted` reason, or a single structured rejection that satisfies both; choosing one in code would invent product behavior.

**Closed by founder-delegated decision, 23 September 2026.** Ruling, extending A003-T54's established pattern (F223/F228/F240/F245) rather than inventing a new one:

1. **Both mutations carry the base version, checked first.** `ghostResource.cancel(ghostId, expectedVersion) -> { success }` and `ghostResource.promote(ghostId, expectedVersion, { fullName, email, employmentType, startDate }) -> { status }` — `stale-state` before anything else, the same shape every other `stateTransition: true` mutation in this codebase already uses.
2. **`ghostResource.promote` joins `services/api/src/mutations/pipeline.ts`'s literal serializable-isolation list**, alongside `calendar.update`, `pattern.set`/`clear`, `assignment.cancel`/`setRateCard` and `rateCard.update` — it is a genuinely multi-step transaction (the GhostResource's own transition, the linked Employee's field update, the `promoted_to` edge write) with exactly the same cross-row-consistency shape those mutations already have, not a single-row update. A transaction that loses the serializable race receives a `40001` and is retried by the pipeline's existing retry loop against fresh state — the same machinery already built for every mutation on that list — so the losing request's version check then correctly sees the new, `Promoted` state. `ghostResource.cancel` is **not** added to that list: unlike promotion, it writes exactly one row (the linked Employee is explicitly untouched by cancellation, per the brief), and a version-conditioned single-row update is race-safe under the database's default isolation the same way every other single-row `expected_version` write already is (`holiday.confirm`'s own exemption from the serializable list, cited in Stage 14's brief, is the precedent for the distinction).
3. **Rejection precedence is resolved by making G07's actor-and-time rejection a specialization of A003-T54's `stale-state`, not a second competing check.** `ghostResource.promote`'s version check is the single source of truth: on a version mismatch, it re-reads the GhostResource's current `lifecycle_status` and its `updated_by`/`updated_at` provenance (already recorded on every write per `VPS-A002`'s universal node conventions); if the current status is `Promoted`, it returns a dedicated "already promoted" rejection naming that actor and time (G07); for any other reason the version moved (a `notes` edit, or `Canceled`), it returns the ordinary generic `stale-state` rejection A003-T54 requires. One check, one code path, two rejection messages depending on what it finds.
4. **`ghostResource.cancel`'s optimistic handler supplies the client's cached `expectedVersion`** the same way every other offline-capable `stateTransition` mutation's optimistic handler already does; a server-side stale-state rejection on reconnection is handled by the same generic optimistic-rejection/rollback path every other mutation on this list already has — no new mechanism.

`VRS-F007`'s API contracts are corrected to show both signatures carrying `expectedVersion`. Stage 15's brief is corrected to match.

**Status: closed.** Stage 15 is unblocked.
