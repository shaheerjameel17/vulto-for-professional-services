### F277 — `VRS-F011`'s own spec still described the week key and expected-hours source in pre-Stage-18 terms

Raised 25 September 2026 by the reviewer, checking `VRS-F011` (Billable vs Non-Billable Pulse) directly against the finished code before writing its Stage 19 brief, per standing practice established at every prior stage boundary. `VRS-F011`'s `UtilizationSnapshot` schema comment for `week_start_date` still read "the first working day of the week per VRS-F004" — the identical pre-`week_start_day` language F276 had already corrected in `VRS-F010`'s own field comment, written before F276 existed and never revisited. Separately, its "Expected hours" section cited `workingDays.count(employeeId, weekStart, weekEnd)` as the source of `expected_hours` — a function that exists under neither that name nor that semantics anywhere in the codebase (`working-days.ts`'s actual `countWorkingDays` returns a day count, not hours). Stage 18 had, in the meantime, already built and tested the real mechanism this feature needs: `getWeek` (`services/api/src/permission/timesheet-queries.ts`) resolves an employee's week via `weekStartForEmployee` (F276's own function) and computes `expectedWeeklyHours` as `hoursOn(tx, principal, employeeId, date)` summed across `isoDatesInclusive(weekStart, addIsoDays(weekStart, 6))` — exactly the figure `UtilizationSnapshot.expected_hours` needs, for the identical employee and week `saveCell`/`submitWeek` already resolve theirs against.

**Closed by direct precedent, 25 September 2026.** No founder consultation needed — this is the same class of correction F276 itself performed on `VRS-F010`'s own stale field comment, now applied to a second document written before F276's mechanism existed. `docs/Vulto_Specs/VRS-F011_Billable_vs_Non-Billable_Pulse.md`'s `week_start_date` field comment and "Expected hours" section are corrected to name `weekStartForEmployee` and `hoursOn`/`isoDatesInclusive` directly. More substantively: `utilizationSnapshot.compute`'s own expected-hours figure must be computed by calling into the identical mechanism `getWeek` already uses — reusing `hoursOn` the same way, or reading `getWeek`'s own `expectedWeeklyHours` directly — rather than a second, independently-written traversal. Two separately-implemented "expected hours for this employee this week" computations is precisely the silent-disagreement risk `VRS-F011`'s own Related Notes section already names for the Bench Forecast's figure, and it applies with equal force to the Speed-Run grid's own numbers, which this feature must never contradict.

**Status: closed.**
