### F220 — resolving the sole membership does not establish an active session workspace

Raised 22 September 2026 while continuing Stage 9 on `stage-9-shell-bootstrap-v3` after F219 was ruled. The F219 endpoint is implemented as specified: a valid session with `activeOrganizationId: null` gets an array containing its one active confirmed workspace, and the server integration test excludes pending, revoked, suspended and other-user rows. The shell then takes that `workspaceId` as selected and constructs `createGraphClient`.

**Proof from the browser and guards.** The previously failing browser test again shows the workspace name never appears, although its trace now records `POST /workspace/list-active-memberships` returning HTTP 200 with exactly one `{ workspaceId, workspaceName }`. The page mounts a shell but remains `Offline` with the generic "Workspace" label. `services/api/src/auth/http.ts`'s `/devices/register` handler rejects the client's `x-vulto-workspace-id` with 403 when it differs from `session.activeOrganizationId`; null necessarily differs. The sync engine catches device-registration failure, but the shape proxy's `accessRevoked` requires a registered device and refuses the shape. `services/api/src/trpc.ts` also returns `principal: null` whenever `activeOrganizationId` is null, so named mutations and protected reads cannot work in the resolved workspace. This is not a data-filtering failure in the new list route; it is a missing transition from a client-side selection to the existing server-authoritative session claim.

**Root cause, checked directly.** `confirmWorkspaceAdmission` (F217's fix) is the only place in production code that ever sets `session.activeOrganizationId` for the ordinary sole-membership case, and it fires exactly once, at confirmation, updating every session row that person holds *at that moment* (`.where(eq(session.userId, confirmed.userId))`, no `activeOrganizationId` filter — safe because it only runs once sole active membership is independently proven). It cannot reach a session created afterward: a fresh sign-in on a new device or browser, for someone already an active confirmed member, creates a new `session` row with `activeOrganizationId` at its column default (`null`, `services/api/src/auth/schema.ts`), and nothing sets it going forward. `services/api/src/auth/config.ts`'s `organization()` plugin config has no auto-activate behavior either. So the "null active organization, exactly one active membership" case Stage 9 point 3 was written for is not a rare edge case — it is the ordinary state of every fresh sign-in for an already-confirmed single-workspace person, and nothing before F220 ever gave that state a way forward.

**Ruling — closed 22 September 2026.** A second new route, `POST /workspace/activate-sole-membership`, added beside F219's route in `services/api/src/auth/http.ts`: session-gated, no request body. It re-derives the caller's active/confirmed memberships itself, from the session alone — it does not trust or accept a client-supplied `workspaceId`, the same discipline `trpc.ts`'s own context-building already follows ("nothing the client sends... can name or alter" the principal). When exactly one exists, it performs the identical write `confirmWorkspaceAdmission` already performs — `update(session).set({ activeOrganizationId })` filtered by that user's id, covering every session row they currently hold — and returns `{ workspaceId }`. When zero or more than one exist, it writes nothing and returns `{ workspaceId: null }`; this is not an error, it is the same "none/many is unresolved" state point 3 already defines, surfaced through this route rather than invented twice. This neither reopens Better Auth's organization plugin (F219's boundary is untouched) nor builds workspace switching (an already-set `activeOrganizationId` is never the target of this write — the route only ever establishes, from null, what independent server-side proof already shows the person's sole active workspace to be).

Stage 9 point 3 is corrected: after the shell resolves a candidate workspace (from `session.activeOrganizationId` directly, or via F219's list route when it was null), it calls this new activation route before constructing the graph client, and only proceeds when the response confirms the same workspace — a stale race where the answer changed underneath falls into the same holding state as "none/many," not a crash. `VPS-F001`'s "Workspace admission control" section gets one more clause naming both new routes together as the session's active-organization boundary.

**Status: closed.** Continue on `stage-9-shell-bootstrap-v3` — the F219 work and existing preliminary bootstrap are unaffected and stay exactly as they are.
