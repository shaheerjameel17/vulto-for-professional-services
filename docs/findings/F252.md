### F252 — Ghost promotion requires a successful audit event that VPS-F004 does not define

Raised 23 September 2026 while resuming Stage 15 (`RST-43`) on F251's ruling, before any product code was written.

**The gap.** `VRS-F007`'s Security Considerations say promotion is audited per `VPS-F004` because the actor and timing matter. Stage 15 Do item 5 is more specific: “reuse the existing `appendAudit` call already wired into every named mutation's `apply()` step,” adding no event type, operation or target. The live code has no such per-mutation call. `services/api/src/mutations/pipeline.ts` delegates audit behavior to `authorizeWrite`; the interceptor audits every denial and successful Tier 1/2/3-sensitive operation according to its rules, but deliberately writes no successful Tier 0 audit entry. Both the GhostResource transition and the linked Employee's operational update are Tier 0.

`VPS-F004` confirms the omission is intentional rather than an implementation oversight. Its “What is logged” section says every denial is logged, while successful-access logging covers Tier 1 and Tier 3 only; G04 repeats that closed rule. Its G02 says AuditEntry creation happens exclusively inside `VPS-A004`'s interceptor and no feature creates one. The live audit schema's closed event taxonomy contains `PermissionDenied`, `SensitiveAccessGranted`, `AuthorizedOperationFailed`, `PrivilegedProjectionAuthorized` and `CryptographicErasureExecuted`. None represents a successful ordinary Tier 0 conversion or lifecycle transition. Reusing `SensitiveAccessGranted` would misclassify a Tier 0 write as sensitive access and violate the event's schema meaning; adding a direct feature-level `appendAudit` call would violate G02 and the architecture check's centralized-writer rule.

This is the same class of taxonomy gap F221 and F225 exposed: a feature requires an audit fact that the authoritative audit vocabulary does not represent. Here it cannot be silently omitted because `VRS-F007` and the Stage 15 brief explicitly make the success audit part of the promotion contract.

**Closed by founder-delegated decision, 23 September 2026, on F221 and F225's own precedent.** Both already resolved the identical shape of gap — a feature spec claiming a `VPS-F004`-audited event for an ordinary, permitted Tier 0 write that the closed taxonomy has no category for — by pointing at provenance the graph already carries, not by extending the taxonomy. The same reasoning applies here without modification:

1. **`VPS-F004`'s closed audit taxonomy is not extended, and no feature-level `appendAudit` call is added anywhere in Stage 15.** Ghost promotion is an ordinary, permitted Tier 0 write — not a denial, not a Tier 1/3 access grant, not an operation failure, not a privileged projection, not an erasure. Reusing an existing event type would misrepresent it (F252's own gap report already rules this out for `SensitiveAccessGranted`); adding a new one for a single feature's ordinary write is exactly what F221 declined to do for Entity transfer and F225 declined to do for Holiday confirmation. `VPS-F004` G02 (interceptor-only creation) and G04 (Tier 1/3-only success logging) are both respected unmodified.
2. **The underlying need — who promoted this Ghost, and when — is already met structurally, with no additional write.** `VPS-A002`'s Universal Node Conventions make `updated_by`/`updated_at` mandatory on every node type except the two named exceptions (`AuditEntry`, the two Aggregate-contribution types); `GhostResource` and Employee are neither, so both already carry them. When `ghostResource.promote` transitions `GhostResource.lifecycle_status` to `Promoted`, `GhostResource.updated_by`/`updated_at` records who and when. `VRS-F007`'s own G03 already establishes `promoted_to` is "created exactly once, at promotion, never modified" — the identical permanent-edge-history shape F221 relied on for `scoped_to_entity`'s transfer record — and `VPS-A002`'s Rule 2 ("edges carry provenance") makes its `created_by`/`created_at` mandatory too. The linked Employee node's own `updated_by`/`updated_at` records the same write on the employment-record side. Together these already answer exactly what `VRS-F007`'s Security Considerations wanted a `VPS-F004` entry for.
3. **`VRS-F007`'s Security Considerations bullet "Promotion is audited per `VPS-F004`" is corrected in place**, the same correction F221 made to `VRS-F003` and F225 made to `VRS-F004`, to instead name the structural provenance above. Stage 15's Do item 5 ("reuse the existing `appendAudit` call... no new event type") is removed outright — there is no `appendAudit` call to reuse or add.

**Status: closed.** Stage 15 is unblocked.
