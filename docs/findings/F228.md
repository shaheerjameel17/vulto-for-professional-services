### F228 — Stage 12's lifecycle mutations omit the A003-T54 base version

`VPS-A003` A003-T54 requires every state-transition mutation to carry the caller's base version and reject `stale-state` if that version moved. F223 applied that exact rule to `entity.deactivate` in Stage 11, adding required `expected_version`. Stage 12's `calendar.update` marks the prior WorkingCalendar `Superseded`; `holiday.cancel` marks a Holiday `Canceled`; `pattern.set`/`pattern.clear` mark the prior WorkingPattern `Superseded`. `holiday.confirm` changes provisional confirmation state and its effective date. Their API signatures in `VRS-F004` and Do items 1–4 give no base-version argument. The shared mutation envelope contains no implicit base version. Reading the row's latest version inside `validate()` would not detect that the person's decision was made against an older value. Adding `expected_version` to these signatures, exempting any operation, or choosing a different conflict rule changes the stated contract.

**Ruling — closed 22 September 2026.** A003-T54's base-version requirement is read the same way F223 already established it for Entity: it applies to a mutation that changes a node's own `lifecycle_status` — a genuine state transition — not to every field write. By that rule: `calendar.update`, `holiday.cancel` and `pattern.set`/`pattern.clear` each move an existing node from `Active` to `Superseded`/`Canceled` and therefore require the caller's base version of *that node* (the one being closed, not the one being created); `holiday.add` creates a new node with nothing to version, exactly like `entity.create`; `holiday.confirm` changes `date`/`confirmed_at`/`confirmed_by` but never `lifecycle_status` — a Holiday stays `Active` whether provisional or confirmed — so it is an ordinary field update, exactly like `entity.update`, and carries no `expectedVersion`, matching that precedent rather than inventing a new one. Corrected signatures: `calendar.update(calendarId, workingWeek, dailyHours, expectedVersion)`, `holiday.cancel(holidayId, expectedVersion)`, `pattern.set(employeeId, workingWeek, effectiveFrom, expectedVersion?)` — optional, present only when a current pattern exists to close (omitted on an employee's first-ever pattern, exactly as there is nothing to version) — and `pattern.clear(employeeId, effectiveFrom, expectedVersion)`, always required since clearing always closes an existing pattern. Each `validate()` checks the given version against the row being closed first (`stale-state` on a mismatch), before any other business rule, exactly `entity.deactivate`'s own ordering. `VRS-F004`'s API contracts and the Stage 12 brief are corrected to carry these arguments.

**Status: closed.** Stage 12 is unblocked on this point.
