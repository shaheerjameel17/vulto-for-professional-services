### F243 — Assignment's `governed_by` edge to RateCard is registered but never written by any contract

Raised 23 September 2026 while checking the code directly before writing the Stage 14 brief (`VRS-F006`), before any product code was written.

**The gap.** `VPS-A002`'s edge registry lists `governed_by` four times against four unrelated pairs, one of them `Assignment → RateCard`, owned by `VRS-F006` — confirmed directly against `packages/schema/src/registry/edges.ts`, where the pairing is real, running registry code, not merely a documentation table. But `VRS-F006`'s own Technical Architecture and API contracts describe rate resolution entirely in terms of Assignment's scalar `rate_card_id` field — already built by Stage 13, matching `VRS-F005`'s Assignment schema (`rate_card_id: UUID, nullable, FK to RateCard`) — and neither `assignment.setRateCard` nor `assignment.create` is ever described as writing the registered edge. Left as specified, the registry declares a relationship no mutation would ever create: `rateCard.usageCount(rateCardId) -> { activeAssignments }` and the rate card editor's version-history "how many assignments still point at it" figure would have no traversal path to answer from, only a full scan of every Assignment row — which A002-T03 already forbids outright: "All edges MUST be first-class objects with their own UUID. Implicit foreign key joins not materialized as edge records are prohibited." FDN-75 closed the identical class of gap once before, for `assigned_to` (Employee → Project "Via Assignment") registered with no materialized edge to the intermediate node.

**Why this isn't a contradiction to resolve by dropping the edge.** Assignment already has a precedent for exactly this shape: `employee_id` and `project_id` are both scalar fields on the Assignment record (per `VRS-F005`'s own schema block) *and* Assignment separately carries `assignment_of` and `assigned_to` edges to the same two nodes, written alongside the scalar fields by Stage 13's mutators — the scalar field serves Assignment's own fast reads, and the edge exists so the *other* side (an Employee or Project) can traverse back to find its Assignments. `rate_card_id` needs the identical shape for the identical reason: Assignment's own resolution algorithm reads the scalar field directly (no cross-feature traversal needed to price itself), while RateCard-side queries (`usageCount`, version history) need to traverse the other direction, which only a materialized edge supports, and which `VPS-A002`'s registry already anticipated by attributing `governed_by`'s ownership to this feature specifically.

**Why the edge is managed manually, not through `historyPolicy`.** `VPS-A002` names only `managed_by` and `scoped_to_entity` as registered for the single-active-outgoing-edge-with-history pattern; `governed_by` carries no such declaration, and adding one now would silently change behavior for the other three unbuilt `governed_by` pairs (`VRS-F018`, `VRS-F062`, `VRS-F063`) this stage has no mandate to design for. The established precedent for a singular governing relationship without that declaration is `governed_by_calendar` (Entity → WorkingCalendar, built in Stage 12): `services/api/src/mutations/calendar.ts` manages singularity itself, closing the entity's prior `governed_by_calendar` edge before opening the new one, rather than relying on an automatic registry mechanism. `governed_by`/Assignment→RateCard follows the same shape.

**Closed by founder-delegated decision, 23 September 2026.**
1. **The scalar field is unchanged.** Assignment's existing `rate_card_id` (built by Stage 13, unmodified by this ruling) remains the value the rate-resolution algorithm itself reads — no cross-feature edge traversal is needed for an Assignment to resolve its own rate.
2. **`assignment.setRateCard` and `assignment.create` (when `rate_card_id` is provided) additionally write the registered `governed_by` edge**, from the Assignment to the chosen RateCard, mirroring the dual scalar-plus-edge shape `employee_id`/`assignment_of` and `project_id`/`assigned_to` already establish.
3. **Singularity is managed manually, mirroring `governed_by_calendar`.** Before writing a new `governed_by` edge from an Assignment, any existing active one from that Assignment is closed (`effective_to` set to the write's timestamp); the new edge opens with `effective_from` at the same instant. No `historyPolicy` declaration is added to the shared `governed_by` edge type.
4. **`rateCard.usageCount` and the version-history "how many assignments still point at it" figure both resolve via `incoming(tx, workspaceId, rateCardId, "governed_by")`**, counting only edges with `effective_to: null` for the live count, never a scan of Assignment rows.

`VRS-F006`'s Technical Architecture, API contracts and Graph Specifications are corrected to state this explicitly, as a new G07.

**Status: closed.** Stage 14 is unblocked; the registered edge has a contract, `rateCard.usageCount` has a traversal path, and Assignment's own resolution needs no change to already-merged Stage 13 code.
