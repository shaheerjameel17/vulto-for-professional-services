### F318 — the client edge mutators never checked the feature-owned edge set

**Found while:** Codex tracing F317's client requirement before writing product code, 26 September 2026 (stage report `f6a894f`); ruled by the reviewer the same day.

F317's ruling said the client optimistic edge mutators read `FEATURE_OWNED_EDGE_TYPES`, so adding `delivered_to` to the set would make all three generic edge mutations refuse it on both sides. They do not: `packages/graph/src/mutators/foundation.ts` imports only `FEATURE_LIFECYCLE_NODE_TYPES`; its `createEdge`, `closeEdge` and `updateEdgeMetadata` parse arguments, load nodes or the edge and write, with no feature-ownership check, and `rg FEATURE_OWNED_EDGE_TYPES packages/graph/src` returns nothing. The server does check the set, so the server refusal (the authority) worked as ruled; the client only lacked the same fast refusal, which the pre-existing `has_skill` and `requires_skill` entries also lacked. The reviewer had written "they read the same shared set" without grepping the client.

**Files:** `packages/graph/src/mutators/foundation.ts`, `services/api/src/mutations/foundation.ts`, `packages/schema/src/mutations/employee.ts`

**Ruling.** **Closed 26 September 2026 by ruling.** The guard is added to the three client edge mutators, mirroring the node guards (`OptimisticRejection("requires-feature-mutation")` when the shared set has the edge type), and it covers `has_skill` and `requires_skill` as well, aligning the client with a server that already refused them. The server remains the authority; the client guard prevents an optimistic write the server would reject. Any existing client test that relied on the old acceptance is reported and adjusted only on that assertion. Lesson (already standing): never write "X shares Y" without grepping X.
