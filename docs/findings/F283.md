### F283 — `VRS-F005`'s bench computation has never implemented the Pitch exclusion `VRS-F012` assumes it has

Raised 25 September 2026, checking `VRS-F012` directly against the code before writing its Stage 20 brief. G02 requires this feature to determine bench status "by calling `VRS-F005`'s bench computation," explicitly forbidding "its own query for Assignment coverage or Pitch exclusion" — and the spec's own Decisions Recorded section states this as a deliberate design correction: "Previously it implemented its own bench query including the Pitch exclusion... The computation now lives with the view that renders it," i.e. `VRS-F005`. The API contract names the call site directly: `benchForecast.computeBench(employeeId)`.

Neither claim survives a direct read of `services/api/src/permission/bench-forecast-queries.ts`. No function named `computeBench`, or anything resembling a single-employee bench-status call, is exported from that file — its two exports are `getBenchForecastAggregate` (an authorization-scoped, cohort-wide utilization aggregate across every employee at once) and `getBenchForecastCosts` (a compensation-based cost figure for a supplied list of employee IDs, reading the Tier-1/2 `compensation` partition — the exact salary source `VRS-F012` explicitly says it must never touch). The actual per-employee bench-day computation lives in a private, unexported helper, `cohortEmployee`, called only from within the cohort-building path `authorizedCohort` uses. Reading `cohortEmployee` itself: it builds each employee's `benchDays` array by walking the window date-by-date, excluding a date only if it is not a calendar working day (`resolvedDayOn`) or is covered by an Active Assignment (`assignmentCovers`) — there is no check anywhere in the function, or anywhere else in the file, against `TimesheetEntry` or the `Pitch` time-classification category. `VRS-F005` (Stage 13) was built and merged before Pitch time tracking existed at all (`VRS-F009`/Time Classification Taxonomy, Stage 17; `VRS-F010`/Timesheet Speed-Run, Stage 18) — Stage 13's own briefing already flagged this as a forward dependency and deferred it (F239, "the Pitch-day exclusion's unbuilt dependency chain"), and no later stage has revisited `bench-forecast-queries.ts` to close that deferral now that Pitch tracking is real.

Without a fix, `VRS-F012`'s own acceptance criterion — "an employee has logged pitch hours every day this week and holds no assignment... the bench computation returns zero bench days, no alert is written" — cannot pass: every pitch-only week would currently read as a full bench week and fire a false alert.

**Closed by direct precedent, 25 September 2026.** No founder consultation needed — `VRS-F012`'s own text already states the intended architecture; this closes the gap between that stated intent and what Stage 13 actually shipped, the same kind of already-merged-stage extension Stage 19 itself made to `getWeek` for a later feature's need. `cohortEmployee`'s exclusion condition in `services/api/src/permission/bench-forecast-queries.ts` gains a third check alongside the calendar and Assignment-coverage ones: a date is excluded from `benchDays` if the employee has a `TimesheetEntry` with `time_category: "Pitch"` on that date, read the same trusted, internal way `utilizationSnapshotCompute` already reads `TimesheetEntry` for its own derived computation (F280's own precedent — an internal read feeding a derived Tier 0 figure, not a raw exposure of protected rows to any caller). A new function, `computeBenchStatus(tx, workspaceId, employeeId, asOfDate, guard)`, is exported from the same file, built on the identical `cohortEmployee` exclusion logic (never a second, parallel implementation), returning the single employee's `benchDays` array and `bench_start_date`. `revenueGapAlert.evaluate` calls this new export — the real name and shape replacing the spec's non-existent `benchForecast.computeBench`.

**Status: closed.**
