### F347 — notification fixtures for the browser proof come from the delivery helper, not a generic mutation

**Found while:** the builder's pre-build trace of UI-1, 27 September 2026.

Do item 6 asks for Informational and backdated notifications "through the API's real pipeline helpers". A `Notification` is feature-owned and written only by the delivery path; no generic mutation exists, both registered rules produce `ActionNeeded`, and `sync-browser-support.ts` exports no delivery helper. The production delivery function is `deliverNotification(tx, delivery, now)` in `services/api/src/mutations/notification-delivery.ts`, which takes a category and a time and performs the authorized node, edge and audience writes.

**Files:** `services/api/src/mutations/notification-delivery.ts`, `services/api/src/test/sync-browser-support.ts`

**Ruling.** **Closed 27 September 2026 by ruling.** Seeding through `deliverNotification` satisfies the brief: it is the production write path, authorized and audience-materialized, not a mock. It is re-exported from `sync-browser-support.ts` (a test-support file; no product code or API surface changes; if the arch gate refuses the import, report it). All later state changes in the tests go through the real read-state mutations. Additionally, at least one `ActionNeeded` row should come from a real rule fired by a real mutation (for example a submitted week that trips the anomaly flag) if the suite's existing helpers can do it cheaply; otherwise say so in the report.
