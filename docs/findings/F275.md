### F275 — `logged_against` denies both its own endpoints for an ordinary Team Member

Raised 24 September 2026 by Codex, who resumed Stage 18 after F274's mechanism was implemented and found that saving a Billable or Pitch cell still failed for an ordinary Team Member, independently of F274's now-working fix: the `logged_against` edge (TimesheetEntry to Assignment or Pitch) was refused at both endpoints. `services/api/src/permission/interceptor.ts`'s `edgeRoleDecision` requires `Full` on an edge's endpoint unless that edge's own registration declares `readSufficientEndpoints` for the endpoint's node type — `sufficient = outcome === "full" || (outcome === "read" && readSufficientEndpoints[nodeType] === true)`. `packages/schema/src/registry/edges.ts`'s `logged_against` registration declared no `readSufficientEndpoints` at all, so a Team Member's own Read-level access to either endpoint never counted as sufficient. Codex correctly declined to invent a fix for either endpoint and reported both, together, as one blocker, since the two turned out to need materially different rulings.

**The Assignment half** traced directly to an existing precedent and needed no founder consultation. `assigned_to`'s own registration (`pairs: [["Assignment", "Project"]]`, from Stage 16's F262) already declares `readSufficientEndpoints: { Project: true }` for the identical shape of problem: a writer holding only Read on an endpoint that should still be allowed to reference it. Team Member holds `READ_ANY()` on Assignment (confirmed directly in `packages/schema/src/policy/policy-table.ts`, unchanged by this ruling), so the identical declaration — `readSufficientEndpoints: { Assignment: true }`, added to `logged_against`'s own registration — closes this half without widening anyone's existing Assignment visibility; it only lets the pre-existing Read count as sufficient for this one edge write.

**The Pitch half** is a genuine architectural fork. Team Member's outcome on `Pitch:identifying` is unconditionally `NONE` (confirmed directly at `policy-table.ts`'s `"Pitch:identifying"` block, `"team-member": NONE_ANY()`), not `READ`, so no `readSufficientEndpoints` declaration can fix it — the formula only ever accepts a `read` outcome as sufficient, never `none`. This was not an oversight: F264–F267 made Team Member's `NONE` on Pitch a deliberate restriction, since pitch details can be commercially sensitive before a deal is won. Closing this half therefore meant an actual access-widening decision, not a mere reclassification, and Codex correctly named three materially different security choices with no existing rule picking one: a blanket Team Member Read grant on every Pitch (rejected — undoes the deliberate F264–F267 restriction for everyone, not just people staffed on the pitch in question); a staffing-scoped grant, where access follows exactly who is currently staffed on that one pitch and nothing broader; and a mutation-local exception bypassing the interceptor entirely (rejected outright — `VPS-A004` already states the interceptor is the only place access is decided, and a side door there would break that guarantee for every future auditor, the identical alternative already rejected during F274's own design).

This was put directly to the founder, who chose the staffing-scoped grant and, on being asked directly whether it was the most robust long-term choice, asked for the stronger version rather than a Pitch-specific hand-coded check: a reusable, declarative mechanism any future participant-scoped feature can register into rather than reinvent. `VPS-A004`'s own "Three recurring override patterns" section already named, but had never implemented, exactly this shape of grant for InterviewRound, FeedbackEntry, and OnboardingTask — confirmed by grep across `services/api/src/permission/interceptor.ts` for any trace of `participating_in`, `InterviewRound`, `assignee`, `OnboardingTask`, or `participant`: zero results, so this was a documented, founder-approved concept with no code anywhere, and those three features remain unbuilt. `staffed_on` (Employee to Pitch, owner `VRS-F009`) is already a properly lifecycle-managed edge — Stage 17's `pitch.staffEmployee`/`pitch.unstaffEmployee` close it on unstaffing — and `services/api/src/graph/store.ts`'s `outgoing(tx, workspaceId, nodeId, edgeType, at?)` already filters through `activeAt(at)`, the same half-open interval check `rowScopeSatisfied` already relies on for `managed_by`/`triggered_by` resolution, so reusing it resolves only currently-active staffing with no new lifecycle logic needed.

**Closed, 24 September 2026.** Assignment: `logged_against`'s registration in `packages/schema/src/registry/edges.ts` gains `readSufficientEndpoints: { Assignment: true }`, alongside its existing `governingPartitions: { Pitch: "identifying" }` from F267. Pitch: a new closed registry, `packages/schema/src/registry/participant-grants.ts`, exports `PARTICIPANT_GRANTS: Readonly<Partial<Record<NodeType, ParticipantGrant>>>`, each entry naming `viaEdgeType`, `fromNodeType`, and an `outcome` of `"read"` or `"full"`; its first and only entry is `Pitch: { viaEdgeType: "staffed_on", fromNodeType: "Employee", outcome: "read" }`. A new resolver in `services/api/src/permission/interceptor.ts`, `participantGrantSatisfied(tx, principal, nodeType, nodeId, asOf, context)`, resolves a member principal's own Employee (via the same `resolveEmployeeForUser` helper `rowScopeSatisfied` already uses) and checks for a currently-active outgoing edge of the declared type to the target node via `outgoing()`. This is wired only into `edgeRoleDecision`, as an independent additional path to "sufficient" alongside (never replacing) the existing role-cell and `readSufficientEndpoints` paths — deliberately not into `decideRead`/`bestCell` generally, since general staffed-Team-Member Pitch read access is already separately handled by `pitch.listStaffedFor` from Stage 17/F264–F267, and widening that general path was never the question here. The mechanism is intentionally reusable: when InterviewRound, FeedbackEntry, or OnboardingTask are eventually built, each adds its own entry to `PARTICIPANT_GRANTS` and wires whichever consumer it actually needs, reusing this same table rather than inventing a parallel one. `docs/Vulto_Specs/VPS-A004_Graph_Permission_Layer.md`'s "Three recurring override patterns" section is corrected to record this as real, implemented code rather than documented intent, with Pitch as its first instance; `docs/Claude_Code_Build_Prompt.md`'s Stage 18 section and `docs/Reviewer_Handoff.md`'s section 19 are corrected to match.

**Status: closed.**
