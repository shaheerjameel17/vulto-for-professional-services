### F259 — Stage 16's server-only execution contract contradicts `VRS-F008`'s local and offline guarantees

Raised 24 September 2026 while tracing the corrected Stage 16 brief into the existing server-authoritative mutation and device-cache boundaries, before any product code was written.

**The gap.** `VRS-F008` makes two execution-boundary promises that the Stage 16 brief explicitly reverses:

1. Its Non-Functional Requirements say `conflictCheck.evaluate` “returns within 100ms from the local graph, before any save is attempted.” The same section says “Computation, panel and override all function fully offline.” The feature's flow depends on that evaluation opening the resolution panel before a save.
2. Stage 16 Do item 4 instead defines `conflictCheck.evaluate` only as a new `services/api/src/permission/conflict-queries.ts` server query. Do item 9 then marks `conflictResolution.overrideAndProceed` `onlineOnly: true`, gives it no optimistic handler, and says an offline caller remains pending until server confirmation because both the manager/Owner gate and corrected capacity total are server-only facts. The stage is expressly server-side only and defines no portable or device-cache evaluator.

These are observable opposite behaviors. A network request cannot guarantee a local-graph sub-100ms result or operate during a network cut. An `onlineOnly` mutation with no optimistic handler cannot complete an override fully offline. Conversely, adding a client-side evaluator and optimistic override would contradict Do item 9's explicit server-confirmation decision and would create a device-side answer to the authorization and capacity questions the corrected brief says are server-only.

The current code does not supply an implicit resolution. `assignment.create` and `assignment.update` have optimistic handlers, but the authoritative capacity validation exists only in `services/api/src/mutations/assignment.ts`; the client handlers do not compute working-day-aware capacity. `resolvedDayOn` is a server graph wrapper, while the portable `resolveWorkingDay` function needs caller-supplied calendar, holiday and pattern facts. No Stage 16 contract defines how the local query assembles those facts, what happens when the permission-filtered device cache lacks one, or how a locally accepted override reconciles with the server-only manager gate.

A ruling must select one execution boundary and correct the other document before implementation. If the server-authoritative brief wins, `VRS-F008`'s local-graph 100ms and fully-offline statements need the same explicit server-confirmed correction used for other post-pivot features. If the feature spec's local/offline contract wins, the brief needs a portable local evaluator, its inputs and failure behavior, and a reconciled override authorization model rather than `onlineOnly`.

**Closed by founder-delegated decision, 24 September 2026.** The contradiction is real, but it is the brief that drifted from established precedent, not the spec that is stale — re-reading the actual code this codebase already ships resolves both halves without touching `VRS-F008`'s NFRs at all.

1. **`conflictCheck.evaluate` is a portable local query, not a server query.** `services/api/src/mutations/assignment.ts`'s own `assignmentCreate` optimistic handler already carries this exact, pre-Stage-16 comment: *"Capacity is deliberately server-only: one device may not have another device's newest Assignment yet."* That is a standing architectural decision this stage does not reopen — the local cache can never be the *authoritative* source for the 100% ceiling, full stop. But `conflictCheck.evaluate`'s own NFR ("before any save is attempted," "100ms," "fully offline") is asking for a fast, best-effort, advisory figure for the interactive panel and the soft warning, not a second source of truth — and this codebase already has the exact pattern for that: `packages/graph/src/queries/bench-forecast.ts` is a portable local query reading `localNodes`/`localEdges` from the device's own replicated Tier 0 cache (`packages/graph/src/queries/cache-data.ts`) and calling the same pure `resolveWorkingDay` function `validateCapacity` uses server-side (F256), entirely on-device, no server round-trip. `conflictCheck.evaluate` is built the same way, in a new `packages/graph/src/queries/conflict-check.ts` — not in `services/api/src/permission/conflict-queries.ts` as Stage 16's Do item 4 specified. The server's `validateCapacity` remains the sole *authority*; nothing about its deliberate server-only design changes, and the two never need to agree exactly — the local figure is best-effort by design, the same caveat `assignmentCreate`'s own comment already lives by.
2. **`overrideAndProceed` gets a genuine optimistic handler, not `onlineOnly`.** `assignmentCreate`'s optimistic handler performs *no* capacity check at all, locally or otherwise — it writes the Assignment unconditionally and lets the server's `validateCapacity` reject it afterward via the outbox's existing undo path if the ceiling is actually breached. `overrideAndProceed` is structurally the same write (an Assignment, this time deliberately above the ceiling) plus the override fields the caller already supplies. The manager/Owner gate is not a server-only fact either: `managed_by` is a Tier 0 edge, already locally replicated, and `VRS-F008`'s own Interface Specification already requires the client to resolve it locally regardless ("Where the viewer is not the employee's manager or an Owner, the option does not render"). The optimistic handler writes the Assignment locally exactly as `assignmentCreate`'s does, using the client's own locally-resolved manager/Owner check to decide whether to attempt the write at all; the server re-verifies that same gate authoritatively inside the mutation — never trusting the client's own permission decision, the same as every other permission-enforced mutation in this codebase — and rejects via the same undo path on a stale or wrong local read. No new mechanism is invented; this is `assignmentCreate`'s own pattern, reused, not `ghostResource.promote`'s (that mutation's `onlineOnly` status is for a genuinely different reason — a multi-row serializable transaction and a workspace-wide uniqueness check neither of which applies here).
3. **`conflictResolution.sweepOvercommitted` is unaffected.** Nothing in the spec claims the sweep's own computation runs locally — "the sweep is best-effort and runs on next connectivity" describes the overcommitment list screen showing cached results while offline, not the sweep itself. It stays server-side per F258's own ruling, unchanged.

This resolves F259 without reopening F255–F258. Stage 16's brief (Do items 2, 4, 5, 9, Done criteria, What to check) and `VRS-F008`'s NFR section are corrected to match.

**Status: closed.** Stage 16 is unblocked; `codex/stage-16-capacity-conflict-resolution` resumes on the corrected brief — no branch restart.

**Status: open.** Stage 16 is blocked before product code; implementing either side now would invent which authoritative contract to discard.
