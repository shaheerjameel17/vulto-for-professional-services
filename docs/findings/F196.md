### F196 — no mechanism was named for projecting a `pending` membership's graph

Surfaced writing FDN-85's decision memo, holding F111 (FDN-60's exact-workspace session guard) and FDN-85's own admission criterion at the same time.

`VPS-F001`'s Workspace-admission model and F112's closure both say a grant "admits only after its graph projection is confirmed." Neither document says *how* the projection is written. F111 / FDN-60's `requireCurrentWorkspaceSession` — which FDN-84's sealed-store unlock calls — refuses a membership that is not `active` and `projection_state = confirmed`. A brand-new membership is `pending/pending`. So the sealed store cannot be unlocked, an ordinary graph `mutate` cannot run, and the membership cannot reach `confirmed` until its projection lands: a genuine bootstrap cycle, not visible from either document alone.

**Closed by FDN-85's design pass (Q1–Q7 memo, founder ruling on Q1c — option (b) narrowed).** A single-use, server-signed **projection grant** breaks the cycle:

* minted by a cookie-authenticated route (`POST /workspace/create`) only after FDN-60's `createPendingWorkspaceAdmission` records the central pending row;
* bound to exactly one `(workspace, device, membership)`, hash-stored, consumed on first use (a CAS on `consumed_at IS NULL`), re-validated against the membership still being `pending/pending` at consume time so a race revocation cannot be projected;
* carrying the server half of the device's sealed-store unlock secret — provisioned here for the still-`pending` membership, the one thing the ordinary unlock path forbids;
* it **bypasses per-write role authorization** because the command's own gating is the authorization: `createPendingWorkspaceAdmission` already succeeded server-side, the grant is single-use and hash-verified, and the projection command is structurally incapable of writing anything but the reserved-type records (it takes typed scalars, not fragments). This is a distinctly named path — `commitPrivilegedProjection`, not a flag on `authorizeNodeWrite` / `authorizeEdgeWrite` — and the outbox/reconciliation log records that a write took the exception path (`authorizationPath: "privileged-projection-exception"`), never indistinguishable from an ordinary authorized write. **The exception covers this issue's projection command only; any future privileged write needs its own ruling.**

The generic `mutate` gate additionally reserves the `Workspace` and `WorkspaceMembership` node types and the `membership_of` / `membership_in` edges (refused `unsupported`, the same treatment a Movable Tree move gets), so the projection command is the sole writer. The runtime instance the grant opens is **projection-only**: it runs exactly one command, refuses an ordinary `mutate` for its whole lifetime (returns `denied`, exactly as for a caller with no grant), and is discarded — never returned to a caller — after that command. Proven on the real stack: the founding grant projects five records, the membership confirms, it queries back, and an ordinary `mutate` through the same handle after the projection is denied. Recorded in `VPS-F001`'s Workspace-creation section, `VPS-A002`'s edge conventions, and G05.
