### F307 — Notification's recipient-only access cannot be resolved by any code

**Found while:** briefing Stage 25 (`VPS-F003`), 26 September 2026, by checking the spec against the code before writing the brief.

Notification's access shape cannot be resolved by any code: `Recipient-only` in `packages/schema/src/policy/policy-table.ts` resolves to `none` for all five roles, including the recipient, through a `recipient-only-unresolvable` scope that `services/api/src/permission/interceptor.ts::rowScopeSatisfied` has no branch for (it decides only `own`, `direct-reports` and `own-plus-team`, all through an Employee subject). So a person could never read their own notification through the interceptor, and the audience materializer (which decides every row with `decideRead`) would never put one on any device.

**Files:** `packages/schema/src/policy/policy-table.ts`, `services/api/src/permission/interceptor.ts`, `services/api/src/audience/materializer.ts`, `packages/schema/src/registry/edges.ts`

**Ruling.** **Closed 26 September 2026 by ruling.** Add a resolvable scope, `recipient`, replacing `recipient-only-unresolvable`: a Notification row satisfies it for a member principal when its `delivered_to` edge's target node id equals the principal's `userId` (a `User` node's id is the Better Auth account id, F204). Every role's cell becomes `full` with scope `recipient`, source text unchanged ("Own only"), so the policy-table fidelity test still reads the literal matrix; no role, Owner included, resolves any other person's row, which is G04's rule at the layer that actually enforces it. The audience materializer needs no change if the Notification and its `delivered_to` edge are written in one transaction and both ids reach `onRowsChanged`. Writing stays closed: `Notification` joins `FEATURE_LIFECYCLE_NODE_TYPES`, so `graph.createNode` refuses it, and only the delivery principal (F308) and the recipient's own read-state mutations write it.
