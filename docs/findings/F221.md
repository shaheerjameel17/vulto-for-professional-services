### F221 — Entity transfer does not fit the Silent Audit Log's closed taxonomy

Raised 22 September 2026 while briefing Stage 11 (`VRS-F003`, Multi-Entity and Jurisdiction Foundation), the next MVP-order feature after RST-33. `VRS-F003`'s Security Considerations states plainly: "Entity transfer is an audited event per `VPS-F004`, because it changes which employment law governs a person." Checked directly against `VPS-F004`'s own schema: `event_type` is a closed enum of exactly five values — `PermissionDenied`, `SensitiveAccessGranted`, `AuthorizedOperationFailed`, `PrivilegedProjectionAuthorized`, `CryptographicErasureExecuted` — enforced by a database check constraint (`services/api/src/audit/schema.ts`), and every existing writer of `AuditEntry` (`services/api/src/permission/interceptor.ts`'s automatic Tier 1/3 access and denial logging, `services/api/src/protected/erasure.ts`'s key-destruction event) uses one of those five. An Entity transfer is an ordinary, permitted, Owner/HR-Admin-initiated write of Tier 0 data — not a denial, not a sensitive-tier access grant, not an operation failure, not a privileged projection, and not a cryptographic erasure. None of the five categories describes it, and `VPS-F004`'s own body (its screen, its filter set, its acceptance criteria) confirms the log's whole design is permission- and access-focused, not a general business-activity trail.

**Ruling — closed 22 September 2026.** The underlying need — "who moved this employee to which entity, and when, so it can be questioned after the fact" — is already met structurally and does not need the Silent Audit Log at all. Every `scoped_to_entity` edge carries `created_by`, `created_at`, `effective_from` and `effective_to` per `VPS-A002`'s Universal Edge Conventions, and G02/G03 already require the full transfer history to be preserved and traversable. That is a complete, permanent, queryable record of every transfer, its actor and its timing — exactly what the spec's stated reason for wanting an audit trail asks for. Extending `VPS-F004`'s closed taxonomy for one feature's ordinary write would set a precedent this project has deliberately avoided elsewhere (cf. F206's system-operation additions, which were all genuinely access- or erasure-related); it is also unnecessary. `VRS-F003`'s Security Considerations bullet is corrected in place: Entity transfer is recorded through the edge's own history, not through `VPS-F004`.

**Status: closed.** No `VPS-F004` change, no migration, no new audit call in `employee.setEntity`.
