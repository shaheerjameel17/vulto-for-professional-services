### F365 — UI-3's entire local query layer is already built and fully unit-tested, but orphaned

**Found while:** Tracing `VRS-F005` (The Bench Forecast) directly against the code before writing UI-3's brief, per standing practice. Checking whether the local, offline-first reads the spec requires (`benchForecast.get`'s 200ms/150-employee/offline budget, G04's Contextual Intelligence Panel traversal, the capacity-conflict local check VRS-F008 built) already existed, or would need building from scratch the way UI-1's and UI-2's equivalents did (F340, F350).

They already exist, complete, with their own passing unit tests, and are called from nowhere: `packages/graph/src/queries/bench-forecast.ts::getBenchForecast` (255 lines — resolves Employee/Assignment/GhostResource/OpenRole rows, calendar-aware bench derivation via `resolveWorkingDay`, filter matching via the shared `matchesBenchForecastFilters`, paired with `bench-forecast.test.ts`); `packages/graph/src/queries/contextual-intelligence.ts::getContextualIntelligence` (the exact G04 two-hop shape — local Tier 0 skills/openRoles/references plus an injected `getProtected` callback for Tier 2 BurnoutAlert/FlightRiskSignal, paired with `contextual-intelligence.test.ts`); and `packages/graph/src/queries/conflict-check.ts::evaluateConflict` (the portable local capacity check `VRS-F008`'s F259 ruling required, paired with `conflict-check.test.ts`). None of the three is registered in `packages/graph/src/query.ts`'s `deviceQuerySchema` discriminated union, none is dispatched in `packages/graph/src/sync-client/query.ts`'s `runCacheQuery` switch, and a repository-wide grep finds no caller of any of the three anywhere under `apps/roster-web`. `apps/roster-web/src/lib/bench.ts` and `ForecastPanel.tsx` instead compute an equivalent, independently-written derivation entirely from `fixtures/roster.ts`/`fixtures/calendar.ts` (hardcoded `SKILLS`/`BURNOUT` maps, a fixture `TODAY` constant, no graph read at all).

This is the same shape F341 found for UI-1 (the skill-match call had no web caller) and F350 found for UI-2 (the directory's local query didn't exist yet) — except here the query layer is not missing, it is complete and shipped as dead code, most likely built ahead of its screen during the Stage 13/16 backend work per this project's own "backend stages 11 to 27 each deferred their screen" framing.

**Files:** `packages/graph/src/query.ts`, `packages/graph/src/sync-client/query.ts`, `packages/graph/src/queries/{bench-forecast,contextual-intelligence,conflict-check}.ts` (unchanged, already correct), `apps/roster-web/src/lib/bench.ts`, `apps/roster-web/src/components/ForecastPanel.tsx`.

**Ruling.** **Closed 29 September 2026, mechanical wiring, no founder ruling needed** — direct precedent from F341's and F350's own resolution (extend the existing `device-query` kind with more names; do not build a second local-query mechanism). UI-3's brief adds `benchForecast.get`, `contextualIntelligence.get` and `conflictCheck.evaluate` to `deviceQuerySchema` and `runCacheQuery`, exactly as `employee.listForDirectory` and `employee.get` were added for UI-2, and wires `apps/roster-web`'s Bench Forecast screen and Panel to them in place of the fixture derivation. None of the three query files themselves needs a code change — they are reused as written, including their existing test coverage, which the stage's own gates must keep passing.

**Status: closed** (mechanical wiring, folded into the UI-3 brief's Do item 1).

**Correction, 29 September 2026.** This finding's claim that "none of the three query files themselves needs a code change" is wrong for `bench-forecast.ts` — see [F366](F366.md), raised during Codex's UI-3 pre-build trace. The wiring conclusion above (extend `deviceQuerySchema`/`runCacheQuery`, don't build a second mechanism) stands unchanged; only the "no code change" clause is superseded.
