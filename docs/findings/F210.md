### F210 — dropping `device_unlock_secret` would un-revoke devices

Raised 21 September 2026, building Stage 6's shape proxy, which reads the workspace-scoped revoke.

**The fact.** F191 split device revocation in two so that one tenant cannot destroy another's local data: a workspace Owner's Revoke is scoped to that workspace and is stored as `device_unlock_secret.revoked_at` for `(workspace, user, device)`; global retirement (`device.is_revoked`) belongs to the device's own user. The Stage 7 brief drops `device_unlock_secret` with the retired unlock code. Nothing else stores the workspace-scoped revoke.

**Founder ruling, 21 September 2026 — an amendment to Stage 7's item that drops `device_unlock_secret`.** In Stage 7, before dropping the table:
1. create a control-plane table `device_workspace_revocation (workspace_id, device_id, revoked_at, revoked_by, reason)` with primary key `(workspace_id, device_id)`, identifiers only, never synced;
2. backfill it from `device_unlock_secret` in the same migration;
3. repoint every revoke check, the session path and the shape proxy, to the new table;
4. then drop `device_unlock_secret`;
5. add a test proving a device revoked before the migration is still revoked after it.

Until then the shape proxy reads `device_unlock_secret` (`services/api/src/sync/shape-proxy.ts`), with a comment naming this finding.
