### F251 — Stage 15's “no permission override” requirement contradicts the Stage 13 policy rows it inherits

Raised 23 September 2026 while resuming Stage 15 (`RST-43`) on F250's ruling, before any product code was written.

**The gap.** Stage 15 says three times that `GhostResource` and `OpenRole` have no `MATRIX_OVERRIDES` entry: its opening code trace says both already fall through to the default policy class, Do item 9 requires a test proving “zero `MATRIX_OVERRIDES` entry for either,” and the Done criteria require Owner/HR Admin full plus Manager/Team Member read-only “per the existing default class.” The live code says the opposite. `packages/schema/src/policy/policy-table.ts` already contains explicit `GhostResource` and `OpenRole` overrides granting Owner/HR Admin full and Finance Admin/Manager/Team Member read. Stage 13's authoritative brief Do item 8 explicitly required those exact five workspace-staffing rows (`Assignment`, `Project`, `Client`, `GhostResource`, `OpenRole`); commit `f2d928d` added them, the policy test exercises them, the Stage 13 report records them as completed, and the independent review approved the stage.

Deleting the two rows does not make Stage 15's stated test pass. `VPS-A004`'s Standard fallback grants Manager `Full (direct reports)` and Team Member `Read (own + team)`, not unqualified read. The interceptor can resolve those person-scoped qualifiers only for an Employee row (and the separately registered BurnoutAlert subject path); for `GhostResource` and `OpenRole`, `rowScopeSatisfied` returns false. With no explicit overrides, Manager and Team Member therefore receive `none`, not the read-only access Stage 15 requires. The two code paths are materially different, not redundant representations of the same policy.

There is a second product-level conflict in the same decision. `VRS-F007`'s Creating a Ghost flow says an Owner, HR Admin **or Manager** creates one. Both the existing Stage 13 override and Stage 15's Done criterion grant Manager read-only, so the permission interceptor would reject `ghostResource.create` for a Manager. Changing Manager to full would satisfy that user-facing flow but contradict the two already-approved briefs; retaining read-only would require correcting the feature flow. No existing text says which fact wins.

**Closed by founder-delegated decision, 23 September 2026.** Ruling, keeping the codebase's existing node-type-level permission model rather than inventing a new one:

1. **Stage 13's `MATRIX_OVERRIDES` rows for `GhostResource` and `OpenRole` are retained, not removed.** They are a real, tested, already-approved policy decision (Stage 13 Do item 8, commit `f2d928d`), not a redundant restatement of the `Standard` default — `rowScopeSatisfied` cannot resolve either node type's Manager/Team-Member cells without them, so deleting them would silently drop Manager and Team Member to `none`, the opposite of Stage 15's own intent. Stage 15's brief is corrected everywhere it claimed the two node types "already fall through to the default policy class" or required a test proving "zero `MATRIX_OVERRIDES` entry" — that claim was simply wrong.
2. **`GhostResource`'s `manager` cell is extended from `READ_ANY()` to `FULL_ANY()`.** This is the one cell that must change: `VRS-F007`'s own Creating-a-Ghost flow names Owner, HR Admin **or Manager** as able to create one, and `authorizeWrite` requires a literal `"full"` outcome for any write — there is no finer-grained "can create, can't otherwise write" permission tier anywhere in this codebase (confirmed by an exhaustive grep across every mutation/permission file for a per-mutation role gate; none exists). Read-only Manager access, as Stage 15's Done criteria wrongly required, makes the feature's own primary creation flow unbuildable. `team-member` stays `READ_ANY()` — no text anywhere gives Team Member a create/write role for Ghosts. `OpenRole`'s override is untouched in both cells; Stage 15 never writes an `OpenRole` node, only the `placeholder_for` edge from `GhostResource`.
3. **Manager's resulting full access to `ghostResource.promote`/`cancel` is accepted, not a second gap.** This codebase's permission model is node-type-level, one cell per role per node type — there is no mechanism to grant "full" for one mutation on a node type and "read" for another, and none has ever been built across fourteen prior stages. `VRS-F007`'s own Security Considerations already state Ghost Resources "carry no elevated privacy concern" and that promotion is "a data-integrity concern rather than a confidentiality one," audited per `VPS-F004` regardless of actor. Building a first-of-its-kind per-mutation role gate for this one case would be disproportionate to a risk the feature's own spec already disclaims, and no existing precedent supports it. If a narrower rule is ever wanted, it is scoped and built as its own feature, not invented ad hoc here.
4. **`policy-table.test.ts`'s shared `it.each(["Assignment", "Project", "Client", "GhostResource", "OpenRole"])` test is split.** `GhostResource` gets its own dedicated test (`manager: "full"`, `"team-member": "read"`, `owner`/`hr-admin: "full"`); `Assignment`, `Project`, `Client` and `OpenRole` keep the original shared assertions unchanged, since none of their cells change.

`VRS-F007` gains a Security Considerations note recording that Manager's write access is node-type-scoped, not mutation-scoped, and that this is a deliberate, accepted consequence of the existing permission model. Stage 15's brief is corrected to match all four points.

**Status: closed.** Stage 15 is unblocked.
