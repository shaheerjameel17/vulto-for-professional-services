### F260 — F259's local authorization checks have no caller-role input

Raised 24 September 2026 while tracing F259's corrected local query and optimistic mutation contracts into the device-cache APIs, before product code was written.

**The gap.** F259 requires two local authorization results, but neither corrected execution contract receives the facts needed to produce them:

1. Stage 16 Do item 4 requires `conflictCheck.evaluate(database, { employeeId, startDate, endDate, billablePercentage, excludeAssignmentId?, nearCapacityWarningThreshold })` to return `callerCanEdit`, resolved from the caller's roles and the employee's active `managed_by` edge. The function input contains no caller user id, caller Employee id or roles. Its prescribed local node set is Assignment, Employee, Project, WorkingCalendar, Holiday and WorkingPattern — no User or WorkspaceMembership fact from which a caller role could be discovered.
2. Do item 9 requires the optimistic `conflictResolution.overrideAndProceed` handler to reject locally unless the caller is the target employee's manager or an Owner. `MutatorContext` in `packages/graph/src/mutators/foundation.ts` carries `cache`, `workspaceId`, `userId`, `mutationId` and `now`; it carries no role or membership identity. `OptimisticCache` in `packages/graph/src/mutators/cache.ts` supports point node/edge access and edge traversal only, with no node enumeration that could discover a WorkspaceMembership record.

The Manager half is mechanically answerable from the existing Tier 0 cache: follow the target Employee's active outgoing `managed_by` edge, read the manager Employee and compare its `user_id` with `MutatorContext.userId`. The Owner half is not. An Owner need not be the target employee's manager, and Owner is a workspace role rather than a fact carried on either Employee node. The query's `callerCanEdit` result has the same problem: F255 restores `Assignment.manager` to unscoped Full, while Owner and HR Admin also have Full, so editability cannot be derived from the target edge alone without the caller's role context.

Silently applying every optimistic override and relying on server rejection would contradict the explicit local gate F259 just added. Rejecting every non-manager would refuse valid Owner overrides. Extending the query arguments and `MutatorContext` with trusted role facts, teaching the cache API how to find membership facts, or redefining the local check as advisory are materially different architecture and product contracts. The corrected brief selects none of them.

A ruling must define how caller identity and role facts enter both local paths, including which source is trusted for an offline optimistic decision. Until then, implementing either local authorization result would invent a contract the specification does not provide.

**Closed by founder-delegated decision, 24 September 2026.** Neither half needs a materially different architecture — both are answerable from facts this codebase already carries, or already carries in an equivalent ambient-session context; the corrected brief simply never named the caller-identity inputs, the identical shape of omission F259 itself was.

1. **The Manager half needs no new capability — `OptimisticCache`'s existing point-access surface already answers it.** `services/api/src/permission/interceptor.ts`'s own `rowScopeSatisfied` already resolves an employee's manager the same direction this needs: `outgoing(tx, workspaceId, employeeId, "managed_by", asOf)`, from the *target* employee toward the manager, not from the caller outward. The client-side equivalent needs only operations `OptimisticCache` already exposes — `edgesFrom(employeeId, "managed_by")` for the target employee's outgoing edge, then `getNode(managerId)`, a point lookup, not enumeration, to read the manager Employee's `user_id` and compare it to `context.userId` (already present on `MutatorContext`). No reverse lookup of the caller's own Employee id is needed at all, because the edge already points away from the target toward the manager. The local query (`conflictCheck.evaluate`) does the identical thing over `localNodes`/`localEdges`, the same relationship `bench-forecast.ts` already has with its own local data.
2. **The Owner half needs one small, precedented context extension, not a new mechanism.** `WorkspaceMembership` is Tier 0, Standard protection (`packages/schema/src/registry/nodes.ts`) and already replicates to every device — `packages/graph/src/sync-client/engine.ts` already special-cases a `WorkspaceMembership` row change to invalidate the protected-value cache, proof the client already receives these rows today, simply unused by any caller-identity logic yet. The server's own equivalent context bundle, `CurrentWorkspaceSession` (`services/api/src/auth/workspace-session.ts`), already carries `roles` alongside `userId`/`workspaceId`/`membershipId` as one unit; `MutatorContext` today carries only the `userId`/`workspaceId` half of that same family of facts. `deriveEffectiveRoles` (`packages/schema/src/policy/effective-roles.ts`) is already a pure, portable function exported from `@vulto/schema`, and its own doc comment already anticipates exactly this — being fed "the stored role set... from a device-unlock grant or a role-refresh response," session-level facts the app layer already holds outside the graph cache, the same place `userId` itself already comes from (`InitPayload`, `packages/graph/src/sync-client/protocol.ts`).

Ruled: `MutatorContext` gains `readonly roles: readonly WorkspaceRole[]`, threaded through `InitPayload` and `packages/graph/src/sync-client/engine.ts` the same way `userId` already is — a plain, non-secret role label, not a credential, so `InitPayload`'s own doc comment ("nothing here carries a token: the session cookie travels with the worker's own fetch") stays true. `overrideAndProceed`'s optimistic handler computes `deriveEffectiveRoles(context.roles).includes("owner")` — the exact function the server already uses, reused, not reimplemented (F237/G08's own precedent again) — and rejects with a new `OptimisticRejection("not-authorized")` (an open string; every prior stage has added a new value the same way, no type change) when the caller is neither that Owner check nor the target employee's manager. `conflictCheck.evaluate`'s signature gains explicit `callerUserId`/`callerRoles` fields on its existing `input` object — `bench-forecast.ts`'s own `getBenchForecast` already establishes the "named fields on `input`" shape this extends, not a new argument convention. Neither `OptimisticCache` nor `cache-data.ts`'s `localNodes`/`localEdges` gains any node-enumeration capability.

Both checks remain purely advisory locally, exactly as F259 already concluded for the write itself: the server re-verifies the manager/Owner gate authoritatively inside `overrideAndProceed` (Do item 6) regardless of what the local check decided, and a stale or wrong local read — a just-reassigned manager, a just-revoked Owner role not yet synced — is rejected there and rolled back via the same undo path already established for a capacity rejection.

This resolves F260 without reopening F255–F259.

**Status: closed.** Stage 16 is unblocked; `codex/stage-16-capacity-conflict-resolution` resumes on the corrected brief — no branch restart.

**Revised by F261, 24 September 2026.** F261 found that neither production `createGraphClient` caller — `apps/roster-web/src/components/shell-bootstrap.tsx`'s shell session or `apps/roster-web/src/app/sync-harness/sync-harness-client.tsx`'s query params — has a `roles` value to supply, and Stage 16 forbids the `apps/` edit that would be needed to add one. The `InitPayload`/`MutatorContext.roles` delivery mechanism ruled above is superseded: both the Manager and Owner checks are now derived entirely from the already-replicated `WorkspaceMembership` node and its `membership_of` edge, using operations `OptimisticCache` already exposes — no `InitPayload` change, no `MutatorContext` field, no `apps/` change, no network call. See F261's own closing ruling for the mechanism actually built.
