### F348 — `text-tertiary` fails WCAG AA contrast in both themes and the literal zero-axe gate cannot hold

**Found while:** the builder's real-browser axe pass for UI-1 (`FDN-131`), 27 September 2026.

`--vt-text-tertiary` fails 4.5:1: light `#a1a1aa` on `#efeff0` is 2.23:1, dark `#71717a` on `#09090a` is 4.11:1. It colours the sidebar micro labels, the Inbox timestamps `VPS-F003` specifies at `small` in `text-tertiary`, and other secondary text across the shell. `VPS-D001` records `color-contrast` as known palette-wide debt, and `a11y-smoke.spec.ts` lists it in `KNOWN_DEBT_RULES`. The UI-1 brief's "zero violations" contradicted both the spec it also cites and the existing baseline (the reviewer's error). On the screenshots the light-theme timestamp is visibly hard to read: this is a real defect, not a tooling quirk.

**Files:** `packages/tokens/src/runtime.css`, `docs/Vulto_Specs/VPS-D001_Design_Foundations.md`, `services/api/browser-tests/a11y-smoke.spec.ts`

**Ruling.** **Open, high; tracked as `FDN-140`.** The token values are a palette-wide visual decision for the founder (darken light tertiary, lighten dark tertiary, or restrict tertiary to non-text); it is not made inside a feature stage. **For UI-1 only:** the new spec inherits the recorded baseline for `color-contrast` alone, with a guard that makes it honest: every other axe rule must report zero, and every `color-contrast` node must carry the `text-text-tertiary` token (so UI-1's own choices, secondary and primary text included, cannot add contrast debt); a violating node without that token fails the test. The full violation arrays stay attached. When `FDN-140` lands the exemption and the guard are deleted.
