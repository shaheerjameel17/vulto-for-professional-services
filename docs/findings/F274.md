### F274 — a row-scoped "own" grant has nothing to check against when the row it authorizes does not yet exist

Raised 24 September 2026 by Codex, who implemented the F270–F273 infrastructure (committed at `3cda786`) and then traced the first ordinary Team Member `saveCell`/zero-entry-marker create before writing it, and stopped a sixth time. TimesheetEntry and TimesheetWeekSubmission both give Team Member `Full (own only)` — the "self-service pattern" [[VPS-A004_Graph_Permission_Layer|VPS-A004]] already names for exactly this shape of record, one an employee submits about themselves. But the pipeline's own documented ordering (`services/api/src/mutations/pipeline.ts`) authorizes every check before `apply()` writes anything — a deliberate, system-wide invariant: a denied mutation must leave no trace but its audit entry. `services/api/src/permission/interceptor.ts`'s `rowScopeSatisfied` resolves "own" by reading the row's stored `employee_id` via `getNode`; on a create, that row does not exist in the database yet, whatever ID it will eventually carry, so `getNode` returns nothing and the scope check fails closed. A completely ordinary Team Member therefore could not save their own first timesheet cell, or submit a genuinely empty week, under the grant the policy table and the spec both say they should have. Every prior node type ever created through this pipeline was created by a role holding unscoped Full (Owner, HR Admin, Finance Admin, or a Manager's unscoped grant); `VPS-A004`'s self-service pattern already names six node types (TimesheetEntry, LeaveRequest, Expense, DevelopmentGoal, TrainingRecord, Invoice) meant to work this way, but none had been built yet, so this gap had never been exercised.

Codex correctly ruled out the two shortcuts that would have "solved" this without actually fixing it: trusting whatever employee ID a create request claims, with nothing checking it against the caller's own identity (this would let anyone create a record and attribute it to someone else); and checking permission after the row is written, rolling back on denial (this breaks the pipeline's own stated invariant that a denied mutation writes nothing, an invariant every one of the previous seventeen stages already relies on). Neither was built.

This was put directly to the founder: no existing mechanism in this codebase had ever authorized the creation of a row under a row-scoped grant, since nothing before TimesheetEntry needed to, and the decision governs every future self-service node type the spec already names. Recommended and adopted: a mutation already knows, from its own already-validated input, who the new row belongs to, before that row exists — the same reasoning `WriteChange.subjectEmployeeId` already relies on for a different gate (Gate 3's reader-set check, which also needs a create's subject before the row is written, proven in this suite's own HRCase test). Rather than overload that field with a second meaning, a distinct field, `WriteChange.declaredSubjectEmployeeId`, carries the mutation's own declared subject specifically for Gate 1's row-scope decision: on a create only, `rowScopeSatisfied` compares the caller's own resolved Employee identity against this declared value, exactly as it already compares against a stored row's `employee_id` once one exists. A Team Member's own `saveCell` or `submitWeek` succeeds because the two values are, definitionally, the same field of the same request; a claim naming someone else's employee ID fails the comparison the same way it always has.

Because that guarantee depends on the row `apply()` actually writes matching what was declared at authorization time — nothing in the type system enforces that the two stay in sync as more self-service node types are added by more contributors over time — the founder asked for the stronger version: after `apply()` runs, the pipeline independently re-reads the row it just wrote and re-derives its subject the same way an update's row-scope check would (the identical resolution F268/F269/F273 already established), and refuses the entire mutation, rolling back everything, if it does not match what was declared and authorized. This does not relax the "authorize before write" invariant — the write is already refused before anything is written whenever the declared subject fails Gate 1 — it adds a second, independent check that catches a future mutation whose declared subject and actual write have drifted apart, which review alone cannot guarantee forever across six more node types built by different hands.

**Closed by founder-delegated decision, 24 September 2026.** `WriteChange` gains `declaredSubjectEmployeeId`, populated only for a create check under a row-scoped grant, sourced from the mutation's own parsed, Zod-validated args — never a raw, unauthenticated claim. `rowScopeSatisfied`'s row-reading resolution (the same one F268/F269/F273 established) is extracted into a shared, reusable resolver, used both for an existing row's scope check and for the pipeline's new post-`apply()` re-check. `services/api/src/mutations/pipeline.ts` gains this independent re-check immediately after `apply()`, before the mutation's outcome is recorded: any mismatch rejects the whole transaction with `subject-mismatch`, never partially committing. `edgeRoleDecision`'s per-endpoint row-scope resolution is extended the identical way, for the endpoint whose node type is being created in the same mutation (`logged_against`'s TimesheetEntry side). `docs/Vulto_Specs/VPS-A004_Graph_Permission_Layer.md`'s self-service pattern paragraph and technical specifications gain this mechanism, since it governs every future self-service node type that pattern already names, not only this one; `docs/Claude_Code_Build_Prompt.md`'s Stage 18 section and `docs/Reviewer_Handoff.md`'s section 19 are corrected to match.

**Status: closed.**
