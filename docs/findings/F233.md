### F233 — `entity.create` gains a server-side calendar write with no optimistic contract or IDs

Raised 22 September 2026 while tracing F227 through the existing Stage 11 mutation. F227 requires both `entity.create` and the founding bootstrap to call `createInitialCalendar` in the same server transaction, adding a WorkingCalendar node and its Entity ownership edge to `entity.create`'s authoritative effect. The existing optimistic `entity.create` in `packages/graph/src/mutators/foundation.ts` creates only the Entity node. Stage 12 Do item 7 names optimistic handlers only for the six newly registered mutations and does not amend `entity.create`. This would leave an offline creation without the Active calendar G02 says exists “from the moment it is created,” and the client would optimistically apply only part of the mutation the server later commits.

The missing part cannot be filled mechanically. The Entity ID is derived portably from `mutationId` today, but there is no separate deterministic derivation for the initial calendar or its ownership edge, and the required helper is described as a server transaction helper. Choosing random server IDs makes the optimistic rows disagree with replication; inventing new deterministic derivations and duplicating template selection on the client changes the shared mutation contract.

**Ruling — closed 22 September 2026.** Yes: `entity.create`'s optimistic handler creates the calendar node and its `Entity`→`WorkingCalendar` ownership edge in the same call, exactly mirroring the server's atomic write (F227) — an offline-created Entity must have its calendar the moment it is created, per G02, with no gap where only the Entity exists locally. Two new functions join `moveEmployeeEdgeId` in `packages/schema/src/mutations/foundation.ts`, reusing its exact shape (a one-to-one bit-flip of the `mutationId`, a distinct constant each, so all three IDs derived from one mutation never collide with each other or with any other mutation's derived IDs): one derives the calendar's `node_id`, one derives the ownership edge's `edge_id`. `createInitialCalendar`'s jurisdiction-template table (F227, AE corrected by F232) is extracted into one small, portable, pure function in `packages/schema` — no I/O, no transaction — that both the server helper and the client's `entityCreate` optimistic mutator call, so the two can never select different templates for the same jurisdiction. Stage 11's server-only founding bootstrap has no client-cache counterpart and is unaffected.

**Status: closed.** Stage 12 is unblocked on this point.
