### F208 — `managed_by` and `scoped_to_entity` have no governing partition, so no reporting-line write can be authorized

Raised 21 September 2026, building Stage 4's `org.moveEmployee`.

**The mechanism.** `VPS-A004` assigns no class to an edge type, so an edge write requires Full on both endpoint node types. Where an endpoint has more than one privacy partition, the edge registry's `governingPartitions` declares which partition governs the edge (F136, founder ruling), and an endpoint with no declaration resolves to `none`, "the conservative default for anything unreviewed".

**The gap.** `managed_by` (Employee to Employee) and `scoped_to_entity` (Employee to Entity) both have an `Employee` endpoint, which has two partitions (`operational`, Tier 0, and `compensation`, Tier 1). Neither edge declares a governing partition. Every role therefore resolves to `none` for every write to them, including the Owner. `assignment_of`, `has_skill` and `holds_certification`, which also connect `Employee`, do declare `operational`.

**Consequence.** `org.moveEmployee` opens and closes `managed_by` edges and can never pass authorization. `VPS-A003` A003-T69 and the Stage 4 done criteria (a cycle-creating move rejected, history half-open and non-overlapping) are unreachable through the pipeline.

**Closed by founder-delegated decision, 21 September 2026.** `governingPartitions: { Employee: "operational" }` was declared on both `managed_by` and `scoped_to_entity`, matching `assignment_of` and `has_skill`, and recorded in `VPS-A002`'s `governingPartitions` table with the rationale that a reporting line and an employing entity are operational HR facts, not compensation, so whoever may write an Employee's operational half may move them. The six tests that were skipped pass. `F125` stays open with the current behavior: a backdated move is refused as `invalid-args`, and `VRS-F037` decides backdating when the org chart is built.
