### F245 — `rateCard.update` cannot express the update Stage 14 requires and has no stale-state contract

Raised 23 September 2026 while tracing the corrected Stage 14 brief (`RST-42`) into the named-mutation registry, before any product code was written.

**The gap.** The authoritative API contract and Stage 14 Do item 1 both name `rateCard.update(rateCardId, lines)`. The same Do item then said `currency` is caller-supplied on both create and update, while the editor specification presents both name and currency as editable fields — but the update contract's own signature accepts neither. Separately, marking the prior card `is_active: false` on supersession carries no caller base version, even though `VPS-A003` A003-T54 requires one for every state transition and the brief said to mirror `calendar.update`'s supersession pattern; and G02 states the prior node is never edited in place, which the `is_active` change appears to contradict without an explicit exception.

**Closed by founder-delegated decision, 23 September 2026.**
1. **`rateCard.update` gains `expectedVersion`, on `calendar.update`'s own precedent (F228).** New signature: `rateCard.update(rateCardId, expectedVersion, lines) -> { newRateCardId }`. `validate()` checks `expectedVersion` against the current card's version first — `stale-state` before anything else — then creates the new version. This is the same version-first ordering F228 already gave `calendar.update`, `holiday.cancel`, `pattern.set` and `pattern.clear`.
2. **`name` and `currency` are never accepted by `update`.** The Stage 14 brief's "caller-supplied on update" claim was a drafting error, not a genuine spec ambiguity — `VRS-F006`'s own API contract never gave `update` a `currency` or `name` parameter, and its "Updating a rate card" user flow only ever describes editing rates, never renaming a card or changing its currency. The new version copies both fields unchanged from the prior card. `currency` remains caller-supplied on `create` only.
3. **The prior card's `is_active: false` transition is a permitted lifecycle-only exception to G02**, not a violation of it. Precedent already exists in this exact codebase: Stage 12's `WorkingPattern` supersession sets the prior pattern's `lifecycle_status: "Superseded"` without touching its substantive fields (`packages/graph/src/mutators/foundation.ts`). G02 protects a card's content — name, currency, lines — from being edited in place; the version-tracking lifecycle flag is the one field every superseding pattern in this codebase is permitted to change on the prior node.

`VRS-F006`'s API contracts, the Rate resolution section and G02 are corrected to state this explicitly, with the version-check requirement recorded as a new G08.

**Status: closed.** Stage 14 is unblocked; `rateCard.update` has one signature, a defined stale-state check, and an explicit statement of which fields carry forward.
