### F294 — workspace-wide `Employee:operational` read widens older derived queries beyond their own, unrelated security contracts

F292's `readScope: "any"` on `Employee:operational`'s `manager`/`team-member` cells correctly gives every workspace member the directory-purpose Employee read `VRS-F013`'s Decisions Recorded requires. But two queries built for earlier features never had their own admission check — they read the caller's *generic* `Employee:operational` decision on the specific Employee in question and treated it as sufficient to disclose something else entirely about that Employee:

- `services/api/src/permission/pitch-queries.ts::listStaffedFor` calls `authorizeRead` on `Employee:operational` for the requested `employeeId`, then, if it returns `read`/`full`, discloses every Pitch that Employee is staffed on, by name, with its client's name. `VRS-F009`'s F264 ruling is explicit and deliberate: "Team Member explicitly `None` at the generic Pitch level, since the spec's own `pitch.listStaffedFor(employeeId)` is its only sanctioned path and is already gated by the working `Employee:operational` row-scope on `employeeId`." Before F292, that row-scope check was itself direct-reports/own-plus-team — an accurate proxy for "may this caller know who this Employee is staffed with." After F292, the same check now succeeds for every workspace member, and the existing PostgreSQL no-existence-leak test (an unrelated Team Member must learn nothing about another Employee's staffed Pitch) fails.
- `services/api/src/permission/conflict-resolution-queries.ts::sweepOvercommitted` filters its candidate Employee list through `filterReadable` — F263's own ruling, closing that finding by reusing the identical call `listEmployees` makes on the identical node type, before computing and returning each Employee's overcommitment. `VRS-F008`'s own spec is explicit: "the sweep is direct-reports-scoped for Manager and own-plus-team for Team Member... callers with no read access never learn another Employee's overcommitment." Both F263's implementation and F292's later, correct widening of that same call's outcome are individually sound; only their composition breaks the sweep's own contract. Two existing PostgreSQL tests (an outsider must see nothing; a scoped Manager/Team Member must see only their own reach) fail.

Checked directly against the code before ruling: both contracts predate F292 by several stages (F263/F264, both Stage 16–17), are explicit in their governing specs, and are entirely unrelated in subject matter to `VRS-F013`'s own Decisions Recorded (which concerns only the directory-purpose visibility of an Employee's own operational fields — name, role, skills, availability — for staffing). Neither spec was revisited or superseded by F292's ruling; F292 never claimed to widen Pitch or capacity-conflict visibility, and doing so was never asked for. This is a mechanism problem, not a product question: two callers borrowed a check that happened to equal their own intended boundary, and F292 correctly changed what that borrowed check now means.

**Closed by direct precedent — no founder consultation needed.** F292 already built the exact machinery this needs: `bestCell`'s `operation` parameter resolves a cell's *literal*, narrow `scope` whenever it is not explicitly called with `"read"` (which is what makes `edgeRoleDecision` and the node-write gate correctly ignore `readScope` today). A new exported primitive in `services/api/src/permission/interceptor.ts` — resolving whether a specific candidate Employee falls within the caller's role-scoped reach for a *named* node type/partition's own policy cell, using that same narrow-tier resolution, without requiring an actual stored row of that other node type to exist — lets each caller authorize against the row it actually needs, not a borrowed generic Employee decision. `listStaffedFor` and `sweepOvercommitted` both call it against `Employee:operational` specifically (their own governing specs, F264/F263, define exactly this scope), restoring their pre-F292 boundary precisely, with zero change to F292's own directory-read fix for the matcher, the plain directory, or Bench Forecast.

The remaining four `pnpm verify:full` failures Codex reported (three audience assertions, one matrix fidelity assertion) are F292's own already-decided ruling propagating correctly, not a new question: `audience-recompute`'s own design (A003-T57, "keeping each person's sync audience equal to what the interceptor permits") derives a device's replicated cache directly from `decideRead`'s outcome, so a Team Member's device correctly now caches the full operational directory locally, exactly as F292 already decided a live server read should return — the same non-confidential directory data (name, role, skills, availability) `VRS-F013`'s own Decisions Recorded reasoning covers, now simply synced rather than fetched per request. Update those four tests to the ruled wide scope; do not revert the widening to make them pass.

**Status: closed.**
