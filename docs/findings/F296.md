### F296 — `certified` has been an unfillable field since Stage 21, and `VRS-F014` inherits the same unqualified claim

Checking `VRS-F014` (Skill Matrix) directly against the finished code before writing its Stage 22 brief, per standing practice, surfaced one finding: `VRS-F013`'s own spec text has claimed since it was written that ad-hoc search "distinguishes self-reported, verified and certified skills from one another," and its `getMatchResults`/`adHocSearch` API contract carries a `certified` boolean on every match. The Stage 21 build honored that contract's shape exactly — `services/api/src/permission/skill-matcher-queries.ts`'s `SkillMatch.certified` field exists — but its value is hardcoded `false` unconditionally, because nothing in the graph can produce anything else: `has_skill`'s edge metadata schema (`employee.attachSkill`'s own fields) has no `certified` flag, `holds_certification` is registered but unwritable (owned by `VRS-F041`, no mutation exists anywhere to create a `Certification` node or attach one to an Employee), and `VRS-F041`'s own spec resolves the derivation as an upgrade to the *same* `verified` flag Skill Matrix and the matcher already read (`grants_skill_id` on `Certification`, "a `has_skill` edge is created or upgraded automatically and marked verified") — not a second, independent `certified` flag anywhere in the currently-planned schema. `VRS-F014`'s own Interface Specification repeats the identical claim one level further downstream: "A small filled dot in the corner marks certified," presented as a marker Skill Matrix can render today, with no caveat that the underlying fact has never existed and cannot exist before `VRS-F041` (row 169 of `VRS-001`'s Feature Register, far down the MVP order) is built and itself defines where a certification-derived attribute is actually stored.

**Closed by direct precedent — traced to `VPS-F002`'s own already-documented forward-dependency pattern (`VRS-F013`'s own Blocks section: "Nothing," with the ad-hoc mode's Cmd+K trigger explicitly deferred to that unbuilt feature), no founder consultation needed.** This is not a defect to fix now — no interim certification mechanism is warranted for a field no later feature has asked to consume early — but a documentation gap: neither spec told a reader that `certified` is currently inert. Both `docs/Vulto_Specs/VRS-F013_Skill-to-Project_Matcher.md` and `docs/Vulto_Specs/VRS-F014_Skill_Matrix.md` gain a one-line Decisions Recorded / Out of Scope note stating plainly that `certified` reads `false` everywhere until `VRS-F041` exists, and that `VRS-F041`'s own eventual design must decide whether a certification-derived attribute is a genuinely separate metadata field on `has_skill` or remains folded into `verified` (in which case Skill Matrix's "distinct marker" requirement itself needs revisiting at that later stage, not this one). Stage 22's own build carries `certified: false` forward unchanged in the local `skillMatrix.get`/`skillMatrix.forSkill` results, honoring the API contract's shape exactly as Stage 21 did.

**Status: closed.**
