### F263 — `sweepOvercommitted` returns every overcommitted employee workspace-wide with no read-authorization filter

Raised 24 September 2026 during the post-completion review of Stage 16's finished implementation, verifying Codex's "Stage 16 is complete... No F263 was needed" report directly against the merged code rather than the report itself.

**The gap.** `services/api/src/permission/conflict-resolution-queries.ts`'s `sweepOvercommitted(tx, principal)` reads every Active `Employee` node and every Active `Assignment` node in the workspace directly via `getNodes`, computes each employee's combined capacity total through the already-reviewed `capacityTotalsFor`, and returns an `OvercommittedEmployee` entry — `employeeId`, `combinedTotal`, `overlapWindow`, `hasRecordedOverride` — for every employee over 100%, unconditionally. Neither this function nor its router wiring (`conflictResolution.sweepOvercommitted` in `services/api/src/router.ts`) narrows that list to what the calling principal may actually see: the router checks only that the requested `workspace_id` matches the caller's own workspace, and the query itself performs no per-row authorization at all.

This is the one workspace-wide node-listing query in the codebase that skips the pattern every comparable query already follows. `services/api/src/permission/employee-queries.ts`'s `listEmployees` — reading the identical `Employee` node type — pipes its rows through `filterReadable(tx, principal, rows, context)` before returning them, specifically, in that file's own words, "so a person who may not read a row does not learn it exists." `services/api/src/permission/ghost-resource-queries.ts`'s `listGhostResources` does the same for `GhostResource`. `sweepOvercommitted` is the only one of the three that omits the call.

`Employee:operational` — the partition this data is drawn from — is not an Owner/HR-admin-only cell: `packages/schema/src/policy/policy-table.ts` grants Manager `Full (direct reports)` and Team Member `Read (own + team)`, both explicitly row-scoped. `VRS-F008`'s own Interface Specification frames the sweep's output as "an admin list" reached from `VPS-F005`'s Workspace Configuration Console, and gates the *override* action explicitly to a Manager or an Owner — but the read query itself carries no such statement in the spec as briefed, and the shipped code grants it to any authenticated workspace member regardless of role or relationship: a Team Member with no reporting relationship at all to the overcommitted employee can call `conflictResolution.sweepOvercommitted` and receive every overcommitted employee in the workspace, including people they hold no `Employee:operational` read grant on whatsoever.

The integration suite does not catch this. `services/api/src/permission/capacity-conflict.integration.test.ts`'s `world()` fixture already builds an `outsider: ["team-member"]` principal specifically for this file — used elsewhere in the same file to prove an unrelated manager is refused at `assignment_of` (F262) — but every `sweepOvercommitted` call in the file, including the one proving G05's Ghost-parity and the read-only guarantee, runs only as `w.principals.owner!`. No test exercises the query as a Manager or a Team Member, so no test could have caught the missing filter.

**Closed — traced directly to the pattern already established by `listEmployees` and `listGhostResources`, no founder consultation needed.** Unlike F262, this is not an architectural fork: the exact mechanism this data needs already exists, is already applied to the same node type by a sibling query in the same permission layer, and needs no new grant, no registry change, and no widening of any policy cell.

**Ruled:** `sweepOvercommitted` gains a `context: InterceptorContext = {}` parameter matching `listEmployees`/`listGhostResources`'s own signature, and filters its `employees` array through `filterReadable(tx, principal, employees, context)` before iterating — the identical call, on the identical node type, `listEmployees` already makes. Every entry in the returned list is now exactly the set of employees the calling principal already holds `Employee:operational` read access to under the existing policy table: unscoped for Owner, HR Admin and Finance Admin; direct-reports-scoped for Manager; own-plus-team for Team Member. No cell in the policy table resolves to `"restricted"` for this partition, so `filterReadable` only ever drops or keeps a row here — it never needs to redact one, and the function's existing per-row shape is unaffected. `capacityTotalsFor`'s own per-employee assignment aggregation is unaffected: it already scopes strictly to the one employee's own assignments and was never the source of the leak. Extend `capacity-conflict.integration.test.ts` with a case calling `sweepOvercommitted` as the fixture's existing `outsider` (team-member, no relationship to the overcommitted employees) and asserting the result omits every employee the outsider cannot read, alongside one asserting a genuine Manager sees only their own direct reports among the overcommitted set.

**Status: closed.** Stage 16 is not reopened on a design question — this is a one-file correction to `sweepOvercommitted` plus new test coverage, on the existing branch, before merge.
