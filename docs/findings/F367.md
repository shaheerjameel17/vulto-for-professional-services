### F367 — `benchForecast.getCost` returns one total per employee for the whole window; the screen needs one figure per bench region

**Found while:** Codex's UI-3 pre-build trace (its UI3-D). Independently verified against `services/api/src/permission/bench-forecast-queries.ts::getBenchForecastCosts` (lines 375–481) before ruling.

**The gap.** `getBenchForecastCosts` accumulates `total` across every date in the caller's supplied `input.window` and returns exactly one `{ amount, currency } | null` per `employeeId` (lines 391–470) — a single figure for the entire queried horizon, not one per bench region. `VRS-F005`'s presentation requires a cost figure inside each qualifying amber region individually, and F36's already-settled rule caps that figure at a 45-day horizon **per region**, not per window: a person with two separate bench gaps, one starting today and one starting in 60 days, needs the near gap costed and the far one correctly showing no figure — a single whole-window total cannot represent that distinction at all, let alone let the client reconstruct it (client-side allocation would mean re-deriving protected compensation math outside the interceptor, which F236 already ruled out for exactly this figure).

**Why this is the same shape as F236/F241, not a new design question.** Both of those findings hit the identical situation — a Tier 1/disclosure-gated figure the spec described in terms the existing or proposed endpoint's shape could not actually produce — and both resolved by extending the dedicated server endpoint's contract to match what the screen genuinely needs, never by pulling protected computation onto the device. This is a third instance of the same pattern, scoped to `getCost` specifically.

**Ruling. Closed 29 September 2026, mechanical extension of an already-authorized endpoint, no founder ruling needed.** `benchForecast.getCost`'s contract is extended to accept the set of bench regions to price rather than a single window — `{ employeeId, fromDate, toDate }[]` — and to return one costed figure per requested region (`null` for a region whose `fromDate` falls beyond the F36 45-day horizon, unchanged from today's per-employee suppression rule). The interceptor gate, the `readProtected` call, and the per-day `compensationCostForBenchDay` math are unchanged; only the grouping of dates into one total per region, instead of one total per employee, changes. This is additive to an existing, already-gated endpoint — it does not touch who may call it or what compensation data it may see, so it is not the kind of permission/policy change the brief reserves for a founder ruling. The call remains a single batched, non-blocking `cache: "no-store"` fetch issued after the local render, unchanged from F236's shape.

**Correction, 29 September 2026.** This finding's ruling paragraph claimed the new per-region 45-day cutoff was "unchanged from today's per-employee suppression rule" — implying `getBenchForecastCosts` already enforced F36's 45-day horizon before this change. Codex's implementation trace found no such check in the pre-existing function (verified directly: the prior `input.window`-based version, `git show dc4f729^:services/api/src/permission/bench-forecast-queries.ts`, contains no date-horizon guard anywhere in `getBenchForecastCosts` — every requested window was priced in full regardless of how far out it started). There was no pre-existing suppression rule for this endpoint to leave unchanged; F36's 45-day cutoff had simply never been enforced here. Codex's own addition of `if (region.fromDate >= addIsoDays(today, 45)) { result(null); continue; }` per region (now in the shipped code) is not a preservation of an existing rule but the first enforcement of it in this function — and it is authorized here, explicitly, as the correct and required completion of this finding's own contract, not a separate micro-decision needing its own ruling. The rest of this finding's ruling — the per-region grouping, the unchanged interceptor gate and per-day math, the unchanged batched fetch shape — stands.

**Status: closed** (mechanical extension, folded into the corrected UI-3 brief).
