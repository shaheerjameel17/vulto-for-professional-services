### F267 — `logged_against` needs a governing partition for Pitch, the same mistake `staffed_on` made before F265

Raised 24 September 2026, checking `VRS-F010` (Timesheet Speed-Run) directly against the code before writing its brief. `VRS-F010` registers `logged_against` (`TimesheetEntry→Assignment`, `TimesheetEntry→Pitch`) in `packages/schema/src/registry/edges.ts` with no `governingPartitions` declared on either pair. `Assignment` is unsplit (`fixedProtection("Standard", 0)`), so it needs none — but `Pitch` is split into `identifying`/`commercial`, exactly as it was when `staffed_on`'s identical omission produced F265: `edgeRoleDecision` applies F136's conservative default to a split endpoint with no declared partition, refusing every write that touches it regardless of role. A Pitch-categorized `TimesheetEntry` — `timesheet.saveCell` with `time_category: "Pitch"`, writing `logged_against` to the staffed Pitch — would fail for everyone, Owner included, exactly as staffing did before F265's fix.

This was caught reading the registry directly before any Stage 18 code was written, not by a failing test during implementation the way F265 was. Same root cause, same fix, one edge earlier in the process this time.

**Closed, traced directly to F265's own precedent — no founder consultation needed.** `logged_against` declares `governingPartitions: { Pitch: "identifying" }`. `Assignment` needs no entry. No new mechanism; the declaration is the entire fix, same as F265.

**Status: closed.**
