### F219 — the null-active-organization fallback has no permitted membership read

Raised 22 September 2026 during the fourth Stage 9 attempt (`stage-9-shell-bootstrap-v3`, FDN-117), after implementing the ruled bootstrap and exercising it in a real browser. Stage 9 point 3 says to add Better Auth's `organizationClient()` and, when a valid session has `activeOrganizationId: null`, resolve exactly one active membership on the client. The client plugin makes `organization.list()` callable, but `services/api/src/auth/http.ts` explicitly returns 404 for **every** `/api/auth/organization/*` path. Its comment explains why: the plugin's public routes are kept closed so that organization mutation and invitation commands have no second write path beside FDN-85 and FDN-86. The route guard covers read calls too.

**Proof.** The browser test `a null active organization resolves a sole confirmed membership` creates and confirms one workspace, clears only `session.activeOrganizationId`, and loads the shell with a valid session. Its trace shows `GET /api/auth/get-session` succeeded, then `GET /api/auth/organization/list` returned 404. No `list-members` request follows; the shell displays the unresolved holding state for a person who has exactly one active membership. A separate test with two memberships correctly holds. This is a failure of the required single-membership case, not an offline condition or a fixture.

**Ruling — closed 22 September 2026.** Checked directly: `services/api/src/trpc.ts`'s `createContext` reads `session.activeOrganizationId` and returns `principal: null` when it's absent — meaning every `protectedProcedure`, `principal.current` included, is unreachable without an already-resolved workspace. There is no existing endpoint anywhere in the API that answers "which workspaces is this session an active member of" without already knowing the answer. Opening Better Auth's `organization/list` would not by itself be safe either: `member.status` is `'pending' | 'active' | 'revoked'` directly on the row Better Auth's own plugin reads, so an unfiltered list would surface pending and revoked memberships the shell must never silently pick among (F217).

No `/api/auth/organization/*` route opens — FDN-85/FDN-86's boundary is correct as built and is not reopened for reads either. Instead, one new narrow route: `POST /workspace/list-active-memberships` in `services/api/src/auth/http.ts`, requiring only a valid Better Auth session (no workspace header, no workspace scope needed — the same shape as the existing `/devices/retire`, whose own comment already establishes this pattern: "takes no workspaceId, because it has no workspace scope"). It runs the exact predicate already used twice in this file — `requireCurrentWorkspaceSession`'s join conditions and `confirmWorkspaceAdmission`'s post-confirmation active-membership count: `member.userId = session.user.id`, `member.status = "active"`, `member.projectionState = "confirmed"`, `organization.status = "active"` — and returns `{ workspaceId, workspaceName }` for each match, nothing else. A person with no active confirmed membership (never admitted, or only pending) gets an empty array, which is the same "none" branch point 3 already defines as unresolved — not a new case.

Stage 9 point 3 is corrected: drop `organizationClient()` from `auth-client.ts` entirely (there is nothing left for it to legitimately call), and `soleActiveWorkspace` (the preliminary code's own name for this resolver) calls the new route instead of `organization.list()`/`organization.listMembers()`. Every other piece of the preliminary work on `stage-9-shell-bootstrap-v3` — the F218 `hasServerAnswer` split, the offline cached-workspace fallback, the graph client construction, the refusal-signal wiring in `Shell.tsx`/`layout.tsx`, and the `packages/graph/src/sync-client/*` changes — is correct and untouched by this finding; none of it should be discarded. `VPS-F001`'s "Workspace admission control" section is corrected with one added bullet recording this boundary and the one exception, so a future reader does not have to rediscover it from the route guard's code comment.

**Status: closed.** Continue Stage 9 on the same branch, same session — this is a surgical fix to already-good work, not a restart.
