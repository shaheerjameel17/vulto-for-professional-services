### F312 — the anomaly flag is Tier 2, so its rule carries no flag field

**Found while:** writing the Stage 25 brief, 26 September 2026, by reading `TimesheetAnomalyFlag`'s registry entry before naming its rule's message fields.

`TimesheetAnomalyFlag` is registered fixed `Manager-restricted` Tier 2, so a generic rule cannot read any field of it, and the Tier 0 proof the Stage 25 brief first named (`validateSearchableNodeTypes`'s last block) is inline, accepts only a fixed Tier 0 type or the Employee's operational partition, and is not reusable as written. A rule's message that names the employee takes the name from the Employee's Tier 0 partition, not from the flag.

**Files:** `packages/schema/src/registry/nodes.ts`, `packages/schema/src/search.ts`, `docs/Vulto_Specs/VPS-F003_Notification_and_Alert_Center.md`

**Ruling.** **Closed 26 September 2026 by ruling.** A rule's `messageFields` are `{ from: "subject" | "source", field }`: a `subject` field must be in the Employee's operational shape, a `source` field is allowed only when the source type is fixed Tier 0, and a Tier 1 or Tier 2 source such as the flag contributes its existence only. The engine reads a watched node's universal row and its `triggered_by` edge, never a protected field. The Tier 0 proof is factored out of `validateSearchableNodeTypes` into one exported helper used by both the search and the notification registries.
