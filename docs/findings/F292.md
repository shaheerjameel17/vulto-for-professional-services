### F292 — the matcher's workspace-wide candidate read conflicts with `Employee:operational`'s current policy row

`VRS-F013`'s Decisions Recorded is explicit and deliberate: "employee operational data — name, role, skills, availability — is readable by every workspace member." Three reasons are given, the first of which is that `VRS-F005` (the Bench Forecast) "already renders every active employee as a row to every viewer." Stage 21 item 7's own build-prompt text, written by this reviewer before Codex reached implementation, took that as settled and specified `matchCandidates` reading candidates via `filterReadable`, "workspace-readable operational data per the spec's own Decisions Recorded."

Checked directly against the executable policy table before ruling: `Employee:operational` (`packages/schema/src/policy/policy-table.ts`) still reads

```
manager: cell("full", "direct-reports", "Full (direct reports)"),
"team-member": cell("read", "own-plus-team", "Read (own + team)"),
```

`PolicyCell` carries exactly one `(outcome, scope)` pair per role/partition — `resolvePolicyCell`/`bestCell` resolve a single literal cell, nothing composes two. `bestCell`'s own row-scope check (`services/api/src/permission/interceptor.ts`) is unconditional: `const outcome = (await rowScopeSatisfied(cell.scope, row)) ? cell.outcome : "none"` — a row outside scope resolves to `none`, not `restricted`. `filterReadable` drops a `none` row entirely; the reader never learns the row exists. So a Manager calling the matcher would never see a qualified Employee outside their own direct reports, and a Team Member never one outside their own team — the matcher would silently return incomplete results, and could create a false `SkillGap` for a requirement real people already satisfy.

Checked whether the spec's own precedent (`VRS-F005`) actually holds, since a working precedent would have settled the mechanism question by example: it does not. `services/api/src/permission/bench-forecast-queries.ts::authorizedCohort` builds its cohort by calling `listEmployees` (`services/api/src/permission/employee-queries.ts`), which itself calls `filterReadable` under the caller's own ordinary principal — the identical mechanism, the identical row-scoped cell, the identical drop. A real Manager or Team Member calling Bench Forecast today would already fail to see colleagues outside their own scope; this stage's own reviewer-authored justification for the underlying product decision rests on a precedent that, read directly, does not exist yet. This is a second, previously undiscovered instance of the same gap, not a working example of the fix.

**Genuine architectural fork.** The *product* question is already decided by the spec — this reviewer does not revisit it. What remains open is the *mechanism*: how to grant a wider read ceiling than the write ceiling within one policy cell, when nothing in the permission engine does that today. Two concrete options were reasoned through:

1. **A general read/write split on `PolicyCell`.** Add an optional `readScope`, defaulting to the cell's own `scope`; `bestCell` gains an `operation` parameter so only the read path (`decideRead`) ever consults it, leaving `edgeRoleDecision` and the node-write gate (both write-adjacent) byte-for-byte unchanged. `Employee:operational`'s `manager` and `team-member` cells both gain `readScope: "any"`. This is more surface (`PolicyCell`'s type, `bestCell`'s signature, matrix-coverage and policy-table fidelity tests) but fixes the matcher, Bench Forecast and the plain employee directory in one mechanism, correctly matching what the spec's Decisions Recorded actually asked for.
2. **A matcher-only dedicated read carve-out.** Leave the policy row untouched; give `matchCandidates` its own narrow authorization path, always granting Read to any member principal for this one purpose. Smaller and contained, but leaves Bench Forecast's and the directory's identical gap in place, now known and undocumented — a Manager would still not see their own colleagues on the Bench Forecast page even after this stage ships.

Put directly to the founder via `AskUserQuestion`, since neither option is traceable to an existing precedent and the two carry materially different product consequences beyond this stage. **Decided by the founder: option 1**, the general mechanism — it correctly closes the gap everywhere the spec's own reasoning said it should be closed, not only where this stage happens to need it.

`PolicyCell` gains an optional `readScope?: PolicyScope`, consulted by `bestCell` only when `operation === "read"` and only after the cell's own narrow `scope` check has already failed — and even then ceilinged at outcome `"read"`, never promoted to `"full"`, and never bypassing `Restricted`/subject-exclusion or any other existing check. `bestCell` gains an `operation: "read" | "write"` parameter defaulting to `"write"`; only `decideRead`'s own call site passes `"read"`, so `filterReadable` and every one of its callers (the directory, Bench Forecast, the matcher) benefit uniformly with zero change to write authorization. `Employee:operational`'s `manager` and `team-member` cells both gain `readScope: "any"` — manager's literal `Full (direct reports)` write ceiling is untouched; team-member's outcome was already `read`, so the split costs it nothing beyond the wider scope.

**Status: closed.**
