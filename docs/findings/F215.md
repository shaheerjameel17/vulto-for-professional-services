### F215 — the identity link had three consumers that could not use it

Raised 22 September 2026, building RST-33. The Stage 8 brief expected `resolveEmployeeForUser` to be the only change (both of its callers already treat `null` as "cannot tell"). Building it showed the link had more consumers than that, and none of them could act on it.

1. **Row scopes.** `rowScopeSatisfied(scope)` in the interceptor was a stub for the one seam its own comment said "changes when the link lands": it was true only for `any`. So a Manager's `direct-reports` grant, a team member's `own-plus-team` read and `own` compensation read all resolved to no access, and the derived Manager role widened nothing. Implemented for an Employee row, from the real link and the real `managed_by` edges: `own` (the row is the caller's Employee), `direct-reports` (the caller is the row's active manager) and `own-plus-team` (`own`, or the row shares the caller's active manager). Every other scope, and every row that is not an Employee, is still unsatisfied, because they need a subject path this does not follow. Edge writes still name no row, so a Manager cannot move people; whoever may write an Employee's operational half at role level (Owner, HR Admin) may.
2. **Reader-set resolution.** `resolveReaderSet` returned `unresolvable` for any row-dependent grant, regardless of the link. Employee compensation (Tier 1) has a team-member `own` read, so Gate 3 ("a protected record must have someone who can read it") could never pass and no compensation could be written by anyone. `own` is now resolved from the subject: the reader it adds is the person the record concerns, if they hold the role and have a login. A derived Manager, and every other row-dependent scope, remain unresolvable.
3. **Subject exclusion on reads.** A004-T16 requires the exclusion "at the interceptor, in the materialized sync audience and in `protected.read`", but it was implemented only as a filter inside the write gate's reader-set. It is now applied in `decideRead`, the one decision all three consume, returning `restricted` with the label from `VPS-D004` (*"Restricted — this record concerns you."*).

**Decisions inside those, for the reviewer to confirm.** (a) A reader with no Employee record is treated as not being the subject, because "the subject" is an Employee record and a login with none is not one; the alternative (deny anyone whose link cannot be determined) would hide every HR case from an Owner who never created their own Employee record. (b) A case with no recorded subject is not excluded for anyone (the write gate already refuses a case with no resolvable subject, so this is a data-inconsistency corner). (c) `own-plus-team` means "shares my active manager"; the spec says "own plus team" without defining team.

**Cost.** Each read decision for an Employee row now resolves the caller's Employee and, for the manager-based scopes, one or two edge lookups. Acceptable at 150 rows a directory; a candidate for a per-request cache if it is not.
