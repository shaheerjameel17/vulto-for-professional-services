### F224 — Stage 11's shared Tier 0 registry needs an offline Entity transfer path

Raised 22 September 2026 while implementing Stage 11 on `codex/stage-11-multi-entity-jurisdiction`, after F223 was ruled. The Stage 11 brief calls this a server-side-only stage and says `entity.resolveForEmployee` has one implementation in `services/api`. Its G06 check says nothing else in the stage may traverse `scoped_to_entity` directly. That is enough for server reads: the new `services/api/src/graph/entity-resolution.ts` can own the traversal, and the server mutations can call it.

The mutation names live in `packages/schema/src/mutations/foundation.ts`'s shared `MUTATIONS` registry, not a server-only registry. `packages/graph/src/mutators/foundation.ts` declares `OPTIMISTIC_MUTATORS: Readonly<Record<MutationName, OptimisticMutator>>`; after adding `entity.create`, `entity.update`, `entity.deactivate`, and `employee.setEntity`, `pnpm verify` reaches TypeScript and fails because all four client handlers are missing (TS2739). This is a required boundary, not a cosmetic type error: `VPS-A003`'s Decision says Tier 0 mutations apply to the local cache immediately, and A003-T63 requires Tier 0 writes to queue offline. A placeholder handler returning no cache changes would compile but break the promised optimistic behavior.

`employee.setEntity` makes the unresolved choice concrete. Its optimistic half would have to close the existing open `scoped_to_entity` edge and insert the new one in the device cache. The current edge ID is not an input to the mutation and cannot be inferred from `employeeId`; the client must inspect cached edges to find it. Doing that in a new `packages/graph` handler introduces a direct `scoped_to_entity` traversal outside `services/api`'s sole resolver, contrary to Stage 11 point 3 and its report check. Calling the server resolver is impossible while offline. Moving the resolution logic into a shared package so server and device use one implementation, or changing the offline contract, would alter the brief and needs a ruling.

**Ruling — closed 22 September 2026.** G06 protects one thing: *temporal resolution* — computing which Entity governed an employee as of a given moment, the `asOf`-parameterized question `entity.resolveForEmployee` answers and that contract generation, leave and payroll must never re-derive themselves. It does not extend to the mechanical, non-temporal question a single-active-edge-with-history mutation must answer about its own state before it can act: *which edge is currently open*. `services/api/src/graph/entity-resolution.ts`'s own `resolveEntityAssignment(tx, ws, employeeId, at: string | "open")` already keeps these two questions distinct inside the server — `at: "open"` never interprets an `asOf` date, it returns the one edge G02's single-active-edge-with-history invariant guarantees is unique. The client optimistic handlers only ever need that same `"open"` question, never the `asOf` one, so G06 is not engaged.

That pattern is already built and already shipping: `org.moveEmployee`'s existing optimistic mutator (`packages/graph/src/mutators/foundation.ts`) finds the employee's currently-open `managed_by` edge by querying `c.cache.edgesFrom(employeeId, "managed_by")` for `effectiveTo === null` directly in the device cache, with no resolver of its own and no `VRS-F003`-style G06 restriction on `managed_by` — because, exactly as here, a bare "find the open edge" query has one correct answer by the same single-active-edge-with-history invariant and needs no `asOf` interpretation. `employee.setEntity`'s optimistic handler follows the identical shape for `scoped_to_entity`: find the one edge with `effectiveTo === null`, close it at `effective_from`, and open a new one to the destination Entity, deriving the new edge's id from `moveEmployeeEdgeId(mutationId)` — already the shared, portable, deterministic derivation `services/api/src/mutations/entity.ts`'s own server implementation uses for the same edge, so client and server independently compute the same id and replication finds nothing to reconcile. That `scoped_to_entity` is already client-cached and directly writable is not new: `employeeCreate`'s existing optimistic mutator already writes a `scoped_to_entity` edge into the device cache when an Employee is created.

`entity.create` and `entity.update` need nothing beyond ordinary node-write optimistic mutators, the same shape `employeeCreate`/`employeeUpdate` already use for a plain node with no lifecycle business rules of its own.

`entity.deactivate` is different, and is not given `employeeTransitionStatus`'s full client-side replication treatment. `employeeTransitionStatus`'s optimistic mutator can safely replicate its business rules offline because they are single-node rules, decidable from the one cached Employee record. G04 and G05 are not: they are workspace-wide aggregate counts (every other Entity's `lifecycle_status`, every Employee's current scope) that a single device's partial, possibly-stale cache cannot be trusted to answer correctly, and a wrong offline answer would let a deactivation appear to succeed on a device that is about to be told otherwise. `entity.deactivate`'s optimistic handler therefore checks only `expected_version` (`stale-state` on a mismatch, exactly `employeeTransitionStatus`'s own first check) and applies the `lifecycle_status: "Dissolved"` write optimistically; it does not re-check G04 or G05 client-side. If the server's authoritative check refuses a deactivation the client allowed through, that is exactly what `packages/graph/src/sync-client/outbox.ts`'s existing rejection path is for — `reject(mutationId, reason)` marks the entry `"rejected"` and its captured `undo: UndoEntry[]` reverses the optimistic write, the same general safety net every other optimistic mutation already relies on for a server-side refusal it can't predict offline. No new mechanism is introduced.

`VRS-F003`'s G06 is corrected to state the distinction explicitly, and its Decisions Recorded section gains this ruling.

**Status: closed.** `packages/graph/src/mutators/foundation.ts` gains four optimistic mutators: ordinary node writes for `entity.create`/`entity.update`; a `moveEmployee`-shaped close-and-reopen of the open `scoped_to_entity` edge for `employee.setEntity`, reusing `moveEmployeeEdgeId`; and a version-check-only write for `entity.deactivate`, with G04/G05 left to the server and the outbox's rejection path. Stage 11 is unblocked.
