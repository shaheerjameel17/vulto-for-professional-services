### F370 — `triggered_by` has no generic write path for any role by design; the browser fixture should seed it the same way production does, directly through the store, not through `graph.createEdge`

**Found while:** Codex's UI-3 implementation trace (`docs/stage-reports/STAGE-UI-3_Bench_Forecast_Implementation.md`, Section 8), which found that the real-browser test's `graph.createEdge` call for the `BurnoutAlert`'s `triggered_by` edge is rejected with `reason: "role"` even for the Owner, and asked the reviewer to rule whether a narrowly test-only edge-seeding helper is authorized or to name the intended production path. Independently verified against `packages/schema/src/registry/edges.ts` (the `triggered_by` group, lines ~430–441), `services/api/src/permission/interceptor.ts::edgeRoleDecision` (lines 862–921), `packages/schema/src/registry/nodes.ts` (Employee's protection partitions, line ~95), and the two production callers that actually create this edge: `services/api/src/mutations/revenue-gap-alert.ts` and `services/api/src/mutations/timesheet-anomaly.ts`, plus the existing seeding pattern in `services/api/src/permission/bench-forecast.integration.test.ts` and the two test-support barrels (`services/api/src/permission/test-support.ts`, `services/api/src/test/sync-browser-support.ts`).

**Why the rejection is structural, not row-scope, and applies to every role including Owner.** `edgeRoleDecision` requires a declared governing partition for any endpoint node type with more than one protection partition (F136/FDN-92): `Employee` is registered with several (`operational`, `compensation`, and others), so an edge touching an `Employee` endpoint falls into the `partitions.length > 1` branch, which returns `"role"` immediately whenever `registration.governingPartitions[nodeType]` is `undefined` — before any row-scope or participant-grant check runs. `triggered_by`'s registration (`edges.ts`) declares no `governingPartitions` entry at all. This means the generic `graph.createEdge` mutation cannot create a `triggered_by` edge for *any* principal, in any role, on any row — the Owner's rejection Codex hit is not a scope miscalculation or a bug; it is the same universal denial every role gets, because the registry entry is genuinely incomplete for the generic path. `assertRegisteredRelationship` alone (present) is not enough; the governing-partition lookup is a second, independent requirement.

**Why that incompleteness is not an oversight.** `triggered_by` connects a Tier 2 signal node (`BurnoutAlert`, `FlightRiskSignal`, `RevenueGapAlert`, `TimesheetAnomalyFlag`) to the `Employee` it concerns. Tracing where these edges are actually created in production: `revenue-gap-alert.ts`'s `evaluateInTransaction` and `timesheet-anomaly.ts`'s equivalent both write the node and its `triggered_by` edge with `insertEdge`/`insertNode` called directly against the graph store, under a `SystemPrincipal` (`principalFor`/`ensureSystemActor`) — never through `authorizeWrite`/`graph.createEdge` at all. These are scheduled/reactive evaluators, not anything a user role invokes. There is no production caller anywhere in the codebase that creates a `triggered_by` edge through the generic, role-gated mutation path. An empty `governingPartitions` entry here is therefore not a registration gap to fill; it is the registry correctly reflecting that no role should ever be able to create or retarget one of these edges through the generic endpoint. Declaring `Employee: "operational"` to make Codex's browser test pass would open a real, new write path — any principal with `operational`-partition write access to an Employee could then attach or detach a Tier 2 alert's subject via `graph.createEdge` — a genuine product/security change to who may assert "this alert is about this employee," not a fixture fix. Codex was correct to stop rather than add it.

**What the existing API integration test already establishes as the seeding pattern.** `bench-forecast.integration.test.ts` seeds exactly this edge (`insertNode(tx, nodeRecord("BurnoutAlert", ...))` then `insertEdge(tx, w.workspaceId, edgeRecord("triggered_by", burnout, report))`) by calling the graph store directly inside a test transaction, using `edgeRecord`/`insertNode` from `permission/test-support.ts` — the same file that already supplies `addNode` (itself a direct `insertNode` call) to the sync-browser suite via `services/api/src/test/sync-browser-support.ts`. That barrel re-exports `addNode` and `writeProtected` for exactly this reason: the browser suite, like the integration suite, is allowed to seed graph state directly as a fixture, bypassing the interceptor for setup the same way `addNode` already does for nodes and `writeProtected` already does for protected fields. `insertEdge` and `edgeRecord` are simply not among the barrel's re-exports yet — an omission of the same shape as F366's, not a deliberate boundary.

**Ruling. Closed 29 September 2026, additive test-support export, no founder ruling needed; no production path exists or should be added.** There is no "intended production path" for a user-facing `triggered_by` write to authorize, because none exists: these edges are exclusively system-created by the two reactive evaluators, which is unchanged by this stage. Add `insertEdge` (from `../graph/store.js`) and `edgeRecord` (from `../permission/test-support.js`) to `services/api/src/test/sync-browser-support.ts`'s re-exports — two lines, mirroring the file's existing `addNode`/`writeProtected` pattern exactly, touching no production code and no policy table. The sync-browser fixture then seeds the `BurnoutAlert`/`FlightRiskSignal` nodes and their `triggered_by` edges the same way the API integration test already does: a direct `db.transaction` with `insertNode`/`insertEdge`/`writeProtected`, never `client.mutate("graph.createEdge", ...)`. This is not a bypass of the permission boundary — it is the same test-fixture-seeds-state-directly convention this suite already uses for nodes and protected fields, extended to cover edges, matching what the API integration suite already does for this exact edge type. No change to `edges.ts`'s `governingPartitions`, no change to `edgeRoleDecision`, no client-side or production workaround of any kind.

**Status: closed** (additive test-support export, folded into the corrected UI-3 brief/implementation).
