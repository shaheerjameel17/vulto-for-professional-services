### F289 — `insertEdge`'s edge-metadata protection check is node-type-level, not partition-level

Raised 25 September 2026. Codex resumed Stage 21 implementation after F288's ruling and, before writing `employee.attachSkill`, traced its own write path into the graph store. `has_skill`'s replace-on-duplicate semantics (G03) require `proficiency_level` and the server-derived `verified`/`verified_by`/`verified_at` to persist in the edge's `metadata`. `services/api/src/graph/store.ts::insertEdge` sets `protectedEndpoint = hasProtectedPartition(from.nodeType) || hasProtectedPartition(to.nodeType)` and replaces `metadata` with `{}` whenever true; `hasProtectedPartition` returns true whenever a node type has *any* partition with a non-zero tier anywhere in its schema (`partitionTiers(nodeType).some((tier) => tier !== 0)`) — a node-type-level fact, blind to which partition a given edge actually concerns. Employee is tier-split (`operational`, Tier 0; `compensation`, Tier 1, Finance-restricted, per `packages/schema/src/registry/nodes.ts`), so every edge touching Employee has its metadata unconditionally discarded, `has_skill` included, even though `has_skill`'s own registration already declares `governingPartitions: { Employee: "operational" }` — decided at F136/FDN-92, specifically because "a skill holding is operational HR data; requiring compensation-level (finance) permission to record one is wrong for the product." `insertEdge` already calls `assertRegisteredRelationship` and receives that exact registration back, then discards it unused.

This bug has never surfaced before because no edge touching Employee has ever needed non-empty metadata: `pattern_for`'s data lives on the `WorkingPattern` node itself, not the edge; Ghost Resource's existing `has_skill` writer supplies no metadata at all. `managed_by`, `assignment_of`, `staffed_on`, `holds_certification` and several other Employee-touching edges already declare `governingPartitions: { Employee: "operational" }` for authorization purposes and would be silently affected by the same defect the moment any of them needed metadata — `store.integration.test.ts`'s own `"stores no edge metadata when an endpoint has a protected partition"` test asserts on `managed_by` and currently pins the buggy behavior.

`edgeRoleDecision` (`services/api/src/permission/interceptor.ts`) already solves the identical partition-precision problem for edge write *authorization*: for a tier-split endpoint, it reads `getProtectionPartitions(nodeType)`, looks up the edge registration's own `governingPartitions[nodeType]`, and fails closed — requires unscoped Full — when no partition is declared. `resolveRegisteredProtectionTier` (`packages/schema/src/registry/protection.ts`) already resolves a named partition's tier from the registry. Both are already the established source of truth for exactly this question; `insertEdge` was simply never updated to consult them.

**Closed by direct precedent, 25 September 2026.** No founder consultation needed — the classification data and the fail-closed convention both already exist for exactly this purpose, one edge-write code path away from being reused a second time. `insertEdge`'s protection check corrected to resolve each endpoint's governing partition via `getProtectionPartitions` plus the already-fetched registration's `governingPartitions[nodeType]`, failing closed (protected) when a tier-split endpoint declares none — mirroring `edgeRoleDecision`'s own `declared === undefined` branch exactly — and stripping metadata only when `resolveRegisteredProtectionTier` resolves a non-zero tier. A new generic Tier-0 store primitive, `graph.updateEdgeMetadata`, applies the identical corrected check for `has_skill`'s in-place replace-on-duplicate write, extending the existing `graph.createEdge`/`graph.closeEdge` generic family (`packages/schema/src/mutations/foundation.ts`) rather than bespoke per-mutation SQL. `store.integration.test.ts`'s existing `managed_by` test is corrected to assert metadata is *preserved* (its governing partition, `Employee:operational`, is Tier 0 — this was always the intended outcome), and a new test proves metadata is still genuinely stripped when a tier-split endpoint's governing partition is undeclared or resolves non-zero, so the protection itself is proven, not merely relaxed.

**Status: closed.**
