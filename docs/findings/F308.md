### F308 — the spec's rules cannot see an event, only changed row ids

**Found while:** briefing Stage 25 (`VPS-F003`), 26 September 2026, by checking the spec against the code before writing the brief.

The spec's rules "watch the same write event the source feature's logic already reacts to", but the mutation pipeline exposes no such event: `Applied` carries only `changedRowIds` (every node and edge id touched), with no created-versus-updated distinction and no before value, and `plan.afterCommit` is per mutation. "Created or escalated" (RevenueGapAlert) therefore cannot be detected from the signal, a rule that fires on every touch would duplicate notifications on every re-evaluation, and a rule that ran inside the source transaction would make a notification failure abort the source feature, contradicting G03 ("no source feature is corrected, each watched independently").

**Files:** `services/api/src/mutations/pipeline.ts`, `services/api/src/mutations/types.ts`, `packages/schema/src/revenue-gap-alert.ts`, `docs/Vulto_Specs/VPS-F003_Notification_and_Alert_Center.md`

**Ruling.** **Closed 26 September 2026 by ruling.** (The hook site was refined by F316: a write-log scope around `applyMutation` and every tRPC procedure, not the pipeline's `changedRowIds`.) One generic hook in the pipeline, after the mutation transaction commits and after the mutation's own `afterCommit`: it hands `applied.changedRowIds` to the rule engine, which runs in its own transaction as a new system principal and never fails the source (a delivery error is logged and swallowed; nothing the source wrote is undone). Idempotency replaces event detection: the Notification schema gains two Tier 0 string fields, `rule_id` and `dedupe_key`, and the engine creates a notification only when none with that `dedupe_key` exists for the recipient, under a transaction-scoped advisory lock on the key so two concurrent runs cannot both insert. A rule's discriminator is part of its key (RevenueGapAlert uses its `severity`, so Low then Medium then High each notify once, and a re-evaluation at the same severity never repeats). At-least-once delivery after a crash between commit and delivery is not solved here: a reconciliation sweep belongs to the jobs service (FDN-57) and is safe to add because every delivery is idempotent. The spec's schema block is corrected to carry the two fields.
