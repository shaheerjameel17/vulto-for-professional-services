### F353 — "Reports to" has no field on `employee.update`'s patch and must go through `org.moveEmployee`

**Found while:** briefing UI-2, 27 September 2026.

`OverviewTab.tsx`'s `managerName` field commits like every other field, through `EditableField`'s generic `onCommit`. But `packages/schema/src/employee.ts`'s `employeeUpdatePatchSchema` is `.strict()` and carries no manager or `managed_by` field — the manager relationship is an edge, not an Employee property. The real mutation that changes it is `org.moveEmployee`, which edits the `managed_by` edge directly and rejects a change that would create a cycle (`wouldCreateCycle`). Wiring "Reports to" to `employee.update` would either be silently dropped by the strict schema's rejection of an unknown key, or — worse — invite adding a field to the patch schema that duplicates what the edge already owns, which `VRS-F002`'s own Feature Acceptance Criteria treats as a distinct operation from an ordinary field edit (an HR Admin setting `managed_by` is what grants Manager permissions per `VPS-A004`, not a side effect of a generic patch).

**Files:** `apps/roster-web/src/components/profile/OverviewTab.tsx`, `packages/schema/src/employee.ts`, the `org.moveEmployee` mutation (`services/api/src/mutations`)

**Ruling.** **Closed 27 September 2026 by ruling.** "Reports to" is committed through `org.moveEmployee`, called separately from the rest of the Overview tab's `employee.update` patch calls; every other field on the tab (email, phone, job title, department, employment type, seniority, dates, timezone, location, notes, contracted hours, `billing_rate_default`, `billability_target_override`) goes through `employee.update`'s patch, matching `operationalShape` field-for-field. A cycle rejection from `org.moveEmployee` is shown in place on the field, the same way any other mutation refusal is shown (F349's plain-sentence mapping extended to `org.moveEmployee`'s refusal reasons, not a new ad hoc message). `employeeUpdatePatchSchema` is not extended with a manager field.
