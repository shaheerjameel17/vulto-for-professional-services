### F237 — the deferred working-day index, inherited from F226/F231, is resolved without building one

Raised 23 September 2026 while briefing Stage 13 (`VRS-F005`), the feature F226 and F231 both name as the eventual owner of the deferred materialized working-day index.

**The inheritance.** F226 (closed during Stage 12's briefing) deferred `VRS-F004`'s G06 (the index's existence and materialization) and the index-rebuild half of G07 "in full to whichever stage builds `VRS-F005`," on the reasoning that the index's only reason to exist is this feature's own 200ms/150-employee render budget, and that it should be "designed against the server-authoritative architecture as it stands at that time, not against the retired one this document's prose still describes." `VRS-F004`'s own Materialization section describes the original design: "a working-day index... materialized in the SQLite-WASM index... consuming features read this index; they never walk the graph," rebuilt incrementally on five trigger events. That description predates the September 2026 pivot and was written against Loro's client-side CRDT materialization pipeline, not the current one.

**What actually changed underneath it.** Under F199/F201, `wa-sqlite` is retained but is now "fed by replication rather than by CRDT materialization" — it is an ordinary local SQL index over Electric-replicated Tier 0 rows, not a bespoke Worker-private materialization step. `WorkingCalendar`, `Holiday` and `WorkingPattern` are all Tier 0 (confirmed directly against `packages/schema/src/registry/nodes.ts`), so every row the resolution order in `VRS-F004`'s "Resolution order" section needs is already present in the device's local cache today, with no additional replication design required. Stage 12 built `workingDays.*` server-side, unindexed, evaluating the resolution order directly per call — correct for Stage 12's own callers, but server-only, which does not by itself give the Bench Forecast a local, no-network evaluation path; calling that server API per render would break `benchForecast.get`'s "no network round-trip" claim (see F236, which resolves the parts of that claim actually invalidated by Tier 1/2 data — this finding is about the Tier 0 timeline computation itself, which the "no network" claim correctly describes provided the resolution logic is available locally).

**Closed by founder-delegated decision, 23 September 2026.** No separate materialized index table is built. The resolution-order logic — the same four-step Holiday → WorkingPattern → WorkingCalendar → ReducedHoursPeriod evaluation `workingDays.*` already implements server-side — is extracted into a portable, pure, no-I/O function in `packages/schema` (the same pattern F233 already established for `initialWorkingWeekFor`: one canonical implementation, called from both sides, never duplicated). `services/api`'s existing `workingDays.*` calls it unchanged; the Bench Forecast's client-side renderer calls the identical function directly against the device's local Tier 0 cache (`WorkingCalendar`, `Holiday`, `WorkingPattern`, already replicated), never through a server round-trip. At 150 employees × 90 cells (13,500 evaluations of a plain function over already-local SQL rows, not a graph traversal through a sync protocol), this comfortably meets the 200ms render and 50ms filter budgets without precomputation — the same "no cache, no precomputed table, prove it against the real numbers before building one" judgment F226 itself already applied to Stage 12, now applied to the stage F226 pointed at. If Stage 13's own performance testing shows the unindexed evaluation does not meet budget at real data volumes, that is a new finding to raise then, grounded in a real measurement — not a reason to build the original index speculatively now. `VRS-F004`'s G06/G07 and Materialization section, and `VRS-F005`'s Technical Architecture, are both corrected to record this resolution in place of the open deferral.

**Status: closed.** Stage 13 is unblocked; it owns no separate index-building obligation.
