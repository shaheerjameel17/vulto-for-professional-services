### F369 — the Manager's broad Employee/Assignment read scope is F292's deliberate, founder-ruled widening, not a UI-3 gap

**Found while:** Codex's UI-3 pre-build trace (its UI3-A), traced against Do item 5's own instruction to confirm rather than assume whether the sync audience already scopes a Manager's rows to direct reports. Independently re-traced against `packages/schema/src/policy/policy-table.ts` (`Employee:operational` lines 376–383, `Assignment` lines 450–455), `services/api/src/permission/interceptor.ts::bestCell`/`rowScopeSatisfied` (lines 294–320), and `services/api/src/audience/materializer.ts` (lines 256–283) before ruling — and, critically, against the history that put that policy row there.

**What Codex found, confirmed accurate.** `Employee:operational`'s `manager` cell carries `readScope: "any"`; `bestCell`'s row-scope check downgrades an out-of-scope row from `full` to plain `read` rather than denying it when a `readScope` is present and satisfied. `Assignment`'s `manager` cell is `FULL_ANY()` outright, no scope restriction at all. The materializer's audience build calls `decideRead` per candidate node and replicates every node the principal can read, at any access level — so a Manager's device cache genuinely receives every workspace Employee and every Assignment, not only their direct reports'. This is real; Codex did not misread the code.

**Why it is not a gap.** `F242` (23 September 2026, Stage 13) described "the caller's own authorized base cohort (a Manager's direct reports, or workspace-wide for a role with broader read, exactly as the forecast itself is already scoped)" — written against the policy table as it stood *that day*, when `Employee:operational`'s `manager` cell was still bare `cell("full", "direct-reports", ...)` with no `readScope`. `F292`, raised later during Stage 21 while building the skill matcher, found and closed exactly this: `VRS-F013`'s own Decisions Recorded is explicit that "employee operational data — name, role, skills, availability — is readable by every workspace member," and gives as its first reason that "`VRS-F005` (the Bench Forecast) already renders every active employee as a row to every viewer." Put to the founder as a genuine architectural fork (how to grant a wider read ceiling than the write ceiling — nothing in the engine did that yet), the founder decided the general mechanism specifically because it "correctly closes the gap everywhere the spec's own reasoning said it should be closed" — naming Bench Forecast by name as one of the three places this was meant to apply. `readScope: "any"` on `Employee:operational` is that decision, implemented. `F242`'s "direct reports" phrasing simply predates it and was never revisited once `F292` shipped.

`Assignment`'s `FULL_ANY()` for manager was not examined by either finding directly, but it is consistent with the same underlying product intent `F292` states: Bench Forecast is a cross-team staffing and resource-planning tool, and a Manager assigning bench capacity onto their own project needs to see and act on Assignment rows company-wide, not only their direct reports' — the same reasoning that made Employee visibility workspace-wide applies to the Assignment rows a staffing decision touches.

**What is actually stale.** `VRS-F005`'s own text — its "what a Manager sees" framing and the Owner/Manager switcher this stage's brief already calls prototype scaffolding — describes a role-scoped view that `F292` deliberately superseded before this stage was ever briefed. The spec's prose was never corrected to match, so it read, correctly, as a contradiction with the real audience when Do item 5 asked Codex to check rather than assume.

**Ruling. Closed 29 September 2026, on F292's own founder-delegated precedent, no new founder ruling needed.** The audience is correct as built; UI-3 does not add a client-side Manager filter, exactly as Do item 5 already forbade. `VRS-F005`'s "what a Manager sees" section is corrected to state the current, intentional design: every active Employee and every Assignment render as a row to every viewer with the operational-tier read `F292` already granted, Tier 1/2 fields remaining gated per-field as before. Do item 5 is corrected from "trace and report a possible gap" to "confirm `F292` governs this screen and correct `VRS-F005`'s stale direct-report language accordingly"; its instruction to remove the role toggle/`principal.current`/`lib/viewer.ts` read stands unchanged, since the real audience now legitimately shows the same broad view to every role without any client-side reduction.

**Status: closed** (spec-language correction against an existing founder ruling, folded into the corrected UI-3 brief).
