### F359 — `Table` owns its sorted row order privately; the profile screen cannot share it for J/K without a small additive API

**Found while:** Codex's UI-2 pre-build trace, 27 September 2026, tracing Do item 6 before writing product code.

`packages/ui/src/Table.tsx` holds `sort` as its own `useState` (line ~146) and derives `sortedRows` internally; `TableProps` (lines ~61-82) exposes `onReorderColumns` for column order (an established precedent, F44) but nothing analogous for row order. The People screen owns the filter state, but the header-driven sort the person actually sees lives entirely inside `Table` and never reaches the page — so handing the profile screen "the directory's current filtered/sorted order" for J/K, as the brief asked, is not possible from `apps/roster-web` alone; it needs one small change in `packages/ui`, which the brief's own scope line ("otherwise lives in `apps/roster-web`") did not authorize.

**Files:** `packages/ui/src/Table.tsx`, `apps/roster-web/src/app/(shell)/people/page.tsx`, `apps/roster-web/src/app/(shell)/people/[id]/page.tsx`

**Ruling.** **Closed 27 September 2026 by ruling.** `Table` gains one additive prop, `onOrderedRowsChange?: (rows: T[]) => void`, fired from an effect whenever its internally-computed `sortedRows` changes (never during render) — the existing `sort` state, its three-way toggle cycle and `sortedRows`'s comparator are untouched. The People screen keeps the emitted employee rows in one small piece of shared client-side state (a module-level store or a light context; Codex's choice, not a route param — sort order is transient UI state, not URL-worthy) that the profile route reads for `J`/`K` in place of `PROFILED_EMPLOYEE_IDS`. When the profile is opened without the directory having been visited in this session (a bookmark or a fresh load), that shared state is empty; `J`/`K` falls back to the plain (unsorted, unfiltered) directory order from `employee.listForDirectory` rather than failing. This is the one `packages/ui` file this stage touches, alongside the two `device-query` names in `packages/graph`; nothing else outside `apps/roster-web` changes.
