### F281 — a role-filtered cohort cannot produce a role-independent agency aggregate

Raised 25 September 2026 by Codex, tracing `utilizationDashboard.getAgencyAggregate` into the existing interceptor immediately after F280, still before any product code. `VRS-F011`'s own spec is explicit that the agency aggregate is a single figure, identical for every role that can see it — not a per-role recomputation like the Bench Forecast's Manager view: Owner, HR Admin, Finance Admin and Manager all see the same agency-wide percentage, and even a Team Member's own dashboard shows that same number alongside their personal pulse bar (only `perEmployee`, the ranking list beneath it, is role-scoped — Manager to direct reports, Team Member not receiving it at all). The only existing mechanism for building an Employee cohort, `listEmployees`, runs under the caller's own ordinary principal and returns whatever that principal is authorized to read — for a Team Member, at most their own team. A cohort built this way cannot produce the agency-wide figure the spec requires that same Team Member's dashboard to show. No existing mechanism reads across the whole agency independently of the caller's own role.

This was escalated directly to the founder as a genuine architectural fork: no precedent existed for a read that must return the identical result regardless of which role requests it, since every prior read-scoping mechanism in this codebase (`filterReadable`, `listEmployees`, `rowScopeSatisfied`, the Bench Forecast's own cohort) exists specifically to vary by caller. The reviewer's first-pass recommendation proposed a dedicated bypass function reading `Employee` rows directly, unguarded by the interceptor, with privacy enforced solely by `applyDisclosureControl` on the resulting figure — and justified the Manager's own aggregate staying team-scoped by analogy to the Bench Forecast.

Put to a robustness challenge ("think deeply... if it's still the one you gave no problem, if not present me the best possible solution"), a second pass found this recommendation wrong on two counts. First, factually: re-reading `VRS-F011`'s own Security Considerations more carefully showed the aggregate figure is the *same* single agency-wide number for every role, never team-scoped for a Manager — the Bench Forecast analogy was backwards, since `VRS-F005`'s own spec states explicitly that its Manager aggregate is deliberately recomputed from the manager's own cohort, "not the firm's number with rows hidden," which is the opposite of what `VRS-F011` requires. Second, architecturally: a raw bypass function sits outside the interceptor entirely, which `VRS-F005`'s own spec also states as a hard principle — every query "must never construct permission logic of its own... queries through the same interceptor as everything else." A function reading `Employee` rows directly and relying on output-side disclosure control alone would violate that principle for a code path this codebase had not previously needed.

**Closed by founder-delegated decision, 25 September 2026, on the corrected design.** Rather than a new bypass mechanism, a second operation, `utilization-snapshot.read-cohort`, is granted to the same `utilization-snapshot-compute` principal F280 already introduces. This operation covers read access to `Employee:operational` (for cohort membership — Ghost Resource and zero-`contracted_hours` exclusion, `bench-forecast-queries.ts`'s own precedent for exclusion, reused rather than reimplemented) and `UtilizationSnapshot:record` (for summing each cohort member's already-computed figure — reusing each employee's stored snapshot, never re-deriving from `TimesheetEntry` a third time alongside `saveCell` and `utilizationSnapshot.compute`'s own read). `getAgencyAggregate` runs this cohort-and-sum step under the system principal uniformly for every caller regardless of role, since the figure it produces is always the same number — the read genuinely does not vary by who asks, so the mechanism that computes it does not vary either. `perEmployee` remains a fully separate read, executed under the caller's own ordinary principal via `listEmployees` and row-scoped `UtilizationSnapshot` reads (F279's fix), gated by the caller's own role exactly as the System States table describes — a Team Member's response carries no `perEmployee` field at all, a Manager's is scoped to their own direct reports, and neither read shares any code path with the system-principal aggregate step.

Implementing both F280 and F281 required granting one system principal two operations with different node targets — `utilization-snapshot.compute` writes `UtilizationSnapshot:record` alone; `utilization-snapshot.read-cohort` reads both `Employee:operational` and `UtilizationSnapshot:record`. `interceptor.ts`'s existing system-principal branches in `decideRead` and `authorizeWrite`'s Gate 1 were each hardcoded to a single operation and a single target (`timesheet-anomaly.read-flags`/`timesheet-anomaly.create-flag` against `TimesheetAnomalyFlag:record` alone); extending either with a third hardcoded clause, now needing to check multiple targets for one operation, was judged not worth repeating a second time — especially since `docs/Vulto_Specs/VRS-F058_People_Analytics_Dashboard.md` already states its own intent to reuse this exact aggregation mechanism directly ("aggregates per week exactly as VRS-F011's own agency view aggregates the current week. No new percentage calculation is invented"), meaning a third system operation on this same principal, or a new one, is a near-certainty rather than a hypothetical. Both branches are generalized into one new closed table, `SYSTEM_OPERATION_TARGETS` (`packages/schema/src/policy/principal-policy.ts`), mapping each node-targeting `SystemOperation` to its permitted `{ nodeType, partitionKey }` target(s):

```ts
interface SystemOperationTarget {
  readonly nodeType: NodeType;
  readonly partitionKey: string;
}

export const SYSTEM_OPERATION_TARGETS: Readonly<
  Partial<Record<SystemOperation, readonly SystemOperationTarget[]>>
> = {
  "timesheet-anomaly.create-flag": [{ nodeType: "TimesheetAnomalyFlag", partitionKey: "record" }],
  "timesheet-anomaly.read-flags": [{ nodeType: "TimesheetAnomalyFlag", partitionKey: "record" }],
  "utilization-snapshot.compute": [{ nodeType: "UtilizationSnapshot", partitionKey: "record" }],
  "utilization-snapshot.read-cohort": [
    { nodeType: "Employee", partitionKey: "operational" },
    { nodeType: "UtilizationSnapshot", partitionKey: "record" },
  ],
};
```

`decideRead`'s and `authorizeWrite`'s node-target system-principal branches both replace their hardcoded single-operation check with a lookup against this table (`isSystemOperationPermitted(principal.name, operation)` unchanged, now paired with a `target` membership check against the operation's own entry); `audit.pseudonymize-actor`, `protected.destroy-key` and `audience.recompute` are absent from the table since they bypass the interceptor entirely (F270's own note) and never reach these gates. `authorizeWrite`'s separate `triggered_by` edge-shape clause for `timesheet-anomaly.create-flag` is left unchanged — it is still a single-user pattern, not worth generalizing until a second edge-shaped system write exists. `docs/Vulto_Specs/VPS-A004_Graph_Permission_Layer.md` gains a new technical specification, A004-T25, recording this as the closed table a system-principal node-targeting operation must be declared in, rather than a per-operation hardcoded clause.

**Status: closed.**
