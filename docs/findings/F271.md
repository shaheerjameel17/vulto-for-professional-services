### F271 — F270's system-principal write authorized creating a flag, but not the audited read `timesheetAnomaly.evaluate` needs to decide whether to

Raised 24 September 2026 by Codex, resuming Stage 18 after merging F270's ruling (`3837102`, pulling `6f4b80a` from `main`) but before implementing it. Tracing `VRS-F010`'s own G09 ("at most one Active uncleared flag per employee, week and reason; a repeat trigger updates `detail`") and G09b (an `ApprovedOvertime`-cleared `HoursExceedExpected` flag must never reappear) into the evaluator's required logic exposed a second gap: both rules require inspecting a candidate flag's prior siblings — `employee_id`, `week_start_date`, `flag_reason`, `cleared_at`, `clearance_outcome` — before deciding whether to create a new flag, update an existing one's `detail`, or skip evaluation entirely. `TimesheetAnomalyFlag` is `fixedProtection("Manager-restricted", 2)` (F269's own subject); its fields live encrypted in `graph_protected_fragments`, never in the plain `graph_nodes.record`. The only audited decrypt path is `services/api/src/protected/read.ts`'s `readProtected`, which calls `authorizeRead` — and thus `decideRead` — per fragment before releasing anything. `decideRead`'s own `decisionRoles` helper already special-cases system principals with a one-line comment predating this feature entirely: "A system principal holds no node grant; its policy rows list operations" — returning `{ roles: [], readOnly: true }` unconditionally, so `bestCell` finds nothing to grant and every read resolves `access: "none"`. F270 gave `timesheet-anomaly-evaluate` exactly one operation, `timesheet-anomaly.create-flag`, write-only; it authorizes creating a flag, not reading one. The submitting Team Member's own principal cannot substitute either — `NONE` on `TimesheetAnomalyFlag`, the same deliberate restriction F270 itself turned on. Codex correctly declined to decrypt directly, fabricate an HR Admin principal, or infer cleared/uncleared status from any unencrypted signal (the `triggered_by` edge identifies only the Employee, none of the week, reason or clearance fields), and stopped to report it rather than let G09/G09b's enforcement go silently unimplemented.

This is not a second architectural fork. F270 established the mechanism — a closed, per-principal table of named operations, checked at a Gate-1-equivalent point instead of the role matrix, because a system principal never holds a `PolicyRole` — for exactly this system principal, this node type, and (per `fixedProtection`, not `splitProtection`) this one partition. The read-side seam already existed, unwired, before F270 was ever raised: `decisionRoles`'s "its policy rows list operations" comment is original code, not something either ruling added. What F271 needs is the previously-unbuilt other half of the same mechanism, for the same principal and the same node type — not a new design question. The one place judgment could have mattered — how narrowly to scope the grant — resolves the same way F270's write already did: the interceptor's operation table is a boolean per-principal permission, not a row filter; `timesheetAnomaly.evaluate`'s own query logic, not the gate, is what limits a read to the one employee/week/reason triple actually being evaluated, exactly as its write is already trusted to create only the one flag it means to.

**Closed, traced directly to F270's own freshly-established mechanism — no founder consultation needed.** `packages/schema/src/policy/principal-policy.ts`: add `"timesheet-anomaly.read-flags"` to `SYSTEM_OPERATIONS`; extend `SYSTEM_PRINCIPAL_OPERATIONS["timesheet-anomaly-evaluate"]` to `["timesheet-anomaly.create-flag", "timesheet-anomaly.read-flags"]` — the same closed table, now permitting two operations for the one principal instead of one. `services/api/src/permission/interceptor.ts`'s `decideRead` (via `decisionRoles`, or a distinct branch alongside it — Codex's implementation call) gains the read-side counterpart to `authorizeWrite`'s Gate 1: for `principal.kind === "system"`, checked against `isSystemOperationPermitted(principal.name, "timesheet-anomaly.read-flags")` instead of falling through `bestCell` with an empty role set, granting `access: "full"` on permit. `ReadDecision`'s `full`/`read` variant currently requires a non-null `role: PolicyRole`; it widens to `role: PolicyRole | null`, mirroring `WriteDecision`'s own `role: PolicyRole | null` shape one type over in the same file — the identical accommodation F270 already needed for the write side, not a new pattern. The member-only subject-exclusion branch in `decideRead` is unaffected — it already gates on `principal.kind === "member"`, and `TimesheetAnomalyFlag` carries no registered subject exclusion regardless (F269). No change to `readProtected` itself: it already calls `authorizeRead` per fragment and will honor the new grant unmodified. `timesheetAnomaly.evaluate` queries prior `TimesheetAnomalyFlag` rows for the employee/week/reason being evaluated through `readProtected`, passing the same `{ kind: "system", name: "timesheet-anomaly-evaluate", workspaceId }` principal F270 already requires it to construct for the write — one principal, two operations, no second mechanism. `docs/Vulto_Specs/VRS-F010_Timesheet_Speed-Run.md`'s Security Considerations is corrected to record this read grant alongside F269's and F270's own entries.

**Status: closed.**
