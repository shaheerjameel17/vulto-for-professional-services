### F268 — `rowScopeSatisfied` cannot resolve TimesheetEntry's or TimesheetAnomalyFlag's subject Employee

Raised 24 September 2026, checking `VRS-F010` directly against the code before writing its brief. `TimesheetEntry`'s policy row (`packages/schema/src/policy/policy-table.ts`) grants Team Member `Full (own only)` and Manager `Read (direct reports)`; `TimesheetAnomalyFlag`'s grants Manager `Full (direct reports)`. Both are row-scoped cells, and `services/api/src/permission/interceptor.ts`'s `rowScopeSatisfied` is the only place a row-scoped grant is evaluated against an actual row. It resolves a row's subject Employee two ways: `row.nodeType === "Employee"` (the row's own `nodeId` is the subject) or `row.nodeType === "BurnoutAlert"` (follow its registered `triggered_by` edge). Every other node type falls to `else return false` — refusing the grant regardless of role, the identical structural gap F264 found for Pitch before any policy row could take effect.

Neither existing mechanism reaches `TimesheetEntry` or `TimesheetAnomalyFlag`. `VRS-F010`'s own schema (G04) stores `employee_id` as a direct field on `TimesheetEntry` — deliberately, not an edge: "a Pitch entry has no Assignment to traverse through at all," so the field can't be made conditional on which edge a given entry happens to carry. `TimesheetAnomalyFlag`'s schema carries the same direct `employee_id` field. `services/api/src/permission/reader-set.ts`'s separate `resolveSubjectEmployee` mechanism (FDN-89, sync-audience resolution, a different policy axis from `rowScopeSatisfied`'s row-scope grants) is also edge-only — `SUBJECT_EXCLUSIONS`'s `subjectPath` is typed `readonly EdgeType[]` and currently lists only `HRCase`/`CaseEvent` — so registering a `subjectPath` there would not help either, and would misuse a mechanism built for excluding a row's subject from an otherwise-broad reader set, not for granting that subject their own row-scoped access. As built today, every read or write an employee attempts against their own `TimesheetEntry`, and every clearance a Manager attempts against a direct report's `TimesheetAnomalyFlag`, would be refused.

**Closed, traced directly to `rowScopeSatisfied`'s own established generalization pattern (F251, F262, F264) — no founder consultation needed.** A third resolution branch: for `row.nodeType === "TimesheetEntry"` or `"TimesheetAnomalyFlag"`, read the row via the interceptor's already-imported `getNode`, and take `subjectEmployeeId` from its own `employee_id` field (a lookup failure, or a non-string field, resolves to `false`, the same fail-closed posture as the two existing branches). This is not a new grant type, a new edge, or a change to how `own`/`direct-reports`/`own-plus-team` are evaluated once `subjectEmployeeId` is known — only a new way to find it, and the way the spec's own field-not-edge design already dictates. `resolveSubjectEmployee`/reader-set is unaffected: it already returns `UNRESOLVABLE` for any node type carrying a Manager grant at `full`/`read` outcome, `TimesheetEntry` and `TimesheetAnomalyFlag` both included, a pre-existing conservative default this finding does not need to touch.

**Status: closed.**
