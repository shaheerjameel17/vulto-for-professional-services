### F293 — the system gap evaluator has no read grant for its own match cohort

Stage 21 item 8 requires `skillGap.evaluate` to call item 7's shared `matchCandidates` under the new `skill-gap-evaluate` system principal (item 9), which reads candidate Employees via `filterReadable`. Checked directly against `services/api/src/permission/interceptor.ts`'s `decideRead`: a system principal's branch is entirely separate from a member's — `systemNodeTargetPermitted(principal, context.systemOperation, nodeType, partitionKey)` checks only whether the named operation's entry in `SYSTEM_OPERATION_TARGETS` (`packages/schema/src/policy/principal-policy.ts`) lists that exact `(nodeType, partitionKey)` pair; it never consults `decisionRoles`/`bestCell`/any policy cell at all, by design (A004-T25: "node grants are exclusively the operation's closed target list"). Item 9 as originally specified granted `skill-gap-evaluate` only `"skill-gap.write"`, targeting `{ SkillGap: "record" }` — no read grant of any kind. Without one, every call to `matchCandidates` under this principal would read zero candidates regardless of who actually qualifies, and `skillGap.evaluate` would create a `SkillGap` for every requirement, real matches included — a false positive indistinguishable, in its output, from a genuine capability gap.

**Closed by direct precedent.** This is the identical shape F281 already solved for `utilization-snapshot-compute`, and item 9's own original text already cited that precedent by name ("F280/F283's own precedent") without extending it far enough: `utilization-snapshot-compute` holds two operations, `"utilization-snapshot.compute"` (its write) and `"utilization-snapshot.read-cohort"` (its read, targeting `{ Employee: "operational" }` and `{ UtilizationSnapshot: "record" }`), declared side by side in one closed table rather than a second hardcoded interceptor branch. `skill-gap-evaluate` gains the same shape: a new `"skill-gap.read-cohort"` operation, granted alongside `"skill-gap.write"`, targeting `{ nodeType: "Employee", partitionKey: "operational" }`.

No target entry is needed for Skill or Assignment, correcting an overstatement in the Stage 21 report's own framing ("reads Employees/Skills/Assignments through `filterReadable`"). Checked directly: item 7's own already-ruled text specifies that `matchCandidates`'s availability resolution "uses the same Assignment-coverage primitives `cohortEmployee`/`computeBenchStatus` already use (`assignmentCovers`, the Assignment query helper in `bench-forecast-queries.ts`)" — and that helper (`assignmentsFor`) calls `getNodes` directly, never `filterReadable`, the same trusted, unauthenticated derived-day pattern already established for the Pitch-date exclusion (F283) and used identically today under ordinary member principals, not only system ones. Skill needs no target either: item 3's `MATRIX_OVERRIDES` row grants every role at least `READ_ANY()` on `Skill`, but that is beside the point for a system principal in any case, since `matchCandidates`'s matching logic compares the required proficiency against the `has_skill` edge's own metadata (`proficiency_level`, F289) — no Skill node content is read to decide a match; a Skill node read is needed only by `skillMatcher.adHocSearch`'s free-text mode, which runs under the calling member's own ordinary principal, never this system principal.

**Status: closed.**
