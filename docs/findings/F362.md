### F362 — `VRS-F021` and `VRS-F022` stated a genuine circular dependency, and are now built together as one effort with Vault first

**Found while:** Explaining the 28 September 2026 independent audit's finding "1a" (three circular `Depends On` clusters across the specification set) to the founder in plain language. `docs/Vulto_Specs/VRS-F021_E-Signature_Native.md` listed `VRS-F022` under **Depends On** ("where the signed document is filed"), and `docs/Vulto_Specs/VRS-F022_Encrypted_Document_Vault.md` listed `VRS-F021` right back under its own **Depends On** ("which files a signed contract here"). Each document named the other as something it needed to exist first — a genuine build-order cycle, not a stylistic inconsistency, and not resolvable by reading either document in isolation.

**The founder's ruling, 28 September 2026:** treat `VRS-F021` (E-Signature) and `VRS-F022` (Document Vault) as one combined build effort, with Document Vault built first — formalized as E-Signature being blocked by Document Vault, the reverse of what the migrated Notion issue relations previously stated.

**Why Vault-first breaks the cycle rather than just relabeling it.** Vault's core mechanism — a document's protection tier is inherited from its provenance, not fixed by node type (an uploaded certification defaults to Tier 0; a document inherited from a Contract is Tier 1) — is fully specified and buildable using only `VRS-F002` (Employee) and `VRS-F020` (Contract, already Tier 1) as sources. It does not need E-Signature's code to exist; a signed contract is simply one caller of a filing mechanism Vault already owns. E-Signature, by contrast, has nowhere to file the document it produces until Vault exists. The dependency was only ever one-directional; the specs had it stated in both directions.

**Files:**
- `docs/Vulto_Specs/VRS-F021_E-Signature_Native.md` — Depends On entry for `VRS-F022` reworded to state the hard build-order dependency explicitly; new **Build note** added.
- `docs/Vulto_Specs/VRS-F022_Encrypted_Document_Vault.md` — `VRS-F021` removed from **Depends On**; `VRS-F021` added to **Blocks**; new **Build note** added.
- `docs/Vulto_Specs/VRS-001_Feature_Register.md` — ordering-principle #1 amended with one documented exception (a numerically-later feature, F022, now built ahead of F021); feature-register table row for F022 updated.
- Notion: "Stage — E-Signature Native (VRS-F021)" (`ISU-62`/`RST-64`) and "Stage — Encrypted Document Vault (VRS-F022)" (`ISU-61`/`RST-67`) — `Blocked by`/`Blocking` relation properties flipped to match (Vault blocks E-Signature); "Contracts, Signing & Documents" milestone (`VMS-14`) brief annotated with the build order and combined-effort decision.

**Ruling.** **Closed 28 September 2026 by founder ruling.** `VRS-F021` and `VRS-F022` are built together as one combined effort within the existing "Contracts, Signing & Documents" milestone (`VMS-14`, which already scoped all of `VRS-F020`/`F021`/`F022` together) — no new Project or Milestone was created, since this one already is the shared grouping the founder asked for. Document Vault is built first; E-Signature is formally blocked by it. The Feature Register's numbering convention (a feature is never numbered before something it depends on) now carries one documented, accepted exception for this pair rather than a silent contradiction. This resolves finding "1a" of the 28 September independent audit for the e-signature/vault pair specifically; the other two circular clusters that finding named (skill-gap/intelligence/probation; payroll-currency/disbursement) remain open.
