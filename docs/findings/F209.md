### F209 — a cryptographic erasure has no audit event

Raised 21 September 2026, building Stage 5's `erasure.ts`.

**What is specified.** `VPS-A003` "Cryptographic erasure": "`VPS-F004` records that erasure occurred." `VPS-F007` G04 exempts the journal from erasure. The Stage 5 brief has the erasure function call `appendAudit`.

**What is not.** The `AuditEntry` contract in `VPS-F004` (as extended by F206) is a closed vocabulary. Its event types describe access decisions and a privileged projection; its operations are `NodeRead`, `NodeCreate`, `EdgeCreate` and the like; its targets are a node, an edge or a query. Destroying an erasure domain's key is none of these: it is a system operation on a key, concerning a domain that may be a person.

**Closed by founder-delegated decision, 21 September 2026.** The recommendation was accepted with one addition. `AuditEntry` gained event type `CryptographicErasureExecuted`, operation `KeyDestroy` and the closed target `ErasureTarget { erasure_domain_id, tier, destroyed_key_count, erasure_request_id }`, written only by the `erasure` system principal, in the same transaction as the key destruction. `erasure_request_id` is null until `VPS-F007`'s ErasureRequest exists, and required from then on, so every erasure traces back to an approved request. `VPS-F004` was corrected (G09). Built in Stage 5: the `ErasureAudit` seam was replaced with the real `appendAudit` call, and a test proves a failed audit destroys no key.
