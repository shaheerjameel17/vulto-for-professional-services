### F303 — F302's label guard excluded every real Ghost Employee

F302 ruled that the `cache_search` triggers index a node only when its registered `labelField` is a non-empty string, so a nameless node is unsearchable rather than an error. For `Employee` the registered label field was `full_name`. Codex resumed on that ruling, traced the guard against the real Ghost writer before writing any product code, and stopped (`11684a6`): `ghost.create` (`services/api/src/mutations/ghost-resource.ts`) builds its Employee with `ghostEmployeeOperationalRecord` (`packages/schema/src/employee.ts`), which deliberately sets `full_name: null` and places the role title in `job_title` — `VRS-F007`'s own Ghost identity contract, settled at F253 — and the unchanged Stage 22 Skill Matrix test uses that same Ghost shape. F302's guard therefore excluded every real Ghost from the index, while the brief's Do item 3, Do item 7, its Done criteria and `VPS-F002`'s own acceptance criterion ("a Ghost's role title matches the query") all require a Ghost to be found by its role title and returned with `isGhost: true`. A test Ghost given an invented non-empty `full_name` would have passed while hiding exactly this production failure. The guard was written for one row shape without checking every real writer of that node type.

**Closed by direct precedent — `VRS-F007`'s own Ghost identity contract (F253) is settled and must not change merely to satisfy search, and the brief's Ghost requirements are the specified behavior; the brief's label rule was the defect. No founder consultation needed.** The ruling, in full. (1) The registry's `labelField` becomes an ordered, non-empty `labelFields` list, each entry also a registered indexed field and each provably Tier 0: `Employee` is `["full_name", "job_title"]`, `Skill`, `Project` and `Client` are `["name"]`. (2) The label is the first entry, in order, whose value is a non-empty text (`json_type(record_json, '$.<field>') = 'text'` and the extracted value `<> ''`); a node with none resolvable gets no index row (any existing row is deleted on update) and the trigger still has no path that can raise. A Ghost is therefore indexed under its role title, and a real Employee under its name. (3) When an Employee's label was itself resolved from `job_title` (a Ghost), its `secondaryLabel` is `null`, not a repeat of the label. (4) Tests build the Ghost with `ghostEmployeeOperationalRecord` (`full_name: null`, role title in `job_title`), never an invented name: it is indexed with `label` equal to its `job_title`, found by that role title, returns `isGhost: true` and `secondaryLabel: null`, and a later `putNode` adding a real `full_name` re-labels it; an Employee with neither field, with empty strings, or with non-text values is written without error and gets no row. The browser suite's expected set becomes rows that have a resolvable label. (5) `operationalShape` (`packages/schema/src/employee.ts`), which the registry's Tier 0 validation for the tier-split `Employee` type was told to consult, is a module-private constant; export it, or a key list derived from it, from that file (in scope, inside `packages/schema`). The reviewer audited the rest of the brief's field assumptions against the code in the same pass, rather than waiting for a fourth stop: `Skill.name` and `Skill.category` exist (`category` is nullable, so `null` reads as absent under the same rule), `Project`/`Client` `name` is read as `record["name"]` by `bench-forecast.ts` and `pitch-queries.ts` (both fixed Tier 0 with no field schema, so any field is Tier 0 by registration), Assignments link to Employees through `record["employee_id"]`, and `record_json` holds the record at its top level.

**Status: closed.**
