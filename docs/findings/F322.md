### F322 — notifications for an already dismissed or cleared source when the first delivery was skipped

**Found while:** the reviewer's independent review of the merged Stage 25 diff, 26 September 2026.

When the delivery engine is handed a touched source row it notifies for any `TimesheetAnomalyFlag`, and for any `RevenueGapAlert` that is `Active`, regardless of whether the source has already been cleared or dismissed (`dismissed_at` is set on a dismissed alert while its lifecycle stays `Active`; a flag's `cleared_at` is a protected field the engine may not read). Dedupe by `dedupe_key` hides this in every normal flow, because the notification already exists from creation. It surfaces only when the first delivery was skipped (the manager had no linked user, or there was no manager) and a later touch of the same source (a re-evaluation, or the clear or dismiss itself) arrives after the link exists: the manager is then notified about something already dealt with. Low severity: pre-pilot, and it needs a skipped first delivery.

**Files:** `services/api/src/mutations/notification-delivery.ts`, `services/api/src/mutations/revenue-gap-alert.ts`, `services/api/src/mutations/timesheet-anomaly.ts`

**Status.** **Open, raised 26 September 2026 (Stage 25 review), low.** Small follow-up: skip an alert whose `dismissed_at` is set (a Tier 0 field, cheap); for the flag, decide with the flag's owning feature whether a Tier 0 signal of clearance can exist (its `cleared_at` is protected), or accept the limitation. Not fixed in Stage 25: no shipped path produces it, and the fix for the flag half needs a design decision.
