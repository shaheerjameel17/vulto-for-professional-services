### F360 — `VPS-003`'s four plans gated features by Feature Type; the founder's decided commercial model is consumption-based, not feature-based

**Found while:** Working through the open "Commercial model and feature gating" item in the Vulto Documentation Contradictions & Reconciliation Register (raised 26 September 2026) at the founder's direction, 28 September 2026.

`docs/Vulto_Specs/VPS-003_Commercial_Model.md` built its entire "four plans" structure around [[VPS-000_Documentation_Standard|VPS-000]]'s Feature Type enum: Starter got `Core`/`Experience`, Professional added `Intelligence`/`Compliance`, Complete added `Financial`, Enterprise added `Platform`. A workspace's plan literally determined which Feature Types it could open (`planEntitlement.check(workspaceId, featureType)`, VPS-003-T01/T02/T08/T09). The founder's own pricing strategy (Vulto Product Suite, Pricing & Organization Architecture, sections 3–6) rejects this directly: "a core Vulto pricing principle is capability parity... engineering feature categories should not automatically become pricing gates." The register flagged this as a direct policy conflict on 26 September; the founder resolved it on 28 September.

`planEntitlement.check` was never implemented in code (`grep -rl "planEntitlement"` across the repository, excluding worktrees, returns nothing) — this is a pre-implementation spec correction, not a migration of built code.

**Files:** `docs/Vulto_Specs/VPS-003_Commercial_Model.md`

**Ruling.** **Closed 28 September 2026 by founder ruling.** Every feature, in every Feature Type, is available on every plan, including Starter, from day one. Feature Type reverts to pure engineering classification, exactly as [[VPS-000_Documentation_Standard|VPS-000]] and [[VRS-001_Feature_Register|VRS-001]] otherwise use it. Plans instead differ by scale, consumption, complexity and commercial obligation: internal users (already the billing unit), active clients/engagements, storage, automation executions and AI consumption once each dimension is metered, and API/compute usage (Enterprise). Exact numeric caps are deliberately left unset, to be informed by real product telemetry once each dimension exists, per the founder's own strategy document's own hedge on this point — this document does not invent numbers the founder hasn't given. Security stays split the same way it already was: core security (encryption, MFA/passkeys, secure sessions, Vault security, basic RBAC) is universal; organizational security governance (SSO/SCIM, customer-managed keys, residency choice, SIEM/DLP, advanced retention) stays Enterprise-only, for real operating cost reasons, not as a feature tax. `VPS-003`'s "Why this is a specification," "The four plans," "How a workspace's plan is enforced" (renamed from "How a feature knows its plan"), Technical Specifications (T01, T02, T08, T09), Acceptance Criteria, Out of Scope, and Decisions Recorded sections are corrected to match; `planEntitlement.check(workspaceId, featureType)` is replaced with `usageEntitlement.check(workspaceId, dimension)`, which passes unconditionally on any dimension with no cap yet defined. Pricing figures, the per-employee billing model, the early-adopter lock table, regional tiers, the billable-seat definition, the trial and the no-free-tier stance are all unchanged — none of those were part of what was decided today. [[VPS-A008_Trust_and_Data_Protection_Program|VPS-A008]]'s own reference to `VPS-003`'s Enterprise plan (P4/P8 customer-managed keys and residency) needed no change, since "Enterprise" remains the top plan name and CMK/residency remain Enterprise-only under the corrected model for the same reason they were before.
