### F254 — `promoted_to` has no governing Employee partition, so no Ghost can be promoted

Raised 24 September 2026 during Stage 15 implementation (`RST-43`) when the first real `ghostResource.promote` integration test reached the server permission interceptor.

**The gap.** `promoted_to` is registered as `GhostResource → Employee` in `packages/schema/src/registry/edges.ts`, but it declares no `governingPartitions` entry. Employee is tier-split into `operational` and `compensation`. `services/api/src/permission/interceptor.ts`'s `edgeRoleDecision` deliberately refuses an edge write with `reason: "role"` whenever a split endpoint has no reviewed governing partition; it does so before considering the caller's role. The real Stage 15 integration test therefore reaches the authoritative interceptor and rejects promotion for HR Admin, and the same structural check rejects Owner too. The GhostResource and linked Employee node updates never begin.

This is the same class of omission F208 found for `managed_by`/`scoped_to_entity` and F235 found for `pattern_for`: the endpoint pair is structurally registered, but it is not writable through the server-authoritative permission layer until the split endpoint's governing partition is specified. Stage 15's opening trace says the Ghost node and both edges are “already fully registered” and Do item 4 requires the `promoted_to` write, but neither the brief, `VRS-F007`, nor `VPS-A002` assigns that edge to Employee's `operational` or `compensation` partition.

The surrounding evidence points strongly to `operational`: promotion changes only Employee's Tier 0 operational identity fields, `VRS-F007` explicitly calls promotion an ordinary Tier 0 write (F252), and `has_skill`, `managed_by`, `scoped_to_entity`, `pattern_for`, `assignment_of`, and `holds_certification` already declare `{ Employee: "operational" }` for comparable operational relationships. But selecting a governing partition is an authorization decision. F208 and F235 both required that decision to be recorded in `VPS-A002` before code widened the relationship's write reach, so Stage 15 must not silently infer it here.

**Closed by founder-delegated decision, 24 September 2026, on F208 and F235's own precedent.** The evidence the finding itself lays out is conclusive and not a close call: promotion changes only Employee's Tier 0 operational identity fields (F252 already established promotion is an ordinary Tier 0 write, not a Tier 1/2/3 one); `VRS-F007` never touches compensation; and six existing edges targeting a split Employee endpoint — `has_skill`, `holds_certification`, `assignment_of`, `managed_by`, `scoped_to_entity`, `pattern_for` — are all already declared `{ Employee: "operational" }` for exactly this reason. No evidence anywhere points toward `compensation`.

1. **`promoted_to` is declared `{ Employee: "operational" }`** in `packages/schema/src/registry/edges.ts`'s `promoted_to` edge group, the same one-line addition F208 made for `managed_by`/`scoped_to_entity` and F235 made for `pattern_for`. No other change to the edge registry is needed.
2. **`VPS-A002`'s governing-partitions table gains a `promoted_to` row**, immediately after `pattern_for`'s, following the same format and rationale style as the six existing Employee-operational entries.
3. **`VRS-F007`'s Technical Architecture gains a one-line note** recording the governing partition, the same way `VPS-A002`'s own text already treats this as a reviewed, recorded authorization decision rather than an inferred one.
4. **No change to Stage 15's Do item 4 or Done criteria beyond registering the partition** — the already-written real-Postgres integration test (`dae1d01`) was correctly built against the intended behavior; it now exercises a permission layer that actually authorizes the write instead of structurally refusing it before any role is even considered.

**Status: closed.** Stage 15 is unblocked; the preserved implementation at `dae1d01` needs only this one registry declaration to proceed.
