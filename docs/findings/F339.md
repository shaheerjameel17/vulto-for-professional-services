### F339 — the ledger has no subject path and must be server-write only

**Found while:** briefing Stage 28, 27 September 2026.

`resolveStoredSubjectEmployeeId` has no branch for a `LeaveLedgerEntry`, so every row-scoped grant (`own`, `direct-reports`) would resolve to no subject and deny (the same structural gap as F268 for `TimesheetEntry`). And the clearing manager, a member principal, must not hold write on the ledger: an entitlement record any role could create or edit would defeat the point of a ledger.

**Files:** `services/api/src/permission/interceptor.ts`, `packages/schema/src/policy/policy-table.ts`, `packages/schema/src/policy/principal-policy.ts`

**Ruling.** **Closed 27 September 2026 by ruling, on F268's and F316's precedents.** The entry stores `employee_id` and the interceptor's stored-subject resolver reads it, exactly as for `TimesheetEntry` (no new edge type). The policy-table row grants no member a `full` cell (Owner, HR Admin and Finance Admin `read` any, Manager `read` direct reports, Team Member `read` own), so no member can write through any path. The one writer is a narrow system operation, `leave-ledger.write`, on a new system principal, invoked only inside the clearance transaction so the flag and its entry commit or roll back together. The reserved interceptor and system-principal changes are this stage's, by this ruling.
