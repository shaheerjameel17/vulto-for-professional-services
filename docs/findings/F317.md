### F317 — nothing reserves the delivered_to edge that defines the recipient

**Found while:** Codex tracing Stage 25 Do item 1 before writing product code, 26 September 2026 (stage report `0f8044f`); ruled by the reviewer the same day.

F307's ruling turned Notification's `Recipient-only` cells into `full` with a `recipient` scope and said adding Notification to `FEATURE_LIFECYCLE_NODE_TYPES` keeps writes closed. That set blocks generic node writes only. The `delivered_to` edge that defines the recipient is not reserved: `FEATURE_OWNED_EDGE_TYPES` (`packages/schema/src/mutations/employee.ts`) holds only `has_skill` and `requires_skill`, `createEdgeMutation`, `closeEdgeMutation` and `updateEdgeMetadataMutation` in `services/api/src/mutations/foundation.ts` consult that set, and `edgeRoleDecision` needs `full` on both endpoints, which the recipient now has on their own Notification and an Owner or HR Admin has on every `User`. So such a recipient could attach a second `delivered_to` edge and redirect or widen access; nothing makes `delivered_to` unique (`graph/schema.ts` limits single-active uniqueness to `managed_by` and `scoped_to_entity`); and a resolver that takes the first edge would follow a caller-chosen `effective_from`. Found by the builder's static trace of the effect of the F307 grant, not a live exploit.

**Files:** `packages/schema/src/mutations/employee.ts`, `services/api/src/mutations/foundation.ts`, `services/api/src/permission/interceptor.ts`, `services/api/src/graph/schema.ts`

**Ruling.** **Closed 26 September 2026 by ruling.** `delivered_to` joins `FEATURE_OWNED_EDGE_TYPES`, the same mechanism Stage 21 used for the skill edges, so the generic create, close and metadata-update edge mutations refuse it with `requires-feature-mutation` on the server, and on the client optimistic mutators once F318 adds the check they lacked. The `recipient` scope fails closed: satisfied only with exactly one active `delivered_to` edge whose target and the row's `recipient_user_id` both equal the caller; two edges, a disagreement or no edge is `false`, and no code takes the first edge. The delivery engine writes its edge as its system principal and is unaffected. Tests seed the conflict through the store. Not audited here: whether other edge types outside F291's set need the same reservation; `delivered_to` is the only one this stage's grant exposes. Lesson: a new grant needs a trace of every write path that grant now opens, edges as well as nodes.
