### F247 — RateCardLine has no traversable or indexed path from its RateCard

Raised 23 September 2026 while resuming Stage 14 (`RST-42`) after F245 and F246 were ruled, before any product code was written.

**The gap.** `VRS-F006` makes `RateCardLine` a fixed Tier 1 node whose substantive fields — `rate_card_id`, `seniority_level`, `hourly_rate`, `daily_rate`, `monthly_rate` — live entirely inside the protected partition. Stage 14 requires two point lookups against those fields: `rateCard.getPreview(rateCardId, seniority)` and `resolveAssignmentRate`, which must find the line matching an Assignment's `rate_card_id` and its Employee's `seniority_level`. The spec said RateCardLine carries no edge of its own because nothing needs to traverse *backward* from a RateCard except through its own lines — true, but it never defined how the *forward* lookup those two callers need actually reaches a line. `services/api/src/protected/read.ts`'s `readProtected` accepts only `nodeIds`, filtered by `inArray(ownerId, ids)` — a point lookup by id, never a predicate over decrypted content — so without an id to ask for, neither caller has an address. The only alternative, enumerating every RateCardLine in the workspace and decrypting each to filter in memory, is exactly the implicit foreign-key scan A002-T03 prohibits, the same rule F243 was closed on for Assignment-side `rate_card_id`.

**Closed by founder-delegated decision, 23 September 2026.**
1. **`RateCardLine.line_id` is generated deterministically from `(rate_card_id, seniority_level)`, not as a random UUID v4.** This extends a mechanism this codebase already has, not a new one: `services/api/src/auth/membership-edge-ids.ts`'s `deterministicUuid(seed)` (SHA-256 of a seed string, version/variant nibbles forced, still UUID v4-shaped) already derives `membership_of`/`membership_in` edge ids this way, and `packages/schema/src/mutations/foundation.ts` already derives F233's `initialCalendarId`/`initialCalendarEdgeId` the same way. `line_id` becomes `deterministicUuid(\`rate_card_line:${rateCardId}:${seniorityLevel}\`)`, computed server-side in `rateCard.create`/`rateCard.update`'s `apply()` step when each line is written. It remains UUID v4-shaped, satisfying A002-T02 exactly as the existing precedent does.
2. **`rateCard.getPreview` and `resolveAssignmentRate` compute the same id from context they already have — `rateCardId` and a `seniority_level` — and call `readProtected` with that one node id.** This is a point lookup, not a scan: no new edge, no index over encrypted content, no enumeration. A seniority level with no line under that card computes an id that was never written, so the lookup returns nothing — the exact "resolution falls through" behavior the spec already describes.
3. **This also makes G05 mechanical rather than a rule the mutation must separately enforce.** Two lines for the same seniority under the same card, whether in one `lines` array or across repeated writes to the same version, always compute the identical `line_id` and overwrite the same protected fragment — "a duplicate replaces rather than doubles" falls out of the id scheme itself, with no separate duplicate-detection code required.
4. **Nothing else about RateCardLine changes.** No edge is added (the spec's own "nothing needs to traverse backward" reasoning still holds — this is a forward lookup, not a reverse one); no index over encrypted content is added; RateCard/RateCardLine's Tier 1, Finance-restricted classification (G01) is untouched; `graph_nodes` still carries RateCardLine's ordinary Tier 0 shell row, unchanged, since `readProtected` already requires one to exist for any node it reads.

`VRS-F006`'s Technical Architecture (the RateCardLine block) and API contracts are corrected to state the deterministic id explicitly, as a new G10.

**Status: closed.** Stage 14 is unblocked; `rateCard.getPreview` and `resolveAssignmentRate` both have a real, scan-free lookup path, and G05 is enforced by construction.
