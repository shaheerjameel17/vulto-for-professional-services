### F350 — the People directory cannot be built on `listEmployees`; it needs a genuine local device-cache query

**Found while:** briefing UI-2, 27 September 2026.

`services/api/src/permission/employee-queries.ts`'s `listEmployees` is a server round-trip, already wired to `router.ts`. `VRS-F002`'s own Non-Functional Requirements are explicit and unconditional: "Directory renders under 200ms for 150 active employees from the device cache" and "The Tier 0 half of the profile and the directory are readable offline with no degradation." A server call cannot meet either — it has no offline behavior and no 200ms guarantee at any employee count, let alone under a real network round-trip. This is the identical shape F340 already ruled for the Inbox and palette: the spec requires a local answer, so the client needs its own query, not the server's.

**Files:** `apps/roster-web/src/app/(shell)/people/page.tsx`, `services/api/src/permission/employee-queries.ts`, `packages/graph/src/query.ts`, `packages/graph/src/sync-client/engine.ts`

**Ruling.** **Closed 27 September 2026 by ruling.** The People directory is a new `device-query` name (F340's kind, not a new kind), for example `employee.listForDirectory`, running against the worker's own cache database — the same `Employee` Tier 0 rows Electric already replicates, filtered and read exactly as `search.query` reads them today. It never calls `listEmployees`. Filtering (entity, employment type, status) and sorting run in the worker over the cached rows; column visibility and reorder stay client-only UI state as they are today. `listEmployees` is untouched and keeps serving whatever server-side callers already use it.
