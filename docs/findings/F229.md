### F229 — the pattern overlap refusal also rejects the replacement it requires

The Stage 12 brief says `pattern.set(employeeId, workingWeek, effectiveFrom)` closes the current Active WorkingPattern at `effectiveFrom`, marks it `Superseded`, and creates the next Active pattern. The same Do item says to reject if the new `effective_from` falls inside an existing pattern's still-open range. For a current pattern `[1 January, null)`, a normal change effective 1 March is inside the still-open range when validation runs. Taken literally, G04 rejects every second `pattern.set`, while permitting it requires treating the edge/node being atomically closed as an exception. The brief does not say whether a future-effective change is allowed, how backdating interacts with already-closed history, or whether a pending future pattern counts as current. Those choices decide whether history overlaps.

**Ruling — closed 22 September 2026.** The brief's stated overlap check was wrong as written: it treated the still-open range `pattern.set` is itself about to close as a rejection target, which rejects every legitimate replacement. `WorkingPattern`'s effective-dated boundary follows the same shared-boundary, half-open convention Stage 11 already established for `scoped_to_entity` (`closeAt`, edge closed *at* the new edge's own `effective_from`, no gap, no overlap): closing the current pattern sets its `effective_to` to the new pattern's `effective_from` itself, not the day before. G04's real overlap check is therefore not about the pattern being closed at all — it is a single guard: `pattern.set`'s `effectiveFrom` must be on or after the current Active pattern's own `effective_from`. A `effectiveFrom` earlier than that would fall inside an *already-Superseded* pattern's closed history (a genuine overlap G04 exists to prevent) rather than inside the one this call is closing, and is refused (`invalid-args`) rather than silently rewriting history. A same-day replacement (`effectiveFrom` equal to the current pattern's own `effective_from`) is allowed and simply supersedes it outright, zero-duration, exactly as a same-day `calendar.update` would. `pattern.clear` uses the identical guard and boundary convention, closing the current pattern with no replacement. `VRS-F004`'s G04 and Stage 12's Do item are corrected to state the check this way, reusing `closeAt`'s existing shape rather than inventing a second boundary convention.

**Status: closed.** Stage 12 is unblocked on this point.
