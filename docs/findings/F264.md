### F264 — Pitch has no creation mutation, no staffing relationship, and no read-access policy row; VRS-F009's spec assumes all three already exist

Raised 24 September 2026, checking `VRS-F009` (Time Classification Taxonomy) directly against the code before writing its Stage 17 brief, per standing practice — the same practice that surfaced F255–F258 before Stage 16's brief was written.

**The gap, in three parts.**

1. **No mechanism creates a Pitch, and none registers who is staffed on one.** `packages/schema/src/registry/nodes.ts` already registers `Pitch` (owner `VRS-F009`, `fixedLifecycle("Active","Won","Lost","Converted")`, `splitProtection` into a Standard-class `identifying` partition and a Finance-restricted `commercial` partition) — but no mutation anywhere creates one, and `packages/schema/src/registry/edges.ts` registers no Employee↔Pitch relationship of any kind. `VRS-F009`'s own API Contracts section takes both for granted: `timeEntry.classifyPitch(entryId, pitchId)`'s write-time dependency is stated as "`pitch_id` where employee is staffed," and `pitch.listStaffedFor(employeeId)` presupposes the same staffing fact — neither the spec nor the registry says how an employee comes to be "staffed" on a Pitch in the first place.

2. **No policy-table row exists for Pitch, and the class default cannot resolve for it.** `packages/schema/src/policy/policy-table.ts` has zero `MATRIX_OVERRIDES` entries for `Pitch` (bare or partitioned), so both partitions fall back entirely to `DEFAULT_CLASS_MAPPING`. That default already grants Manager and Team Member row-scoped cells for a Standard-class partition (`direct-reports` and `own-plus-team` respectively) — but `services/api/src/permission/interceptor.ts`'s `rowScopeSatisfied` only ever resolves a subject Employee for `nodeType === "Employee"` or `"BurnoutAlert"`; every other node type, Pitch included, falls to its final `else { return false; }`. So as things stand today, Manager and Team Member would get `none` on `Pitch:identifying` regardless of any staffing relationship — not the intentionally scoped access the feature's whole flow depends on, but an accidental blanket lockout that happens to look like security.

3. **The registered `Pitch→Project` conversion has no owner in F009's own spec.** `packages/schema/src/registry/conversions.ts` already carries `{sourceNodeType: "Pitch", destinationNodeType: "Project", sourceTerminalStatus: "Converted", edge: {edgeType: "originated_from", ...}}` — registered ahead of any feature that implements it, exactly like the already-registered `Candidate→Employee` conversion (owned by not-yet-built `VRS-F028`, per `VPS-A002`'s own words that "`VRS-F009` converts a Pitch into one [Project]"). `VRS-F009`'s spec document never mentions this conversion at all, so as briefed nothing would ever fire it.

**Closed — traced to F251's and F262's own precedent, no founder consultation needed.** None of the three parts is a genuine fork: each has a single, traceable answer already established by this codebase's own prior rulings.

- **Creation and staffing (part 1).** `pitch.create` follows `ghostResourceCreate`'s own `defineMutation` shape (Tier 0, `stateTransition: false`), taking the `identifying` partition's fields (`name` required, `client_id` nullable FK, `projected_start_date` nullable, `lifecycle_status` defaulted to `Active`). A new `staffed_on` edge (Employee → Pitch, owner `VRS-F009`) is modeled directly on `has_skill` (`governingPartitions: { Employee: "operational" }` — an operational HR relationship, not a Finance-restricted one, the same reasoning `has_skill`'s own F136/FDN-92 ruling already gives). `pitch.staffEmployee`/`pitch.unstaffEmployee` supply `fromNodeId`/`toNodeId` on the edge target, so F262's now-confirmed-generic `edgeRoleDecision` row-context mechanism resolves Manager's existing `Employee:operational` `Full (direct-reports)` cell correctly on the Employee endpoint — restricting Manager-initiated staffing to their own direct reports with no new capability, the same mechanism F262 already proved generic for `assignment_of`.

- **Read access (part 2).** A new `Pitch:identifying` override, styled directly on `GhostResource`'s own row (F251, Stage 15 — "extending a node type's Manager cell... is this codebase's node-type-scoped permission model... not a new gap"): Owner and HR-admin `FULL_ANY()`, Finance-admin `READ_ANY()` (consistent with `VRS-F239`'s own Pitch-time bench-forecast dependency), Manager `FULL_ANY()`. Manager is deliberately unscoped rather than row-scoped: a staffing-based row scope (checking whether any of the manager's direct reports are already staffed on the pitch) would be circular for the very first staffing action on a new pitch, since no staffing edge yet exists to satisfy the check — F251's precedent that an additive, unscoped extension of a previously-inert node type's Manager cell is not a new gap applies directly, and avoids inventing a scope this codebase has no other use for. Team Member gets an explicit `NONE_ANY()` override, not the Standard-class row-scoped default: the spec's own `pitch.listStaffedFor(employeeId)` is stated as "the only path this feature uses to reach a Pitch," and that query is gated by the caller's *existing, already-working* `Employee:operational` row-scope on the `employeeId` argument (own for Team Member, direct-reports for Manager, unscoped for Owner/HR-admin/Finance-admin) — never by a generic node-level read on `Pitch` itself. Writing `NONE_ANY()` explicitly, rather than leaving Team Member to fall through `rowScopeSatisfied`'s unresolvable-node-type default, keeps the policy table's own fidelity tests honest about what's actually intentional versus what's an artifact of an unextended mechanism. `Pitch:commercial` is left on its existing Finance-restricted class default entirely untouched — nothing in `VRS-F009` reads or writes those fields.

- **The conversion (part 3).** Scoped explicitly out of `VRS-F009`, deferred to whichever future feature first needs to convert a won Pitch into a real Project — mirroring the identical, already-established `Candidate→Employee`/`VRS-F028` precedent (registered in the schema, implemented by neither the owning node's own feature nor any feature built so far).

**Also corrects the API Contracts section as briefed.** `VRS-F009`'s spec describes `timeEntry.classifyBillable`/`classifyNonBillable`/`classifyPitch` as live mutations against a `TimesheetEntry` node — but `TimesheetEntry` (owner `VRS-F010`) has no creation mutation either; no `entryId` can exist until `VRS-F010` builds it. Read together with the spec's own words — "specified here and incorporated into `TimesheetEntry`'s schema by `VRS-F010`" — F009 is correctly scoped as delivering a reusable `time_category`/`internal_category` field-and-validation schema fragment for `VRS-F010` to incorporate into its own real mutations, not as shipping standalone `timeEntry.classify*` mutations itself. This is a spec-clarity correction, not a security gap, and needs no numbered ruling of its own; it is folded into F264's resolution since it governs the same API Contracts section.

**Status: closed.** The Stage 17 brief for `VRS-F009` proceeds on this corrected design: `pitch.create`, `staffed_on`/`staffEmployee`/`unstaffEmployee`, the new `Pitch:identifying` policy row, the classification schema fragment (not standalone mutations), and the conversion left out of scope.
