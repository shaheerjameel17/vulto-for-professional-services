### F253 — Ghost creation cannot satisfy Employee's required fields, and promotion never supplies an employee code

Raised 23 September 2026 while resuming Stage 15 (`RST-43`) on F252's ruling, before any product code was written.

**The gap.** Stage 15 Do item 1 says the Ghost's linked Employee node uses `employeeOperationalRecord`'s existing shape, with `employee_type: "Ghost"`, `job_title`, `start_date`, Active status, optional seniority/rate, and “every other field null.” `VRS-F007`'s Technical Architecture states the same rule. The helper cannot construct that record: its `EmployeeCreateFields` input requires `employee_code`, `full_name`, `email`, `job_title`, `employment_type` and `start_date`, and it always writes required `contracted_hours` (default 40). `VRS-F002`'s canonical Employee schema independently declares `employee_code`, `full_name`, `email`, `job_title`, `employment_type`, `start_date` and `contracted_hours` required for every Employee; only `employee_type` distinguishes a Ghost.

No caller value exists for four of those required facts. `ghostResource.create` accepts role title, projected start, optional seniority/skills/rate/OpenRole — no employee code, name, email, employment type or contracted hours. Synthesizing placeholders would invent human-readable identity and uniqueness facts the specification says remain null; passing null cannot typecheck through `employeeOperationalRecord` and contradicts `VRS-F002`'s schema. This is not merely a creation-time issue: Do item 4's promotion details supply full name, email, employment type and start date, but still no `employee_code`. After a successful promotion the node would have `employee_type: "Employee"` while its required workspace-unique human-readable employee code remained absent or fabricated. Non-FullTime contracted hours are also specified by `VRS-F002` G07 as prompted rather than defaulted, but promotion provides no value.

The live graph's generic node parser does not validate feature fields, so an implementation could technically persist an invalid Employee record. That would hide the contract defect rather than resolve it: downstream code and future imports are entitled to rely on `VRS-F002`'s required-field schema, and Stage 15 explicitly directs both server and optimistic client to share one canonical record constructor.

**Closed by founder-delegated decision, 23 September 2026.** A Ghost-specific record constructor, kept entirely separate from the real-Employee path Stage 8 already built and approved:

1. **A second, narrower schema and constructor pair, for Ghosts only.** `packages/schema/src/employee.ts` gains `ghostEmployeeCreateFieldsSchema` (`job_title`, `start_date` required; `seniority_level`, `billing_rate_default` optional — exactly `ghostResource.create`'s own input set, nothing else, `.strict()`) and `ghostEmployeeOperationalRecord(fields)`, returning the same record shape `employeeOperationalRecord` already returns but with `employee_type: "Ghost"`, and `employee_code`, `full_name`, `email` and `employment_type` explicitly `null` — the four genuinely unknowable identity/employment facts, matching the discriminated-schema pattern this codebase already uses elsewhere (`packages/schema/src/audit.ts`, `services/api/src/permission/principal.ts`). `employeeCreateFieldsSchema` and `employeeOperationalRecord` are untouched — Stage 8's real-Employee contract keeps its existing required fields exactly as approved.
2. **`contracted_hours` is not treated as an identity fact.** `ghostEmployeeOperationalRecord` defaults it to 40, the same default `employeeOperationalRecord` already applies when a real `employee.create` call omits it (`VRS-F002` G07's "prompted rather than defaulted" is, as built, a UI-only convention with no server-side enforcement anywhere in this codebase — Stage 15 has no UI, so it inherits exactly the same non-enforcement, not a new gap). The Bench Forecast needs a real number for a Ghost's assumed capacity; 40 is the same reasonable default a real employee gets.
3. **Promotion's contract gains `employeeCode` (required) and `contractedHours` (optional).** There is no employee-code auto-generation mechanism anywhere in this codebase — `employee.create` already requires the caller to supply it — so promotion asks for the same human decision real hiring already asks for. `contractedHours`, if given, overwrites the Ghost's current value; if omitted, the value already on the node (40 by default, or whatever it already holds) carries forward unchanged, the same "every other field untouched" principle G06 already states for Assignment/skill edges and graph history.
4. **Promotion validates uniqueness with the mutation layer's own existing helper.** `services/api/src/mutations/employee.ts` already exports `requireUnique(ctx, fields, excludeNodeId?)`, used by `employee.create` for exactly this check. Promotion calls it identically — `requireUnique(ctx, { email, employee_code: employeeCode }, employeeId)`, excluding the Ghost's own linked Employee node since this is an update to that node, not a new one — returning the same `duplicate-email`/`duplicate-code` rejections `employee.create` already returns. No new uniqueness mechanism is invented.
5. **`VRS-F007`'s "every other field null until promotion" line is corrected** to name the four fields precisely (`employee_code`, `full_name`, `email`, `employment_type`) rather than "every other field," since `contracted_hours` is not one of them. Its API contracts, Technical Architecture and Stage 15's Do items 1 and 4 are corrected to match.

**Status: closed.** Stage 15 is unblocked.
