### F217 — the ruled shell bootstrap had no authoritative active workspace to open

Raised 22 September 2026 by the Stage 9 builder (Codex, fresh session, `stage-9-shell-bootstrap`) while tracing F216's ruling against the live workspace lifecycle before writing code — another correct stop, not a routing-around. Verified directly: `services/api/src/auth/workspace-projection.ts`'s `createWorkspace` calls `createPendingWorkspaceAdmission` then `confirmWorkspaceAdmission` and returns `{ workspaceId, membershipId }`; neither function touches `session.activeOrganizationId`. A repository-wide search for writes to that field finds exactly one: `workspace-session.ts`'s revocation path, which sets it to `null`. The existing workspace-creation test calls `requireCurrentWorkspaceSession` with the new workspace id passed explicitly, never asserting the session's active organization was set — because it never is. Offline, `packages/graph/src/sync-client/database.ts` names each cache `vulto:<workspaceId>:<userId>`; `session_hint` inside one repeats that pair but nothing outside it records which cache was last opened. `device-identity.ts`'s `vulto:device` database is deliberately narrow — `assertAllowedKey` and a pinned test permit only a device id and a pending-erase list, never workspace or person state — so there is nowhere to add an active-workspace pointer without a real, reviewed contract change.

F216's ruling was incomplete on this point: it confirmed the *field* existed and is read correctly, not that anything *populates* it. That gap is on this review, not on the builder catching it.

**Ruling.** `confirmWorkspaceAdmission` (`services/api/src/auth/workspace-session.ts`) sets `session.activeOrganizationId` to the newly confirmed workspace, in the same transaction, **only when that membership is the person's sole active one** — checked the same way `revokeWorkspaceAdmission` already checks membership state, not invented fresh. A person who creates or joins a second workspace while already active in a first is **not** auto-switched; their current active organization is left alone. This covers the ordinary case (a founding Owner's first workspace, or anyone's first membership) without silently deciding workspace switching, which `docs/Reviewer_Handoff.md` already lists as undesigned and deferred.

A session with a **null** active organization is resolved by the shell bootstrap itself: if the person has exactly one active membership, open it (there is no real ambiguity, whatever cleared the field); if they have more than one, or none, the shell cannot pick, and must not guess — render whatever the minimal not-yet-a-workspace-selector state is for Stage 9 (a plain "reconnect to choose a workspace" holding state is enough; it is not F214's `Reconnect` and must not reuse that trigger or copy), not a silently wrong workspace.

Offline, the same rule: **exactly one cached workspace for the signed-in user boots from it; more than one is unresolved and requires coming online**, because there is no persisted marker to pick from and adding one to the device-identity database is a scope change this ruling does not make. This is a recorded limitation, not a defect — the same one workspace switching already carries. No change to `device-identity.ts`'s allowed-key list.

**Scope check.** This does not touch `Offline`, `Reconnect` (Stage 10), or any fixture screen. It adds one narrow write inside an existing transaction and one read-time rule at the shell boundary. `F217` closed.
