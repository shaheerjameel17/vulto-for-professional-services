### F242 — The Bench Forecast's `filters` argument has no defined schema or matching semantics

Raised 23 September 2026 while resuming Stage 13 (`RST-41`) on F241's ruling, before any product code was written.

**The gap.** F241 established `benchForecast.getAggregate(workspaceId, window, filters?)` as the authoritative server call for filtered aggregate utilization, alongside the same `filters?` parameter already present on the local `benchForecast.get`. `VRS-F005`'s Filtering section names five user-facing filter dimensions — skill, seniority, department, entity, availability window — in prose, but neither it nor the API contracts define field names, value types, empty-filter behavior, how multiple values within one dimension combine, how the five dimensions combine with each other, or what an "availability window" match actually means: at least one bench day in the window, wholly unassigned throughout it, available on its first day, or available by its end date all produce different cohorts.

**Why this cannot be worked around locally.** Passing the local query's matched employee IDs to `benchForecast.getAggregate` is not an available fix: F241 already ruled that the client cannot be a second authority for who is visible, precisely because a device choosing its own disclosure cohort is the same "client-side visibility rule" `VPS-A004` prohibits. The server must derive both the filtered cohort and the unfiltered comparison cohort itself, from the caller's own authorized base cohort — which means the server needs the same filter definition the client used to decide what the person was looking at, not a list of IDs standing in for it. Without one shared, precise contract, the local row query and the server aggregate can silently disagree on membership, and the disclosure-control comparison in F238's `applyDisclosureControl` (filtered cohort size vs. unfiltered cohort size) becomes meaningless if the two sides do not agree what "filtered" means.

**Closed by founder-delegated decision, 23 September 2026.**
1. **One filter type, five fields, AND across fields, OR within a field.** `BenchForecastFilters = { skillIds?, seniorityLevels?, departments?, entityIds?, availability?: { fromDate, toDate } }`. An employee matches the whole object only if they satisfy every field that was specified; within a field, multiple values match on any one of them (a two-skill selection means either skill). An omitted `filters` argument, or one with every field omitted, applies no narrowing — it returns the caller's full authorized cohort, the same result as viewing the forecast with nothing selected.
2. **Each field's match is grounded in an existing schema fact, not a new one.** `skillIds` matches the `has_skill` edge; `seniorityLevels` matches `Employee.seniority_level`'s already-closed enum; `departments` matches `Employee.department` by exact string equality, since the Filters row is a Select populated from the workspace's own existing values, not typed text, so no normalization question exists; `entityIds` matches the employee's currently active `scoped_to_entity` edge (this feature computes everything live at render time, per G01–G07, so a historical at-any-point-in-window reading is out of scope); `availability` matches an employee with at least one G02 bench day inside `[fromDate, toDate]` inclusive — reusing the same derivation Stage 13 Do item 3 already computes, rather than inventing a second, competing definition of "available."
3. **One shared function, called identically by both sides.** `matchesBenchForecastFilters(candidate, filters)` — pure, no I/O, taking an already-derived per-employee shape (skill IDs, seniority, department, current entity, bench-day set) and the filter object, returning a boolean — is added to `packages/schema` alongside `resolveWorkingDay` (F237) and `applyDisclosureControl` (F238). Stage 13's local row query (item 3) and `benchForecast.getAggregate` (item 4) both call it, so the rows a person sees and the cohort size behind the aggregate they see can never diverge on filter logic.
4. **The server derives both cohorts itself.** `benchForecast.getAggregate` computes the filtered cohort and the unfiltered comparison cohort directly from the caller's own authorized base cohort (a Manager's direct reports, or workspace-wide for a role with broader read, exactly as the forecast itself is already scoped) using `matchesBenchForecastFilters` against its own server-side data — never from a client-supplied employee-ID list, which is the workaround F241 already ruled out.

`VRS-F005`'s Filtering section, API contracts, a new G08 and Security Considerations are corrected to carry this contract explicitly; Stage 13 Do items 3 and 4 are corrected to name `matchesBenchForecastFilters` as their shared filter-matching function.

**Status: closed.** Stage 13 is unblocked; the local query and the server aggregate share one filter definition, so their cohorts cannot silently disagree.
