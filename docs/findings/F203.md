### F203 — the CI Postgres service cannot be started with logical replication as specified

Raised 21 September 2026 while implementing Stage 1 of the server-authoritative build.

**What the brief requires.** Postgres must run with `wal_level=logical`, `max_replication_slots=10` and `max_wal_senders=10` locally and "wherever Postgres is started" in CI, because Electric replicates from the write-ahead log (F201). Locally this is the `command` on the compose service, and it works: `SHOW wal_level` returns `logical`.

**What CI allows.** `.github/workflows/slow-lane.yml` starts Postgres in two jobs as a `services:` container. A service container is configured with `image`, `env`, `ports`, `volumes` and `options`. The `options` string is passed to `docker create` ahead of the image name, so there is no place to give the container a command or arguments. The three settings therefore cannot be supplied the way the compose file supplies them.

**What was not done in Stage 1.** No workaround was chosen: each candidate changes how CI starts its database, which is a pipeline decision. The slow lane was left as it was.

**Consequence.** None yet. No CI suite touches logical replication until Stage 6 adds the Electric-backed browser suite, and Stage 7 wires it into the slow lane, so the decision is needed before Stage 6 finishes, not before Stage 2 starts.

**Closed by founder-delegated decision, 21 September 2026.** CI gets a small Postgres image of its own, `FROM` the digest the workflows already use, whose default command carries the three flags. It is built and pinned exactly as the CI image is, and every Postgres service container then uses it. Implemented in Stage 6 item 0 of `docs/Claude_Code_Build_Prompt.md`, because no CI suite needs replication before then.
