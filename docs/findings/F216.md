### F216 — the Reconnect state had no session-aware shell call to retry

Raised 22 September 2026 by the Stage 9 builder while tracing the Reconnect brief before implementation, and correctly stopped on rather than resolved unilaterally, per the project's decision policy. Verified directly against the code, not taken on the report's word: `apps/roster-web/src/app/(shell)/layout.tsx` wraps only the fixture `Shell.tsx`, which hardcodes `workspaceName="Northgate Studio"` and `syncStatus="Synced"` as literals — not state, not a query, not a prop threaded from anywhere real. `createGraphClient` is mounted nowhere in the application except the standalone `/sync-harness` diagnostic route. `authClient.useSession()` appears only on `/auth-ready` and `/devices`, both outside the shell; `/auth-ready`'s own copy says plainly that "workspace access remains closed until the server confirms the membership projection." Every screen under `(shell)/` — Home, People, Timesheets, Foundations — renders from hardcoded fixture data (`EMPLOYEES`, a fixed viewer, a client-side `canSeeCompensation()` helper unrelated to the real interceptor). `SyncEngine.#handleRevoked` stops every source and publishes `signedOut: true` before any retry could reuse that worker, confirming the report's claim that Retry cannot be wired as a literal re-issue once `access-revoked` fires.

**This is wider than Stage 9.** It is `FDN-69` — "Deliver the shared application shell and end-to-end workspace bootstrap" — never built, sitting in Backlog since before Stage 1. Nothing in `apps/roster-web` has ever been connected to the real backend Stages 1–8 built; the whole front end is still the original design prototype. Reconnect cannot be built against a call that does not exist.

**Ruling: the contract, checked directly against what already exists rather than invented from scratch.** `services/api/src/auth/config.ts` already configures Better Auth's `organization()` plugin server-side; the session already carries `activeOrganizationId`, and `services/api/src/auth/workspace-session.ts` already clears it to `null` on revocation — `requireCurrentWorkspaceSession` already treats it as the workspace claim. The gap is client-side only: `apps/roster-web/src/lib/auth-client.ts` has no `organizationClient()` plugin, so nothing in the shell can read what the server already tracks.

1. No Better Auth session (client-side, no workspace call needed) → sign-in.
2. A session → add `organizationClient()`, read `user.id` and `session.activeOrganizationId`, construct the real graph client with those two values (the same constructor `/sync-harness` already exercises), and mount it in the shell in place of the fixture props.
3. Offline cold start with a cached `session_hint` mounts from the cache with no network call, per `VPS-A003`'s restored offline boot — this must not regress.
4. A `401`/`access-revoked` from the mounted client is surfaced to the shell as a signal; rendering it is Reconnect's job, not this stage's.
5. Retry, for Reconnect, means re-running this bootstrap from scratch — there is nothing to retry inside a client `#handleRevoked` already stopped.

**Scope, deliberately minimal.** Only the shell's own bootstrap becomes real. Home, People, Timesheets and the rest stay on fixtures; migrating them is separate, larger work, not folded into this ruling. Full text of the build brief: `docs/Claude_Code_Build_Prompt.md`, "### Stage 9 — the real shell bootstrap." The original Stage 9 (Reconnect) brief is unchanged in substance and renumbered Stage 10, now unblocked once Stage 9 lands.
