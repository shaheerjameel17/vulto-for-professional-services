### F340 — the device queries the Inbox and palette need are unreachable from the main thread

**Found while:** briefing UI-1 (`FDN-131`), 27 September 2026, by tracing the issue's "from `notificationListForUser`" and "from `searchQuery`" into the client.

`notificationListForUser`, `notificationUnreadActionCount` and `searchQuery` all take a `SyncDatabase`, which exists only inside the sync worker. The public `GraphQuery` union has four cache kinds (`node-get`, `node-list`, `edge-neighbors`, `recursive-neighbors`), and `GraphClient.query` and `subscribe` accept only that union, so no screen can call these three queries. A screen that re-derived the Inbox groups or the search ranking from `node-list` rows would duplicate the very logic Stages 23 and 25 built and tested.

**Files:** `packages/graph/src/query.ts`, `packages/graph/src/sync-client/engine.ts`, `packages/graph/src/queries/notifications.ts`, `packages/graph/src/queries/search.ts`

**Ruling.** **Closed 27 September 2026 by ruling.** Add one fifth `GraphQuery` kind, `device-query`: strict, with a closed `name` enum (`notification.listForUser`, `notification.unreadActionCount`, `search.query`) and per-name strict arguments (`search.query` takes the text and an optional limit; the other two take none). The engine runs the named function against its own database, through the same `query` and `subscribe` paths, so a subscription re-runs when the cache changes and the Inbox and the sidebar count stay live. No client-side regrouping or re-ranking, no second permission filter (the cache is the audience), and the screens never read `Notification` through `node-list`.
