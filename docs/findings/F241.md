### F241 — Bench aggregate locality contradicts VPS-A004's single-enforcement-point rule for disclosure control

Raised 23 September 2026 while resuming Stage 13 (`RST-41`) on F240's ruling, before any product code was written.

**The conflict.** `VRS-F005`'s `benchForecast.get` contract bundles `aggregateUtilization` and `cohortSize` into the same call as `rows`, with a comment claiming the whole call "resolves entirely from the device's local Electric-replicated cache. No network round-trip." Its offline acceptance criterion and the "Filter application completes within 50ms from the local graph" NFR repeat the same local claim for the filtered aggregate specifically. Stage 13 Do item 4 already computes aggregate utilization server-side and passes it through the shared `applyDisclosureControl` function (item 5) — but returns it "from `benchForecast.get`'s aggregate portion," naming no separate endpoint, so the two reviewer-authoritative documents describe the same return value as both local and server-computed.

**Why the contradiction resolves toward the server, not the local cache.** `VPS-A004`'s own "Where enforcement runs" section states the rule in terms that leave no reading: "The interceptor runs in `services/api`, and nowhere else decides access... A stream written by hand, or a client-side visibility rule, is a second answer to 'who may read this' and is prohibited." Its "Aggregate disclosure control" section names the Bench Forecast's filtered utilization by name as the reason the mechanism exists at all — "the Bench Forecast's filtered utilization percentage, which can identify an individual in a small workspace as readily as any survey result" — and one of its three differencing-protection requirements is that "sequences of aggregate queries against overlapping cohorts are recorded in `VPS-F004`'s Silent Audit Log," a server-side write no client function can perform. F238's own ruling built `applyDisclosureControl` as a generic, portable function, but portability of the function's code is not the same claim as where it is permitted to run — `VPS-A004` restricts that separately, and F238 never addressed the restriction. Stage 13 Do item 4 read `VPS-A004` correctly; `VRS-F005`'s locality claim for the aggregate, and the 50ms budget bound to "the local graph," did not.

This is the same class of correction F236 already made once in this spec: `benchForecast.get`'s bench-cost figure was pulled out into `benchForecast.getCost` because compensation data is Tier 1 and cannot resolve locally. Aggregate utilization needs the identical treatment for a Tier-0-adjacent but access-control-gated reason — the underlying `billable_percentage` rows are Tier 0 and already on-device, but the aggregate built from them is a disclosure surface `VPS-A004` requires the interceptor to gate, which a device cannot do to itself.

**Closed by founder-delegated decision, 23 September 2026.**
1. **A new named endpoint, mirroring `getCost`'s existing split.** `benchForecast.getAggregate(workspaceId, window, filters?) -> { aggregateUtilization: number | Suppressed, cohortSize: number }` is added to `VRS-F005`'s API contracts, gated by the same permission interceptor `VPS-A004` requires and calling `applyDisclosureControl` server-side. It is a single on-demand call issued after item 3's local render (bars, dates, bench-day counts), reissued whenever the filter changes, and never blocks the local render — the same non-blocking shape F236 already established for `benchForecast.getCost`.
2. **`benchForecast.get` narrows to exactly what is genuinely local.** Its return type drops `aggregateUtilization` and `cohortSize`; its comment is corrected to describe only rows/bars/dates/bench-day counts as local, matching what Stage 13 Do item 3 already (correctly) built without needing correction itself.
3. **The 50ms budget is split, not removed.** Local filter matching (which employees match skill/seniority/availability) stays bound to the existing "completes within 50ms" / "from the local graph" language, since matching rows against filter criteria is genuinely local. Aggregate recomputation for the filtered cohort is reassigned its own non-blocking, post-render budget — the acceptance criterion and NFR are corrected to name the two as separate operations rather than one local claim.
4. **Offline behavior gains one more entry.** The offline acceptance criterion and the "Fully functional offline for Tier 0 data" NFR bullet add aggregate utilization and cohort size to the list of features that require connectivity, alongside bench cost and the Contextual Intelligence Panel's Tier 2 content — the timeline's bars, bench regions and day counts remain the only guarantee.

`VRS-F005`'s API contracts, G06, the filter/offline acceptance criteria, the NFR list and Security Considerations are all corrected to name `benchForecast.getAggregate` and its server-side enforcement explicitly. Stage 13 Do item 4 needed no change to its computation — only to name the endpoint instead of attributing the result to `benchForecast.get`; item 5's `applyDisclosureControl` description is corrected to name `benchForecast.getAggregate` as its first caller instead.

**Status: closed.** Stage 13 is unblocked; the aggregate boundary now has one server-side call, one named contract, and one local contract, with nothing attributed to both.
