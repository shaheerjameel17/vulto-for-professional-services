### F304 — F302's authorized test re-export fails the repository's own architecture gate

F302 ruled that `seedProtected`'s Employee be given operational Tier 0 fields, and to that end authorized exactly two re-export lines in `services/api/src/test/sync-browser-support.ts` (`nodeRecord` from `../permission/test-support.js`, `insertNode` from `../graph/store.js`) as the single test-only exception to Stage 23's `services/api/` boundary, ruling out any change to `addNode`. Codex resumed on F303, built the partial implementation (preserved at `90ba633`, focused search, cache and Skill Matrix tests passing 24 of 24), ran `pnpm install --frozen-lockfile`, `pnpm stack:up` and `pnpm verify`, and `verify` failed at `arch:check`. `scripts/arch-check.mjs` (A003-T52) permits `graph/store` to be imported only from the graph, permission, mutations, protected, audience and jobs folders of `services/api/src`, and does not except `services/api/src/test/`; the exact line F302 authorized therefore fails the required gate twice, once as an import and once as a re-export. Codex changed neither the gate nor the fixture instruction and stopped, preserving the partial work. The reviewer had ruled the exception in without running the repository's own gate against the file it named — the same defect as F301 and F302 (a brief instruction not checked against the code path that enforces it), a fourth time.

**Closed by direct precedent — A003-T52's own gate, which already names the correct place, no founder consultation needed.** `scripts/arch-check.mjs` already allows the `permission/` folder to import `graph/store`, and its write check already recognizes `services/api/src/permission/test-support.ts` as the test-support file by name. That file's `addNode(tx, workspaceId, nodeType)` (which builds the record with `nodeRecord` and writes it with `insertNode`) is the one place a test fixture may write a node, and `services/api/src/test/sync-browser-support.ts` already re-exports it (`export { addNode, makeWorkspace } from "../permission/test-support.js"`). The ruling, in full. (1) `addNode` gains an optional fourth parameter, `fields`, defaulting to `{}`, whose entries are merged beneath `nodeRecord`'s own fields (`insertNode(tx, { ...fields, ...record })`), so it cannot override `node_id`, `node_type`, `workspace_id` or the universal provenance fields. Every existing caller (all tests, all three-argument) is unchanged by the default. (2) `services/api/src/permission/test-support.ts` is the only `services/api/` file this stage changes, and only by that parameter. (3) `services/api/src/test/sync-browser-support.ts` is restored to `main`'s version: the `nodeRecord` and `insertNode` re-export lines Codex added are removed, and no new import of `graph/store` appears anywhere outside the allowed folders. (4) `packages/graph/sync-browser-tests/helpers.ts`'s `seedProtected` calls `addNode(tx, workspaceId, "Employee", { employee_type: "Employee", full_name: SEARCH_FIXTURE_EMPLOYEE_NAME, job_title: "Search Fixture Engineer" })` instead of `insertNode(...)`, importing nothing new from the API. (5) `arch-check.mjs`, its allowlists and every other gate are unchanged; `pnpm verify` must pass on the diff as a required gate, exactly as the brief already states. This reverses F302's clause that `addNode` is not to change: that clause was written to avoid a wider effect on other tests, and a defaulted optional parameter has none, while the alternative it protected — a re-export from a non-allowed folder — is what the gate forbids. All of F301, F302's other rulings and F303 stand. Unlike F301 through F303, this ruling was checked against the gate before it was written: on a scratch copy of `main`'s `services/api/src` the reviewer ran `scripts/arch-check.mjs` and confirmed (a) `main` passes, (b) appending F302's re-export line reproduces Codex's failure, and (c) the `addNode` change above, with `sync-browser-support.ts` untouched, passes.

**Status: closed.**
