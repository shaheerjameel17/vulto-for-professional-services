### F270 — no authorized principal exists to create a Tier 2 TimesheetAnomalyFlag as a system-triggered write

Raised 24 September 2026 by Codex, resuming Stage 18 after applying F269's correction (`2cd5b03`). The Stage 18 brief requires `timesheetAnomaly.evaluate` to run as a separate named-mutation transaction immediately after every successful `timesheet.submitWeek`, creating or updating a `TimesheetAnomalyFlag` (`Manager-restricted`, Tier 2) and its `triggered_by` edge. `packages/schema/src/policy/policy-table.ts` gives a Team Member `Full (own only)` on `TimesheetEntry` but `NONE` on `TimesheetAnomalyFlag` — deliberately, per the spec's own Security Considerations: "the flagged employee does not see their own flags... visibility would let someone learn the detection thresholds by observation." `services/api/src/mutations/pipeline.ts` accepts only a `MemberPrincipal` and passes it, unchanged, to every named mutation's `authorizeWrite` call. If `timesheetAnomaly.evaluate` runs as the submitting Team Member, `authorizeWrite`'s Gate 1 refuses the flag write with `role`, correctly, since that Team Member genuinely has no grant on this node type — and it must not have one, since the entire point of the flag is that its subject cannot see or create it.

Codex checked whether the codebase's existing non-member principal kinds resolve this and confirmed neither does. `SupportPrincipal` (`services/api/src/permission/principal.ts`) is an Owner-approved, time-boxed staff grant — nothing issues one yet, and it is capped at Owner's own policy-table access, not a bypass mechanism. `SystemPrincipal` exists and is evaluated in `authorizeWrite`, but `packages/schema/src/policy/principal-policy.ts`'s `SYSTEM_PRINCIPAL_OPERATIONS` is a closed table naming exactly three operations (`audit.pseudonymize-actor`, `protected.destroy-key`, `audience.recompute`), across four named principals — none is "create a graph node." `authorizeWrite` itself gives a system-kind principal `gateRoles = []` unconditionally, so `bestCell` never returns `full` for any node type; a system principal today can write nothing through this gate. The three operations that do exist bypass this mechanism entirely, writing directly to infrastructure tables (`protected_data_keys`, the audit journal, the two audience tables) that sit outside the `graph_nodes`/`graph_edges` model `TimesheetAnomalyFlag` is part of — so none of them is actually a precedent for a system principal writing an ordinary, permission-tiered graph node.

The one apparent precedent, `services/api/src/graph/founding.ts`'s `writeFoundingRecords`, does not transfer cleanly either: it calls `insertNode`/`insertEdge` directly, bypassing `authorizeWrite` entirely, but it runs exactly once per workspace, outside any principal context at all, orchestrated by the signup flow rather than dispatched through the named-mutation pipeline `timesheetAnomaly.evaluate` is specified to use alongside `saveCell`/`submitWeek`/`listActive`/`clear`. Reusing that shape here would mean every future reactive write (and `BurnoutAlert`, `FlightRiskSignal`, `RevenueGapAlert` are all already schema-registered, all still unbuilt, all needing exactly this same mechanism) re-decides authorization from scratch outside the interceptor, rather than through one reusable, audited path. Codex correctly declined to invent or impersonate an HR Admin principal, add an unreviewed system grant on its own initiative, or write the flag outside the named-mutation path — this is a genuine architectural fork with no single answer forced by precedent, not a build-time surprise with an obvious fix, and was put to the founder rather than ruled unilaterally.

**Closed by founder-delegated decision, 24 September 2026.** `timesheet-anomaly-evaluate` is added to `SYSTEM_PRINCIPAL_NAMES` (`packages/schema/src/policy/principal-policy.ts`), permitted exactly one new `SystemOperation`, `timesheet-anomaly.create-flag`, via `SYSTEM_PRINCIPAL_OPERATIONS["timesheet-anomaly-evaluate"] = ["timesheet-anomaly.create-flag"]` — the same closed-table shape every existing system principal already uses, extended rather than replaced. `authorizeWrite` (`services/api/src/permission/interceptor.ts`) gains a distinct system-principal path at Gate 1: when `principal.kind === "system"`, the write is checked against `isSystemOperationPermitted(principal.name, ...)` for the specific node/edge type being written, not against `bestCell`'s role matrix — a system principal is still never assigned a `PolicyRole`, only ever a named, closed, per-principal operation list, exactly as `principal-policy.ts`'s own comment already states the table is meant to grow ("operations are added, with the stage that builds the job, only when the code that performs them exists"). Gate 2 (write authority/app scoping) and Gate 3 (protected-record readability) are unaffected — `TimesheetAnomalyFlag` is Tier 2 with no registered subject exclusion, so Gate 3 does not apply to this write regardless of principal kind. Audit already renders a system actor correctly (`actor_kind: "system" as const` is already handled in the audit writer; no change needed there). `timesheetAnomaly.evaluate` constructs and passes `{ kind: "system", name: "timesheet-anomaly-evaluate", workspaceId }` — never the submitting Team Member's own `MemberPrincipal` — specifically for the flag-and-edge write, inside the same transaction as the write itself. Every other Stage 18 operation (`saveCell`, `submitWeek`, `unlockWeek`, `timesheetAnomaly.listActive`, `timesheetAnomaly.clear`) continues to run under the calling member's own principal exactly as already specified; this ruling concerns only the one reactive create.

**Status: closed.**
