### F255 — `Assignment.manager` is scoped to `READ_ANY()`, contradicting `VPS-A004`'s own Permission Matrix

Raised 24 September 2026 checking `VRS-F008` directly against the code before writing the Stage 16 brief, since the feature's override gate assumes a Manager can already write Assignment.

**The gap.** `VPS-A004`'s own authoritative Permission Matrix table states `Assignment | Full | Full | Read | Full | Read` for Owner, HR Admin, Finance Admin, Manager and Team Member in that order — an unscoped Full for Manager. But `packages/schema/src/policy/policy-table.ts`'s `MATRIX_OVERRIDES` declares `Assignment.manager: READ_ANY()`. `git blame` isolates that single line to Stage 13's `f2d928d` (23 September 2026); every other line in the same `Assignment` block — `owner`, `hr-admin`, `finance-admin`, `team-member` — traces to the original interceptor bootstrap commit `67ad2c1c` (21 September 2026). Stage 13's own brief and completion report never claimed to narrow Assignment's Manager row, and no finding raised during Stage 13 discusses it; this is an unreviewed regression against the suite's own table, caught only now because `VRS-F008` is the first feature to actually exercise a Manager write to Assignment. Under the shipped code, a Manager cannot call `assignment.create`, `assignment.update`, or any new Stage 16 mutation — `conflictResolution.overrideAndProceed` included — because the interceptor refuses the write before the feature's own authorization check (caller must be the employee's manager or an Owner) ever runs.

**Closed by founder-delegated decision, 24 September 2026.** `packages/schema/src/policy/policy-table.ts`'s `Assignment.manager` cell is corrected from `READ_ANY()` to `FULL_ANY()`, matching `VPS-A004`'s table exactly — unscoped Full, not a `direct-reports`-scoped `cell(...)` entry, since the table specifies no such scoping for this row. No other cell in the `Assignment` block changes. This is a one-line code fix, a Do item for Codex rather than a documentation-only correction, since `VPS-A004`'s table was already correct and the code is what drifted from it.

**Status: closed.**
