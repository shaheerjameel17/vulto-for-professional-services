### F273 — a zero-entry week's submission leaves no state to distinguish it from Not-Started

Raised 24 September 2026 by Codex, resuming Stage 18 after merging F272's ruling, tracing the submission and week-query contracts before writing any mutation code. The Stage 18 brief's own Do item 5 requires `submitWeek` not to error on zero Draft entries — an empty week can genuinely be submitted, per the spec's own Empty state note that a person between assignments should be able to confirm they have nothing to log rather than being blocked. But `timesheet.getWeek`'s contract requires `weekStatus: 'Draft' | 'Submitted'`, and `hrCompliance.listSubmissionStatus` must report Draft, Submitted or Not-Started per employee per week — the entire point of the compliance view being to chase the people who haven't looked at their timesheet, not the people who correctly confirmed there was nothing to log. The only specified persisted submission state is `TimesheetEntry.lifecycle_status`/`submitted_at`, both per-entry fields. When there are zero entries, `submitWeek`'s transaction changes no rows at all, so the graph looks identical before and after the empty submission — there is nothing left to query.

Codex checked whether any other persisted write could serve as this record and found none. `graph_mutations` (`services/api/src/graph/schema.ts`) was confirmed directly: it is an idempotency log (A003-T53) keyed by client `mutation_id`, storing `args_sha256` — a hash, not queryable fields — with no index beyond `(workspace_id, created_at)`; its own comment states it is "never replicated," meaning it is infrastructure for safe retry, not a business-status store any read path is meant to query. Codex correctly declined the two workarounds that would have papered over this rather than fixed it: a synthetic zero-hour `TimesheetEntry` (new, unreviewed data semantics — every future reader of TimesheetEntry, including the anomaly detectors, would need to learn to ignore a fake row) or a new bespoke status table outside the graph model (would bypass the interceptor's permission checks entirely, the one thing every other piece of business data in this system goes through). Rather than invent either unilaterally, Codex stopped and reported it.

This traces directly to a precedent already sitting in the registry, unbuilt but exactly on point: `PolicyAcknowledgment` (`packages/schema/src/registry/nodes.ts`, owner `VRS-F044`) is a real, already-registered `fixedProtection("Standard", 0)` node whose entire purpose is recording that an Employee took a confirming action, with nothing richer to say about it — precisely the shape this problem needs. `VPS-A002`'s own Decisions Recorded section already treats adding a node type as routine registry growth ("twenty-four node types are added... each classified against the same tier-splitting rule already established"), and `VRS-F010` itself already registers two node types of its own; a third, equally narrow, feature-owned node type is not a new kind of decision for this project. The alternative shape — a bespoke infrastructure table like `graph_mutations` — was rejected because it would require reinventing permission-checking outside the interceptor for genuinely business-facing content (who may know an employee's week was submitted is exactly as sensitive as who may see the entries themselves), a real regression in consistency with no offsetting benefit.

**Closed, traced directly to `PolicyAcknowledgment`'s own registered precedent — no founder consultation needed.** A new node, `TimesheetWeekSubmission` (owner `VRS-F010`, `fixedProtection("Standard", 0)` — the same tier as `TimesheetEntry` and as `PolicyAcknowledgment` itself), carries `employee_id` (UUID, a direct field, G04's own precedent — this node is Tier 0 exactly like `TimesheetEntry`, so a field is the right mechanism, not an edge), `week_start_date` and `submitted_at`, plus the standard universal envelope. `submitWeek.apply()` creates exactly one such row, in the same transaction as the (empty) entry transition, only when the Draft-entry read for `(employee_id, week_start_date)` comes back with zero rows — the ordinary non-empty case is completely unchanged, since `TimesheetEntry.lifecycle_status` already carries status correctly whenever entries exist. `unlockWeek.apply()` soft-deletes the marker for a zero-entry week, mirroring the reverse transition already specified for entries. `rowScopeSatisfied`'s existing `TimesheetEntry` branch (F268/F269) extends its condition to include `TimesheetWeekSubmission`, reading `employee_id` the identical way — no new resolution mechanism. `packages/schema/src/policy/policy-table.ts` gives `TimesheetWeekSubmission` the identical `MATRIX_OVERRIDES` row `TimesheetEntry` already has (owner/HR Admin Full, Finance-admin Read, Manager Read direct-reports, Team Member Full own) — the same audience, since knowing a week was formally submitted is no more sensitive than seeing the entries themselves. `getWeek` and `hrCompliance.listSubmissionStatus` resolve status by checking `TimesheetEntry` rows first (unchanged) and falling back to a live `TimesheetWeekSubmission` marker only when none exist: present means Submitted, absent means Not-Started — `getWeek`'s own two-value contract folds Not-Started into Draft for a single employee's own view, since an untouched grid looks identical either way; `hrCompliance`'s three-value contract reports Not-Started distinctly, which is the entire reason this fix exists. `docs/Vulto_Specs/VRS-F010_Timesheet_Speed-Run.md` and `docs/Vulto_Specs/VPS-A002_Master_Graph_Schema_Definition.md`'s node type registry are corrected to register the new node. `docs/Claude_Code_Build_Prompt.md`'s Stage 18 section and `docs/Reviewer_Handoff.md`'s section 19 are corrected to match.

**Status: closed.**
