### F218 — cold offline boot conflicts with the unconditional no-session redirect

Raised 22 September 2026 by the third Stage 9 builder on `stage-9-shell-bootstrap-v2`, before implementation. The revised Stage 9 brief says that `authClient.useSession()` resolving with no data once `isPending` clears is unconditionally “sign in,” and that this is checked first with zero workspace calls. The same brief requires a fresh offline load to enumerate `session_hint` caches and mount when exactly one eligible workspace exists.

The pinned Better Auth 1.6.29 client initializes its session atom with `data: null` and `isPending: true` (`dist/client/session-atom.mjs`). When `/get-session` fails on a cold offline load, its catch path leaves `data: null`, records the error, and sets `isPending: false` (lines 94–103). Thus the specified redirect condition is true for the required offline-boot case. A real no-session response and a network failure differ by the error field, but the brief expressly says no data after pending clears unconditionally redirects. Making an exception for errors, or selecting an IndexedDB identity when the live session is unavailable, is a behavioral and security decision rather than a private implementation detail. `session_hint` contains workspace and user IDs, but it is not an authenticated session.

**Ruling — closed 22 September 2026.** Checked directly against the pinned client, not just the report. `session-atom.mjs` has two distinct error paths, not one. When `$fetch` returns normally (the request reached the server, whatever it answered — a clean no-session response, a 401, a 5xx), `error` is either `null` or a `BetterFetchError` (`@better-fetch/fetch`'s own error class, which always carries a numeric `status`). When the fetch itself throws before any response — network unreachable — the `catch (fetchError)` branch sets `data: latest.data` (`null` on a cold boot) and `error: fetchError`, whatever the underlying fetch implementation threw (a `TypeError`, an abort `DOMException`); this is never a `BetterFetchError` and never carries a numeric `.status`. The two are reliably distinguishable: `error` present without a numeric `.status` means the server was never reached. This mirrors a split the sync engine already makes for the identical reason — `packages/graph/src/sync-client/engine.ts`'s `#onFailure` treats `failure.kind === "network"` (offline; retried with backoff) differently from `"unauthenticated"` (session lapsed; no retry) — so the fix reuses an established shape rather than inventing one.

The sign-in redirect (Stage 9 point 1) now fires only on a confirmed answer: `data` null and `error` either `null` or carrying a numeric `.status`. An `error` present without one is indeterminate, not a confirmed absence of session, and falls through to the offline cache-boot path (point 4) instead. Point 4 needed one addition the original wording didn't anticipate: when point 1 couldn't resolve at all, there is no `user.id` to filter cached workspaces by (Better Auth never answered), so the shell enumerates every `vulto:<workspaceId>:<userId>` cache on the device via `listIdbDatabases()`, unfiltered — exactly one across the whole device mounts from its `session_hint`; more than one, whether that is one person's two workspaces or two people sharing the device, is the same unresolved-selection case F217 already established and requires coming online. No new identity mechanism is introduced, and `device-identity.ts`'s deliberately narrow allowed-key list is not reopened. `apps/roster-web/src/app/(shell)/` (Part 3, Stage 9, points 1 and 4) and this file are updated in the same pass; `VPS-A003` and `VPS-F001` need no wording change — both already describe the offline-boot and sign-in behaviors this ruling reconciles, not new ones.
