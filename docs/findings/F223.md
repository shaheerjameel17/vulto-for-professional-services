### F223 — Entity deactivation has no defined state transition or base version

Raised 22 September 2026 while tracing the Stage 11 brief before implementation (RST-39). The brief instructs the builder to add `entity.deactivate(entityId)` and enforce the separate G04 and G05 refusals. `VRS-F003` gives exactly that API signature. Its Entity schema has both `is_active: boolean` and `lifecycle_status: Active | Dissolved`, but it does not define whether deactivation sets `is_active` to false, moves the lifecycle to `Dissolved`, or does both. Those choices lead to different definitions of the “remaining Active Entity” counted by G04, and different behavior for later reads and updates.

There is a separate contract conflict in the same operation. `VPS-A003`'s Conflict resolution section and A003-T54 require every state-transition mutation to carry the base `version` on which the decision was made, rejecting a changed version with `stale-state`. The Stage 4 brief implemented that rule for `graph.transitionLifecycle` through required `expected_version`, and Stage 8's `employee.transitionStatus` follows it. Deactivation is a change from active to inactive or dissolved, yet neither Stage 11's brief nor `VRS-F003` gives `entity.deactivate` a version argument or an exception to A003-T54. Marking it `stateTransition: false` or silently using the current database version would evade the existing concurrency rule; adding a required argument would change the stated API contract. Neither choice is authorized by the brief.

**Ruling — closed 22 September 2026.** `is_active` is dropped from Entity's schema. It was never anything but a leftover: every other `fixedLifecycle`-registered node type (`WorkingCalendar`, `Holiday`, `WorkingPattern`, all owned by `VRS-F004`) carries `lifecycle_status` alone in its own schema block, with no separate boolean — confirmed directly against their spec text and against `packages/schema/src/registry/nodes.ts`. `is_active` is the convention `featureOwnedLifecycle` node types use instead (`VRS-F018`'s LeavePolicy, `VRS-F006`'s RateCard, `VPS-F010`'s CustomFieldDefinition — each registered `lifecycle: featureOwnedLifecycle` and each carries `is_active` with no `lifecycle_status` field of its own). Entity is registered `lifecycle: fixedLifecycle("Active", "Dissolved")` — the platform-fixed pattern, not the feature-owned one — so its spec text carrying both fields was simply never cleaned up when it was standardized onto `fixedLifecycle`. `VRS-F003`'s schema is corrected to drop `is_active` entirely; deactivation transitions `lifecycle_status` from `Active` to `Dissolved`, and G04/G05's "remaining Active Entity" / "Active scoped employees" language refers to `lifecycle_status = "Active"`, nothing else.

The version gap is resolved the same way `VRS-F002` resolved it for Employee, not by inventing a new rule. `graph.transitionLifecycle` already implements A003-T54 generically for any `fixedLifecycle` node — it writes `lifecycle_status` through `updateNodeFields`'s own `expected_version` check — but it refuses any node type in `FEATURE_LIFECYCLE_NODE_TYPES` (currently only `Employee`) precisely because a feature-specific transition needs business-rule checks the generic mutation cannot express. `entity.deactivate` needs exactly that: G04 and G05 are business rules, not a bare state flip. `Entity` joins `FEATURE_LIFECYCLE_NODE_TYPES` alongside `Employee`, and `entity.deactivate`'s API contract gains the argument its sibling `employee.transitionStatus` already has: `entity.deactivate(entityId, expectedVersion) -> { success }`. Its `validate()` checks `expected_version` against the current row first (`stale-state`, A003-T54, exactly `employeeTransitionStatus`'s own first check), then G04 and G05 as the two distinct business refusals already briefed; `apply()` writes `lifecycle_status: "Dissolved"` through `updateNodeFields` under the checked version, the same call `transitionLifecycle` and `employeeTransitionStatus` both make. `VRS-F003` and the Stage 11 brief are both corrected to match.

**Status: closed.** `packages/schema/src/mutations/employee.ts`'s `FEATURE_LIFECYCLE_NODE_TYPES` gains `"Entity"`; the new `packages/schema/src/mutations/entity.ts` and its `services/api` implementation carry the corrected signature from the start. Stage 11 is unblocked.
