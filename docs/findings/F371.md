### F371 — the 14-day historical lead-in 500s whenever a date it queries precedes the employee's own `start_date`; the fix is `computeBenchStatus`'s own existing clamp, extended to the two call sites that never got it

**Found while:** Codex's UI-3 implementation trace, real-browser run against a freshly created workspace/Entity, after F370's fixture ruling unblocked seeding. `getBenchForecastAggregate` and `getBenchForecastCosts` both returned HTTP 500; the aggregate's error was `Error: not-found` inside `resolvedDayOn` (`services/api/src/graph/working-days.ts`), for a date in the 14-day historical lead-in that preceded the just-created Entity's first `WorkingCalendar`. Codex asked for a product ruling on how pre-existence historical days should be interpreted, since VRS-F005 never specifies it and the same defect "can affect a real new workspace." Independently traced before ruling against `services/api/src/graph/working-days.ts::resolvedDayOn`, `calendar-resolution.ts::resolveCalendarForEntity`, `entity-resolution.ts::resolveEntityAssignment`, and every caller of `resolvedDayOn`/`benchDaysForWindow` inside `services/api/src/permission/bench-forecast-queries.ts`.

**The actual shape of the bug is broader than "a brand-new workspace's first two weeks."** `resolveEntityAssignment(..., at)` returns `null` whenever no `scoped_to_entity` edge covers the requested instant — which is exactly as true for a date before *any* employee's own hire as it is for a date before a freshly created Entity's first calendar. `resolveCalendarForEntity` returns `null` for the same reason on the calendar side. `resolvedDayOn` turns either `null` into `throw new Error("not-found")` — deliberately, since the same throw also covers a genuine permission denial (`mayRead` failing), which must keep failing closed. Three call sites in `bench-forecast-queries.ts` iterate a caller-supplied date range and call `resolvedDayOn` (directly, or via the shared `benchDaysForWindow`) for every date in it, with no guard: `cohortEmployee`'s call into `benchDaysForWindow` (feeds every Forecast row), `utilizationTotals` (feeds `getBenchForecastAggregate`), and `getBenchForecastCosts`'s own per-region loop (F367). Any of the three throws, uncaught, the instant the iterated range includes one date before the employee had a `scoped_to_entity` edge in force — which happens not only in a fresh workspace, but for any ordinarily recently hired employee viewed within 14 days of their start, in any workspace of any age. This is a live-production correctness gap, not a fixture-only curiosity.

**This exact problem is already solved, in the same file, for a different caller.** `computeBenchStatus` (F012/Revenue Gap Alert's consumer of `benchDaysForWindow`) already refuses to ask for a bench day before the employee existed: `const fromDate = latestEnded ? addIsoDays(...) : String(employee.record["start_date"] ?? asOfDate); if (fromDate > asOfDate) return { benchDays: [], benchStartDate: null };`. It never lets the shared date-range loop see a date earlier than the employee's own `start_date` (a required, always-populated `isoDate` field on every `Employee`, per `packages/schema/src/employee.ts`). `cohortEmployee`, `utilizationTotals`, and `getBenchForecastCosts` simply never received the equivalent clamp when they were built — an omission, not a considered difference in semantics; nothing in VRS-F005 or any finding says a lead-in day before hire should be treated differently for the Forecast screen than for the alert that shares its own bench-day math.

**Why this doesn't need a founder ruling.** The 14-day lead-in's own stated purpose (`VRS-F005`: "the lead-in gives an assignment already in progress enough context to remain legible") is presentational continuity for an assignment that predates the visible window — it is not a claim that every historical day, including ones before the employee existed, must resolve to a real calendar answer. A day before an employee's `start_date` cannot be a bench day (they were not yet staffable) and cannot carry an unrecovered-cost figure (there is no employment to cost) under any reading of the spec; excluding it is not a new interpretation, it is the interpretation `computeBenchStatus` already embodies and this project already ships for F012. The local `bench-forecast.ts` device query is consistent in spirit: `packages/graph/src/queries/bench-forecast.ts` resolves the employee's *current* calendar and projects it across the full lead-in window rather than doing point-in-time historical resolution at all, which is why the local Forecast rendered without error in Codex's browser run — it never encounters this failure mode because it never asks "did a calendar exist back then." The protected, compensation-bearing server calls (F236/F367) are held to the interceptor's stricter historical-accuracy standard, and the correct way to reconcile the two is to make the protected calls stop asking a question that has no legitimate answer for those dates, not to relax the interceptor or backdate calendar data.

**Ruling. Closed 29 September 2026, mechanical extension of `computeBenchStatus`'s own existing clamp to its two sibling call sites, no founder ruling needed.** A historical lead-in date earlier than the employee's own `start_date` is excluded from both bench-day derivation and cost/utilization accumulation — it contributes nothing, is never a bench day, and is never costed — exactly as `computeBenchStatus` already treats it for F012. Concretely: `benchDaysForWindow` clamps its own iterated range's start to `employee.start_date` internally (a single fix point, since `computeBenchStatus`'s existing external clamp becomes redundant-but-harmless once this lands, and `cohortEmployee` is automatically covered without its own change); `utilizationTotals` and `getBenchForecastCosts` each skip (not error on) any iterated date earlier than the employee's own `start_date`, the same way they already skip a date covered by an assignment or excluded as a Pitch day. `resolvedDayOn`/`resolveCalendarForEntity`/`resolveEntityAssignment` — `working-days.ts`'s and `entity-resolution.ts`'s shared G08 primitives, used well beyond Bench Forecast — are not touched; their `throw new Error("not-found")` for a genuine permission denial or a genuinely missing calendar on an otherwise-existing employee/date is unchanged, since this ruling narrows only the caller-side date range these three Bench Forecast functions ever ask the primitive about. This is additive, scoped entirely to `services/api/src/permission/bench-forecast-queries.ts`, and extends an already-shipped, already-accepted pattern rather than inventing new semantics.

**Status: closed** (mechanical extension of existing precedent, folded into the corrected UI-3 brief/implementation).
