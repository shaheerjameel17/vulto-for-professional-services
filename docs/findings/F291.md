### F291 — generic edge writes can bypass `has_skill`/`requires_skill`'s own business rules

Raised 25 September 2026, alongside F290, while Codex traced the write paths F289's fix had just made functional. `has_skill` and `requires_skill` each gained feature-owned business rules this stage that the interceptor's ordinary endpoint-permission check does not, and was never meant to, enforce: F287's `employee.attachSkill` derives `verified`/`verified_by`/`verified_at` from the caller/target relationship, never accepting them as caller-supplied — "a self-attestation of 'verified' would defeat the field's own purpose," F287's own words — and G03 requires at most one active edge per Employee/Skill (or Project/Skill) pair, replacing rather than duplicating. But `graph.createEdge` and the new `graph.updateEdgeMetadata` (F289) are ordinary entries in the `MUTATIONS` registry, reachable by any authorized caller through the single generic `graph.applyMutations` router procedure (`services/api/src/router.ts`) — the same shared write pipeline `graph.applyMutations` has been since F266 established it as the standard path, not a per-mutation router entry. Both mutations' `validate()` was literally `nothing`: no check exists that a caller with `has_skill`/`requires_skill` write authority under `edgeRoleDecision` must go through the named mutation rather than the generic one. An authorized caller could therefore create a `has_skill` edge with `verified: true` self-attested, or a second active edge for the same pair, entirely outside `employee.attachSkill`/`project.attachSkillRequirement`.

This is not a new class of problem: `FEATURE_LIFECYCLE_NODE_TYPES` already exists to solve the identical shape for nodes — `graph.createNode`, `graph.updateNodeFields`, `graph.softDeleteNode` and `graph.transitionLifecycle` all check `FEATURE_LIFECYCLE_NODE_TYPES.has(nodeType)` in their own `validate()` and reject a listed type with `MutationRejection("requires-feature-mutation")` (`services/api/src/mutations/foundation.ts`), precisely so a type whose feature owns real business rules cannot be generically written around them. No edge-side counterpart had ever been built, because no edge type had needed one until `has_skill`/`requires_skill` gained rules this stage.

**Closed by direct precedent, 25 September 2026.** No founder consultation needed — the mechanism, the rejection reason, and the reasoning all already exist for nodes; this extends them to their obvious second consumer. A new `FEATURE_OWNED_EDGE_TYPES: ReadonlySet<string>` (`packages/schema/src/mutations/employee.ts`, alongside `FEATURE_LIFECYCLE_NODE_TYPES`, same export surface): `new Set(["has_skill", "requires_skill"])`. `createEdgeMutation.validate()` and `updateEdgeMetadataMutation.validate()` gain the identical `FEATURE_OWNED_EDGE_TYPES.has(edgeType)` check, reusing `MutationRejection("requires-feature-mutation")` verbatim; `closeEdgeMutation` gains it too, for symmetry, though this stage never closes either edge type. The block is edge-type-wide, matching `FEATURE_LIFECYCLE_NODE_TYPES`'s own granularity, not pair-scoped — `requires_skill`'s four still-unowned pairings (Pitch, OpenRole, CareerMilestone, Requisition) are blocked from generic writes too, which is an accepted, explicitly recorded forward dependency (no feature currently writes them) rather than a regression. F285's own "genuinely exercised by a real write" proof requirement is corrected in the same ruling: since the full generic `graph.createEdge` path is now correctly closed for `requires_skill` entirely, that proof moves to an `edgeRoleDecision`/`insertEdge`-level test — the same style `store.integration.test.ts` already uses to test `insertEdge` directly — rather than a real write through the now-blocked generic path.

**Status: closed.**
