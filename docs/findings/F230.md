### F230 — a superseding calendar has no defined relationship to existing holidays

`VRS-F004` says a WorkingCalendar defines an Entity's working week *and holiday set*, and G01 requires `calendar.update` to create a new WorkingCalendar node while the old one remains for history. Holiday has `calendar_id` and the registered `holiday_in` edge to one WorkingCalendar. After an update, every existing Holiday still points to the old calendar. Neither the spec nor Stage 12 says whether the new version copies those holidays, adds new edges to them, inherits them by traversing `supersedes`, or starts without them. The options produce different `workingDays.*` answers after an ordinary working-week edit and different historical results if a provisional holiday is later confirmed. Moving a Holiday to the new calendar may also erase the old version's holiday history; copying may duplicate the holiday and its confirmation state.

**Ruling — closed 22 September 2026.** `VRS-F004` already gives the reason a `WorkingCalendar` version exists at all: "so that a period computed under the previous working week stays correct" (G01). That reasoning applies identically to the holiday set a calendar defines — a period computed under the previous calendar's holidays must also stay correct, so holidays are versioned the same way the calendar itself is, rather than left ambiguous. `calendar.update` copies forward every currently-`Active` `Holiday` (never a `Canceled` one) belonging to the calendar version being superseded, writing a new `Holiday` node with identical fields (`name`, `date`, `holiday_type`, `applies_to_locations`, `is_provisional`, `estimated_date`, `confirmation_window_days`, `confirmed_at`, `confirmed_by`, `is_half_day`) and a new `holiday_in` edge to the new calendar version, in the same transaction as the calendar write itself. The old calendar version's own original `Holiday` nodes and edges are untouched — a query against the old, now-`Superseded` version (via `calendar.get(entityId, asOf)`) sees exactly the holiday set that was true at that time, forever. `holiday.confirm`/`holiday.cancel` operate on the *current Active* calendar's own holidays only — `validate()` refuses (`not-found`) a holiday belonging to a `Superseded` calendar version, since a historical holiday set is frozen the same way historical working weeks are. `VRS-F004`'s G01/G05 and `calendar.update`'s Do item are corrected to state this copy-forward explicitly.

**Status: closed.** Stage 12 is unblocked on this point.
