### F256 — `validateCapacity` aggregates calendar days, contradicting `VRS-F008`'s own G02 and its "reused, not reimplemented" claim

Raised 24 September 2026 checking `VRS-F005`'s existing hard constraint against `VRS-F008`'s Technical Architecture section before writing the Stage 16 brief.

**The gap.** `VRS-F008`'s Technical Architecture section states the conflict computation is "exactly the aggregation [[VRS-F005]]'s constraint already performs, reused rather than reimplemented," and G02 requires "Overlap is measured in working days per [[VRS-F004]]. Assignments sharing only non-working days do not conflict." But `services/api/src/mutations/assignment.ts`'s existing `validateCapacity` — called from both `assignmentCreate` and `assignmentUpdate` — aggregates via `eachDate(from, to)`, a plain calendar-day iterator with no reference to `VRS-F004`'s calendar, holidays or patterns at all; it walks every calendar day from `startDate` to `endDate` inclusive. Reusing this function unmodified for the new `conflictCheck.evaluate`, exactly as the spec's own words direct, would carry calendar-day aggregation straight into new code G02 explicitly forbids: two assignments overlapping only on a weekend or public holiday would register a false conflict or an inflated combined total.

**Closed by founder-delegated decision, 24 September 2026.** Extended, not replaced, on F237/G08's own precedent. `resolveWorkingDay` (`packages/schema/src/working-day.ts`, F237's pure, portable implementation) and `resolvedDayOn` (`services/api/src/graph/working-days.ts`, G08's tx-aware wrapper) are already the one established mechanism for this exact resolution, currently called only from `services/api/src/permission/bench-forecast-queries.ts`'s three read-query call sites, each behind a `readGuard`. `validateCapacity`'s date loop gains a working-day filter through this same mechanism, using the mutation's own already-granted `tx`/`principal` context in place of a query module's `readGuard`, at both of its existing call sites — a genuine, small behavior correction to already-shipped `VRS-F005` code, not new code. `VRS-F005`'s own spec gains a one-line note recording the working-day filter. The new `conflictCheck.evaluate` read query and `conflictResolution.sweepOvercommitted` reuse the now-corrected `validateCapacity` (or a shared aggregation helper extracted from it) directly rather than reimplementing the overlap sum a second time, making "reused, not reimplemented" true of the shipped code rather than only of the prose.

**Status: closed.**
