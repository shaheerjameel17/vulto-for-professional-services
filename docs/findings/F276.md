### F276 — week-start key is not derivable for every permitted working-week shape

Raised 24 September 2026 by Codex, who implemented F275's endpoint-authority mechanism (committed at `d98c5d1`, verified 5/5 against the real interceptor including Assignment access, Pitch denial, staffing, unstaffing and restaffing) and then traced `saveCell`'s own required `week_start_date` derivation before writing it, and stopped an eighth time. `VRS-F010` G05 requires `week_start_date` to be the employee's "first working day of the week," so a Sunday-to-Thursday workspace does not get split across two Monday-anchored records — the exact bug a hardcoded Monday anchor would have caused. But `VRS-F004`'s `working_week` schema (`packages/schema/src/mutations/calendar.ts`'s `workingWeekSchema`) accepts any arrangement of seven booleans, not only a contiguous block: a genuine seven-day working week has no rest gap to identify a first day from, and a split pattern (Sunday, Monday, Wednesday, Friday, say) has several candidates for "first working day after a rest day." Worse, `resolveWorkingDay` folds holidays into whether a day counts as working, so even an ordinary contiguous week's key could have silently shifted depending on which day a holiday landed on — changing which entries `submitWeek` locks together and which marker a later compliance query finds. No `week_start_day` or equivalent field existed anywhere in the schema. Codex correctly declined to invent a hidden Monday default or a longest-gap heuristic and stopped rather than choose unilaterally; the incomplete `timesheet` mutation-schema draft was removed rather than left as a stub.

This was put directly to the founder: no existing concept in this codebase ever defined which day begins a week, since nothing before `VRS-F010` needed one, and three materially different domain choices existed with no precedent picking one. A deterministic rest-gap rule with a tie-break was considered and rejected: it stays sensitive to ordinary `pattern.set` edits and to holiday placement, reintroducing the exact instability `week_start_date` exists to prevent — the founder noted this is, if anything, *more* exposed to drift than a calendar-level anchor, since a `pattern.set` edit (routine, per-employee) is far more frequent than a `calendar.update` (Owner/HR-Admin-only, entity-wide, rare). Restricting which schedules are permitted (requiring a contiguous working block) was rejected outright: it would break the three-day-a-week and split-pattern employees `VRS-F004` already explicitly names as real, intended cases, not edge cases to design away.

The founder's first-pass recommendation — a new, explicit `week_start_day` field on `WorkingCalendar`, versioned identically to `working_week` — was then tested against a second, harder question: does resolving that field per entry (via each entry's own date) stay stable if the governing calendar or the employee's entity assignment changes mid-week? It does not, in one narrow case: a `calendar.update` that changes `week_start_day`, or an entity re-scoping, landing mid-week can legitimately split one real week's entries across two `week_start_date` values, since `resolveCalendarForEntity`/`resolveForEmployee` each resolve strictly as of the entry's own date. Rather than build a guard for this (which would require `VRS-F004`'s mutations to read `VRS-F010`'s `TimesheetEntry` table — the identical cross-feature coupling `VRS-F004`'s own G08 already forbids in the other direction), the founder chose to name it explicitly as an accepted, inherent limitation of any anchor-based design, rather than let a future stage rediscover it as an unnoticed bug.

**Closed by founder-delegated decision, 24 September 2026.** `WorkingCalendar` gains a new required field, `week_start_day` (ISO weekday 1–7), versioned exactly as `working_week`/`standard_daily_hours` already are — `calendar.update` supersedes it the same way, and the already-existing `resolveCalendarForEntity(tx, workspaceId, entityId, asOf)` already resolves the calendar version in force as of any date, so no new resolution mechanism was built. A new pure function in `packages/schema/src/working-day.ts`, alongside `resolveWorkingDay`/`addIsoDays`/`isoDatesInclusive` (F237's own "one portable implementation" precedent), walks backward from a date to the most recent date whose ISO weekday equals `week_start_day` — consulting no working-day, holiday or pattern state at all. `saveCell`/`submitWeek` resolve the employee's Entity via the existing `resolveForEmployee`, that Entity's calendar version via the existing `resolveCalendarForEntity`, then compute `week_start_date` once and store it on the row — never recomputed on a later read, the same stability `VRS-F004`'s F230 already established for a historical working week. Defaults are set per jurisdiction to match `initialWorkingWeekFor`'s existing contiguous defaults (Monday for PK/Global/UK/US/IN/SG, Sunday for AE/SA), so every existing calendar's behavior is unchanged; a manually edited calendar carries `week_start_day` as an explicit required input, never a derived heuristic. `entity.create`'s optimistic handler must carry `week_start_day` in its locally-computed calendar object from the same shared `initialWorkingWeekFor` template logic (F233's own online/offline parity precedent), so an offline-created calendar does not diverge from the server-created one on this field. `docs/Vulto_Specs/VRS-F004_Working_Calendar_and_Working_Patterns.md`'s WorkingCalendar field listing and Decisions Recorded section, and `docs/Vulto_Specs/VRS-F010_Timesheet_Speed-Run.md`'s TimesheetEntry field listing and Decisions Recorded section, are corrected to match; `docs/Claude_Code_Build_Prompt.md`'s Stage 18 section and `docs/Reviewer_Handoff.md`'s section 19 are corrected to match.

**Status: closed.**
