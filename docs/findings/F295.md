### F295 — `hrCompliance.listSubmissionStatus` has carried the identical exposure since Stage 18, independent of F292

Verifying F294's fix directly against every other query that authorizes against `Employee:operational` before disclosing something about that Employee (the same check applied to `pitch-queries.ts` and `conflict-resolution-queries.ts`, per standing practice — not merely trusting the Stage 21 report's own two-query diagnosis) surfaced a third: `services/api/src/permission/timesheet-queries.ts::listSubmissionStatus` (the `hrCompliance.listSubmissionStatus` router procedure) filters its candidate Employee list through the same `Employee:operational` `filterReadable` call, then discloses each admitted Employee's weekly timesheet submission status — `Draft`/`Submitted`/`Not-Started`, an HR-compliance signal.

But this query's own governing row was registered by F273 (Stage 18) with a *narrower* scope than `Employee:operational` has ever had, even before F292: `packages/schema/src/policy/policy-table.ts`'s `TimesheetEntry` and `TimesheetWeekSubmission` rows both give Manager `Read (direct reports)` and Team Member `Full (own only)` — not `own-plus-team`. `VRS-F010`'s own spec text is explicit: "TimesheetWeekSubmission carries the identical `MATRIX_OVERRIDES` row TimesheetEntry already has — owner/HR Admin Full, Finance-admin Read, Manager Read (direct reports), Team Member Full (own only)." A Team Member has therefore been able to see every teammate's compliance status — not merely their own — since this function was built at Stage 18, a pre-existing gap F292 widened further (to the whole workspace) but did not create. No PostgreSQL test exercises a Manager or Team Member principal against this function (the existing coverage in `timesheet.integration.test.ts` calls it only under `w.owner`), so nothing caught either the original own-plus-team-vs-own-only gap or F292's further widening of it.

**Closed by direct precedent — no founder consultation needed, same mechanism as F294.** `listSubmissionStatus` is corrected to call the same new primitive against `TimesheetEntry:record`'s own cell (or `TimesheetWeekSubmission`'s — F273 registered them identically) instead of `Employee:operational`'s, resolving each caller's admission against the policy row that actually governs this specific disclosure. This is narrower than F294's own fix for the other two queries (`own`, not `own-plus-team`, for Team Member) — matching `VRS-F010`'s explicit text exactly, not merely reverting to a pre-F292 state that was itself already wrong for this one case.

**Status: closed.**
