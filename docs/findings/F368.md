### F368 — the brief's contextual-intelligence wiring cannot work as written; and Ghost promotion needs `protectedMutate`, not `client.mutate`

**Found while:** Codex's UI-3 pre-build trace (its UI3-E and the mechanism half of its UI3-F). Independently verified against `packages/graph/src/sync-client/query.ts` (lines 95–130), `packages/graph/src/sync-client/engine.ts` (lines 316–358), `packages/graph/src/queries/contextual-intelligence.ts` (lines 57–66), and `packages/schema/src/mutations/ghostResource.ts` (lines 59–68) before ruling.

**Part one — the combined query cannot be the `device-query`.** The brief's Do item 1 said to dispatch `contextualIntelligence.get` straight to the existing `getContextualIntelligence(database, employeeId, getProtected)`, supplying the engine's own `protectedRead`/`protectedMutate` pattern as `getProtected`. Two things make this impossible as written: `runCacheQuery` (`sync-client/query.ts`) is a synchronous, local-only dispatch with no network path of its own, and every `device-query` subscription awaits it under the engine's `#exclusive` lock — injecting a network round-trip into that path would make a supposedly Tier-0, offline-first read block on connectivity, contradicting the whole point of a `device-query`. Separately, `getProtected`'s expected shape takes a known node id; the Tier 2 `BurnoutAlert`/`FlightRiskSignal` node ids are not in the Tier 0 cache at all — the existing server procedure discovers them itself, server-side, by walking `triggered_by` edges before reading them (`services/api/src/permission/contextual-intelligence-queries.ts`). There is no node id for the client to hand `protectedRead`.

**Part one, resolved.** Split the read exactly as `benchForecast.getCost`/`getAggregate` already split from `benchForecast.get` (F236, F241): the `contextualIntelligence.get` device-query dispatches to `getLocalContextualIntelligence` alone (Tier 0 — skills, open roles, references), unchanged and genuinely local. The Tier 2 fields are fetched by a separate, on-demand `contextualIntelligence.getProtected` typed call — the server procedure of that name already exists and is unchanged — following the identical batched, non-blocking `cache: "no-store"` pattern F358 established for the Employee profile and this brief's own Do item 4 already uses for bench cost and aggregate utilization. This is not a new mechanism; it is the same one this stage already builds twice, applied a third time. The existing `contextual-intelligence.test.ts` (which already tests `getLocalContextualIntelligence` alone, not the combined function) needed no change to keep passing — it was quietly already testing the right half.

**Part two — Ghost promotion cannot go through `client.mutate`.** The brief's Do item 3 said to wire "Promote to employee" through `client.mutate`. `ghostResourcePromote` is declared `onlineOnly: true` (`packages/schema/src/mutations/ghostResource.ts` line 68), and `SyncEngine.mutate` refuses every `onlineOnly` definition outright — `{ accepted: false, reason: "requires-protected-mutation" }` (`engine.ts` lines 352–358) — before it ever reaches the outbox. This was already confirmed correct by design earlier in this stage's own briefing (`onlineOnly: true` with no client-side optimistic mutator registered is deliberate, not a gap); what was missed is that "correct by design" also means the call mechanism itself has to be `protectedMutate`, the engine's dedicated path for exactly this class of mutation, never `client.mutate`.

**Ruling. Closed 29 September 2026, wiring corrections against already-settled mechanisms (F236/F241/F358), no founder ruling needed.** Do item 1 is corrected to dispatch `contextualIntelligence.get` to `getLocalContextualIntelligence` only; Do item 3 is corrected to fetch Tier 2 contextual fields via a new on-demand `contextualIntelligence.getProtected` call, and to submit Ghost promotion via `client.protectedMutate`, not `client.mutate`.

**Status: closed** (wiring correction, folded into the corrected UI-3 brief).
