### F290 — `SkillGap.severity` has no calendar to resolve for a Project with no Assignment

Raised 25 September 2026. Codex resumed Stage 21 implementation after F289's fix and, tracing `skillGap.evaluate`'s severity computation before writing it, found G07's requirement — working days to `Project.start_date`, per `VRS-F004` — has no calendar to count against. `resolvedDayOn`/`countWorkingDays` (`services/api/src/graph/working-days.ts`) require a real Employee: calendars are resolved through `resolveEntityAssignment`'s `scoped_to_entity` traversal (Employee → Entity → `governed_by_calendar` → `WorkingCalendar`), plus that Employee's own personal `WorkingPattern` and `location`. Project carries no `scoped_to_entity`-equivalent edge, no Client-level jurisdiction, and no Entity link of any kind — it is still only the minimal `VRS-F005` bootstrap node (`name`, `lifecycle_status`, and this stage's own new nullable `start_date`). The exact case that creates a SkillGap — a requirement with zero qualifying candidates after availability filtering — need not have any Assignment on the Project at all, and even when other unrelated Employees exist, their Entity calendars can genuinely disagree within one workspace, since `entity.create` has no uniqueness constraint and multiple Entities are already structurally possible today (`VRS-F064`, Multi-Currency Payroll, would be the feature that makes multiple Entities a real, exercised case — it is unbuilt). Selecting an arbitrary Employee's calendar, using the server's own weekday, or treating calendar days as working days would each violate `VRS-F004` and yield nondeterministic severity for otherwise-identical gaps.

This is a genuine architectural fork, not a traceable-to-precedent gap: no prior feature has ever needed a working-day calculation with no Employee to anchor it, and the spec itself never named which calendar governs — it says only "per `VRS-F004`," leaving the calendar-selection question entirely open. Put directly to the founder with three options reasoned through: degrade to `Low` whenever no calendar resolves (simplest, but silently under-reports urgency for the single most product-critical case — a brand-new, understaffed Project with a real, looming start date, exactly the shape most SkillGaps on a fresh Project would take); commit a real Project→Entity link now (structurally correct long-term, but a schema commitment beyond this stage's own stated boundary, and duplicates ground `VRS-F064` will need to cover regardless); or resolve opportunistically from the Project's own existing structure, falling back to the workspace's sole Entity where today's data model has at most one, and only degrading to `Low` in the genuinely ambiguous residual case.

**Decided by the founder, 25 September 2026: resolve from Assignments, else the workspace's sole Entity, else `Low`.** If the Project has any Assignment, resolve the calendar through the earliest-staffed one's Employee — deterministic, no arbitrary pick. If it has none, and the workspace has exactly one Active Entity (true for every workspace today), use that Entity's calendar directly, never an Employee's personal overrides. Only when neither resolves — no Assignment and zero or multiple Entities — does severity degrade to `Low`, extending the already-established null-`start_date`-degrades-to-`Low` convention to this second, now genuinely rare, missing-input case rather than the common one. New `resolveProjectCalendarEntity` (`services/api/src/graph/entity-resolution.ts`) and `countWorkingDaysForEntity` (`services/api/src/graph/working-days.ts`, sharing the same `resolveWorkingDay` pure function `countWorkingDays` already uses, with `pattern`/`location` always `null`) implement it — G08's "one implementation" rule stays intact; only the Employee-specific input-gathering wrapper gains an Employee-less sibling. Explicitly recorded as a forward dependency on `VRS-F064`: once multi-entity workspaces are real and exercised, the "exactly one Active Entity" fallback will need a real Project→Entity link, not solved here.

**Status: closed.**
