### F325 — audit immutability is structural only

**Found while:** briefing Stage 26 (`VPS-F004`), 26 September 2026, by checking the spec against the code before writing the brief.

Immutability is structural only: the journal is append-only because `journal.ts` exports no update or delete and `audit/schema` may be imported only from `audit/` and `db.ts` (arch-check rule 3), the one test for it (`has no update and no delete path`) checks the exported names of `journal.ts` and nothing else, and no database mechanism (trigger, revoked privilege) stops a raw `UPDATE` or `DELETE`. The spec's own acceptance criterion is broader ("any API path", "no code path anywhere"), and only the pseudonymizer legitimately updates a retained row.

**Files:** `services/api/src/audit/journal.ts`, `services/api/src/audit/schema.ts`, `services/api/src/audit/audit.integration.test.ts`, `scripts/arch-check.mjs`

**Ruling.** **Closed 26 September 2026 by ruling; a database-level guard is deferred, recorded as a limitation.** This stage strengthens the structural proof without adding a database mechanism: (a) a test scans `services/api/src` and asserts that `.update(auditJournal)` occurs only in `audit/pseudonymizer.ts` and `.delete(auditJournal)` occurs nowhere; (b) a runtime test proves that every generic write path (`graph.createNode`, `updateNodeFields`, `softDeleteNode`, `transitionLifecycle`, and the three edge mutations) is refused for `AuditEntry` even for the Owner, and that `AuditEntry` is neither replicable to a device nor searchable. A trigger that allows only the pseudonymizer's update and blocks everything else needs a workspace-deletion (`ON DELETE CASCADE`) story and a session-flag design that has not been verified, and the tamper-evidence the spec really wants is the hash chain (`FDN-108`, named in `audit/schema.ts`); until then a database owner or a migration can still edit the journal, and that is stated, not hidden.
