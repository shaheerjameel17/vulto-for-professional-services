### F246 — Card-bearing `assignment.create` has no defined offline or optimistic behavior

Raised 23 September 2026 in the same Stage 14 contract trace, before any product code was written.

**The gap.** Stage 13's `assignment.create` is Tier 0, `onlineOnly: false`, with a real optimistic handler. Stage 14's Do item 3 made the same mutation, when `rate_card_id` is supplied, respons­ible for writing a `governed_by` edge to a RateCard that is never present in the device cache (F244), and Do item 2 made it resolve `effective_billing_rate` against a Tier 1 `RateCardLine` the device cannot read. Do item 7 defined optimistic handlers for the three new Assignment-rate mutations but never revisited `assignment.create`'s own existing handler, whose authoritative effect item 2 had just changed.

**Closed by founder-delegated decision, 23 September 2026.**
1. **The `governed_by` edge is written exclusively server-side**, in the mutation's `apply()` step against Postgres — never by any optimistic handler. Nothing on-device ever needs to read this edge: RateCard/RateCardLine are never cached (F244), the local Bench Forecast query needs no rate data at all, and `rateCard.usageCount`/the version-history count are server-only reads (F243). With no local consumer, there is no reason for the optimistic path to attempt a speculative edge write at all — resolving the question without inventing a "dangling edge" mechanism.
2. **`assignment.create`'s optimistic handler is unchanged from Stage 13.** It already writes `rate_card_id` as a plain scalar field and always sets `effective_billing_rate` to the employee's cached `billing_rate_default`, regardless of whether a card is supplied — this was already Stage 13's exact behavior, before `rate_card_id` had any real meaning, and it remains correct now: a deliberate placeholder, corrected by the server's authoritative response once the mutation confirms — the same "deliberately server-only, no client precompute" discipline F224 already established for the 100% capacity constraint and F241 already established for disclosure control.
3. **No conditional `onlineOnly` mechanism is needed.** `assignment.create` stays `onlineOnly: false` and fully offline-capable, card or no card — `MutationDefinition.onlineOnly`'s static, per-name shape needs no change, and card selection is not split out into a separate later step.

`VRS-F006`'s Technical Architecture and Stage 14's brief (Do items 2, 3 and 7) are corrected to state this explicitly, as a new G09.

**Status: closed.** Stage 14 is unblocked; `assignment.create`'s existing offline behavior needs no change, and the new edge write has one clear owner.
