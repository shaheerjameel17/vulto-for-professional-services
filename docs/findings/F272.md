### F272 — a system-authored node or edge has no genuine User UUID for `created_by`/`updated_by`

Raised 24 September 2026 by Codex, resuming Stage 18 after merging F271's ruling, tracing the now fully-authorized system write and read into the graph's universal record schema before writing any mutation code. `VPS-A002`'s universal node conventions require `created_by`, `updated_by` (node) and `created_by` (edge) as a genuine `user_id UUID` on every node type `TimesheetAnomalyFlag` and its `triggered_by` edge fall under — `packages/schema/src/records.ts`'s Zod schemas enforce this with no exception besides the two anonymous-contribution node types and (for `updated_by` alone) `AuditEntry`, neither of which applies here. `packages/schema/src/mutations/shared.ts`'s `stampNewNode`/`stampNewEdge` take a `Provenance` whose `userId: string` is required and placed directly into these fields; `services/api/src/permission/principal.ts`'s `SystemPrincipal` carries only `name` and `workspaceId`, no User UUID at all. `services/api/src/mutations/types.ts`'s `MutationContext.principal` is typed `MemberPrincipal`, not the `Principal` union, so every existing `provenance(ctx)` helper across the mutation files assumes `ctx.principal.userId` exists unconditionally.

Codex checked the three values this could plausibly hold and found each closed off. Attributing the write to the submitting Team Member's own UUID is not merely inaccurate — it directly contradicts F270's own ruling: that Team Member has `NONE` on `TimesheetAnomalyFlag`, deliberately, so recording them as the record's author would put a false, policy-incoherent claim into a field an HR product's own disputes rely on (`VPS-A002`'s own stated reason for `updated_by` existing at all). Inventing an arbitrary UUID with no row behind it passes the Zod format check but resolves to nothing — a dead end for any future feature that reads `created_by` back, and Codex confirmed by direct inspection of `services/api/src/graph/schema.ts` that `created_by`/`updated_by` are in fact nullable at the Postgres layer with no foreign key to any auth table at all ("consistency... is enforced in code," per that file's own comment) — so the Zod schema, not the database, is the only thing actually requiring a value here, which reframes this as a representation choice rather than a hard constraint. Codex checked for precedent and found none: `services/api/src/graph/founding.ts`'s `writeFoundingRecords` — the only place that writes graph nodes outside `authorizeWrite` — stamps the real signing-up human's own UUID, not a system actor; the three existing system operations (`audience.recompute`, `audit.pseudonymize-actor`, `protected.destroy-key`) never call `insertNode`/`insertEdge` at all, confirmed by direct grep, so none of them has ever faced this question. Codex correctly declined to invent an unruled representation and stopped to report it, rather than pick one of three semantically different answers unilaterally.

This was put directly to the founder as a genuine architectural fork, and the choice reasoned through with him rather than settled by tracing to precedent, because none existed and the decision is cross-cutting: `VPS-A002`'s own text already states that another omission or representation policy for these fields "is a specification change, not an implementation choice," and F270's own writeup already flagged that `BurnoutAlert`, `FlightRiskSignal` and `RevenueGapAlert` are all schema-registered, all unbuilt, and all need exactly this same mechanism — so whatever this feature settles becomes the pattern every future system writer inherits. Three shapes were weighed: a synthetic `User` per system principal (chosen); a reserved sentinel UUID with no real row; and extending the universal schema itself with an `actor_kind`-style discriminator mirroring the audit journal's own already-proven representation (`packages/schema/src/audit.ts`'s `AUDIT_ACTOR_KINDS`, stress-tested successfully against real-erasure pseudonymization in `services/api/src/audit/pseudonymizer.ts`). The audit journal's own representation was confirmed sound on its own terms — its coherence is enforced by `addAuditCoherenceIssues`, not merely documented, and pseudonymization already proves it holds under an adversarial rewrite — but cloning that exact discriminated shape onto `records.ts`'s passive universal envelope would require duplicating that coherence machinery across every node and edge validator for a field nothing reads today, which is heavier than the problem calls for. The founder chose future robustness in the field itself over minimal footprint: `created_by`/`updated_by` should always resolve to something real and joinable, the same way for a human or a system actor, with no null-handling burden pushed onto every future reader of the field.

**Closed by founder-delegated decision, 24 September 2026.** Each named system principal (`packages/schema/src/policy/principal-policy.ts`'s `SYSTEM_PRINCIPAL_NAMES`) is given its own reserved `User` node, one per principal per workspace: universal fields only, no linked Employee profile, and deliberately no `WorkspaceMembership` edge, since every people- or membership-facing query in this codebase reaches `User` through that edge today (confirmed by direct grep — there is no broad "list all Users" scan anywhere) — the reserved identity is therefore invisible to every such query by construction, not by a filter someone has to remember to add. It is provisioned lazily and deterministically: an ID derived from `(workspaceId, systemPrincipalName)` — the same deterministic-ID pattern F233 and F247 already established for other derived entities in this codebase, not a new mechanism — created via a race-safe get-or-create (`INSERT ... ON CONFLICT DO NOTHING`) the first time that principal writes anything in a given workspace, never a founding-time backfill, since `SYSTEM_PRINCIPAL_NAMES` grows as later stages add jobs and a backfill would be needed every time. Its own `created_by`/`updated_by` are self-referential, the identical bootstrap resolution `writeFoundingRecords` already uses for the founder's own `User` row. `Provenance` (`packages/schema/src/mutations/shared.ts`) gains a resolution step: when the acting principal is a `SystemPrincipal`, its `userId` is this reserved identity's UUID, not `ctx.principal.userId` (which does not exist on that type) — `stampNewNode`/`stampNewEdge` themselves are unchanged. A new closed table, `SYSTEM_PRINCIPAL_DISPLAY_NAMES`, pairs each system principal with a plain, human, non-technical label for whichever future stage displays "created by" in the interface — never the internal principal name, never a raw UUID. `timesheet-anomaly-evaluate`'s label is **"Automatic Review."** `VPS-A002`'s universal node and edge conventions are corrected to state this explicitly, since the decision governs every future system-authored write, not only this one — see that document's own Decisions recorded entry. `docs/Claude_Code_Build_Prompt.md`'s Stage 18 section and `docs/Reviewer_Handoff.md`'s section 19 are corrected to match.

**Status: closed.**
