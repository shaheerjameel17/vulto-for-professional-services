### F358 — compensation's real visibility is already encoded in `getEmployee`'s own response; the profile screen needs no role of its own to gate it, superseding part of F351 and F352

**Found while:** Codex's UI-2 pre-build trace, 27 September 2026 (its findings C and D), verified directly against the code before ruling.

F351 and F352 assumed the profile screen would need the caller's real role to decide whether to render compensation — F351 said a "null/absent response renders the Compensation section as structurally absent"; F352 said `canSeeCompensation`'s signature would take "a real role value... mapped onto the same union." Tracing `getEmployee` (`services/api/src/permission/employee-queries.ts`) and `readProtected` (`services/api/src/protected/read.ts`) directly shows this is unnecessary and, worse, would have been wrong: `readProtected` already returns a three-state `ProtectedReadItem` per partition — `"available"` (the decrypted value), `"restricted"` (a server-supplied `label`, e.g. `"Visible to Finance Admin"`), or the fragment omitted entirely (structurally absent) — and the real `Employee:compensation` policy row (`packages/schema/src/policy/policy-table.ts`) has **five** distinct behaviors (Owner and HR Admin full, Finance Admin full, Manager restricted-with-label, Team Member read-own), which `lib/viewer.ts`'s binary `canSeeCompensation` (owner/hr-admin only, no Finance Admin, no self case) cannot represent and was never asked to. `ShellBootstrap` (`apps/roster-web/src/components/shell-bootstrap.tsx`) also carries no role at all — the client would have needed a new call to `principal.current` (`services/api/src/router.ts`) to get one.

**Files:** `apps/roster-web/src/components/profile/OverviewTab.tsx`, `services/api/src/permission/employee-queries.ts`, `services/api/src/protected/read.ts`, `packages/schema/src/policy/policy-table.ts`, `apps/roster-web/src/lib/viewer.ts`

**Ruling.** **Closed 27 September 2026 by ruling, superseding F351's and F352's compensation-gating detail (their other rulings stand unchanged).** The profile screen never checks a role for compensation. It renders directly from `getEmployee`'s `compensation` array (via F351's typed fetch, now going out through F357's `protectedMutate`/`protectedRead`-style path for the write and read respectively): no item for this employee → the Compensation section is structurally absent, exactly as before; an item with `state: "restricted"` → the section renders read-only with the server's own `label` text in place of the fields, never the values; an item with `state: "available"` → the fields render editable as today. No fetch to `principal.current`, no role plumbed through `ShellBootstrap`, and `lib/viewer.ts`/`canSeeCompensation` are not read by this screen at all — F352's instruction to remove the `ProfileViewer` `ToggleGroup` stands, but nothing replaces it with a role lookup.
