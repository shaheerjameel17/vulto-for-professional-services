### F214 — the locked shell has no store left to lock

Raised 22 September 2026, correcting `VPS-D004` for Stage 8. **Ruled 22 September 2026 (founder-delegated decision; see the Ruling below).** It was raised as a design question, not a wording fix.

**What the section says.** The shell renders a full-bleed *Locked* screen, before anything mounts, whenever the sealed local store has not been unlocked by a server-authorized online unlock in this process (cold start), or has been sealed again by an authoritative denial from the role-refresh checkpoint (mid-session, F146). Only an authoritative denial locks; a timeout, a 5xx or an unreachable network does not (F148). A denied revocation and an unreachable server render identically (non-enumeration), and the client may distinguish them to decide whether to seal the store while still rendering both the same. *Locked* and *Offline* are different: an unlocked offline device never shows Locked.

**What no longer exists.** The sealed store, `POST /device-store/unlock`, the role-refresh checkpoint and the worker that held the live store are all deleted. A device now opens its cache from identifiers alone (`session_hint`), with no unlock and no token, and boots offline straight into `Offline`. There is nothing that can be sealed, so neither variant can occur, and the two properties the section protected have no implementation to hang on: (1) *a person whose access was withdrawn must not be shown their workspace*, and (2) *what the client shows must not reveal why*.

**What the current architecture already does.** The server refuses every request from a session that is not an active member of the workspace with the same non-distinguishing failure (`requireCurrentWorkspaceSession` raises one error for no session, wrong workspace and revoked membership; tRPC answers `401`). The shape proxy answers every way of not being an active member with one byte-identical `access-revoked` body and `erase: true`, and the client's response to that is to erase that workspace's cache (Stage 6). An unreachable server is a network error, not a `401`, and leaves the shell as it is.

**Proposed replacement (for a ruling).** One state, replacing both variants:

- **Trigger.** Any `401`/`UNAUTHORIZED` from an authenticated call, or an `access-revoked` from the shape proxy. Never a network failure, a timeout, a 5xx or a rate limit; those keep the shell exactly as it is and show the ordinary `Offline` or error treatment.
- **Rendering.** The full-bleed treatment as today, no illustration, one `body` sentence and a `primary` **Retry**. Copy that names neither cause nor person, for example *"Reconnect to continue. Vulto needs to verify your session before opening your workspace."* The same copy for cold start and mid-session; there is no longer a difference in what was on screen that a store needs to protect.
- **What Retry does.** Re-issues the failed call. If it succeeds the shell mounts; if it fails the same way the same state remains. It never says why.
- **Data.** On `access-revoked` the client has already erased that workspace's cache, so nothing readable is behind the screen. On a plain `401` (an expired or missing session) nothing was erased and the cache stays, but it is not rendered until a call succeeds.
- **Kept.** *Locked* is still distinct from *Offline*: an already-open device that loses connectivity keeps its cache and shows `Offline`. Only an authoritative refusal produces this state (F148). No feature may reuse the treatment.
- **Removed.** The unlock step, the cold-start/mid-session split, and "the local store stays sealed"; the unsaved-work clause becomes the outbox's (queued Tier 0 changes are kept until sent, and are erased only by a revocation or sign-out, per Stage 6).

**Tradeoffs to rule on.**
1. *A person whose session simply expired sees the same screen as a person removed from the workspace.* That is what non-enumeration asks for, but it is a worse experience for the common case (an expired session). The alternative is to send a plainly unauthenticated response (no session at all) to sign-in, and reserve the *Reconnect* state for a session that exists but is refused. That is safe today, because the proxy already distinguishes `unauthenticated` from `access-revoked`, and a missing session leaks nothing about any workspace. It does add a second refusal treatment, which the section currently forbids.
2. *A removed person sees a screen that says "Reconnect" and keeps offering Retry forever.* They cannot be told, and there is nowhere for a Retry to succeed. Accepting that is the price of the property. The alternative (a terminal state after N identical refusals) would itself reveal the difference between an outage and a refusal.
3. *`access-revoked` erases that workspace's cache.* That is a device-visible signal the client necessarily acts on, so the client does distinguish; what it must not do is render the distinction. The section's own last paragraph already says this ("non-enumeration governs what is rendered, never what the client concludes").
4. *Nothing is sealed on a plain `401`.* Cached Tier 0 rows remain on the device until a call succeeds or the person signs out. The old design sealed them. If that residual exposure matters (a shared computer, a session revoked while the laptop is closed), the alternative is to erase the workspace's cache on any `401`, at the cost of destroying a returning user's cache on every expiry.

**Recommendation.** The single state above, with tradeoff 1 decided in favor of sending a plainly missing session to sign-in and everything else to *Reconnect*, and tradeoff 4 left as stated (no erase on a plain `401`). This is a recommendation only; the section stays as it is, marked, until it is ruled.

**Consequence of leaving it open.** Nothing in Stage 8 renders a shell state; the marker keeps the historical section from being built to.

**Ruling (22 September 2026).** The proposed replacement is accepted as written: one *Reconnect* state, triggered only by `401`/`UNAUTHORIZED` on an authenticated call or `access-revoked` from the shape proxy, never by a network failure, timeout, 5xx or rate limit; full-bleed, one **Retry** that re-issues the failed call and never says why. **Tradeoff 1** is decided as recommended: a call carrying no session at all (never authenticated on this device, or already signed out) goes to sign-in; *Reconnect* is reserved for a call that had a session and was refused. Non-enumeration holds, because within "had a session, got refused" an expired and a revoked session still render identically, and whether a device ever had a session says nothing about any workspace or person. **Tradeoff 4** is decided as recommended: nothing is erased on a plain `401`; cached rows stay until a call succeeds or the person signs out. That is accepted only because the device cache holds Tier 0 only by the tier system's design, so a lapsed session on a shared device exposes nothing beyond what that design already decided is safe to leave there. **If a future stage widens what the device cache holds, this decision must be revisited.** Tradeoffs 2 and 3 are accepted as stated.

`VPS-D004` is corrected to match (the "Locked shell" section is now "The reconnect state", the marker is removed and the Decisions Recorded entry records this ruling). **Building the state (the component, its `401`/`access-revoked` wiring and its tests) is not part of this closure; it is tracked as Stage 9.**
