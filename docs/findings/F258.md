### F258 — `VRS-F008`'s Depends-On section omits its real forward dependency on `VPS-A006`'s unbuilt job-scheduling infrastructure

Raised 24 September 2026, the identical shape F248 already ruled on.

**The gap.** `VRS-F008`'s Depends-On line names `VRS-F002`, `VRS-F004`, `VRS-F005`, `VRS-F007` and `VPS-A004`, but not `VPS-A006` — the architecture document that is the actual authority for the "four-hourly cadence" the safety-net sweep's own prose invokes twice ("on the same four-hourly cadence [[VRS-F012]] uses"). `VPS-A006`'s own Job queue and scheduling section names both `VRS-F012`'s bench sweep and `VRS-F008`'s own capacity safety-net sweep, by name, as part of the reason BullMQ (workers in `services/jobs`) was chosen over a Postgres-based alternative — a real, already-decided dependency, not an invented one. But no `services/jobs` directory and no BullMQ reference exists anywhere in the repository, confirmed by a repository-wide search, and `VRS-F012` itself — the sibling feature whose cadence this sweep claims to reuse — sits four stages later in `VRS-001`'s build order (Stage 20) and is not yet built either. Read alone, "the same four-hourly cadence [[VRS-F012]] uses" suggests an existing schedule Codex could simply hook into; in fact neither the schedule nor its infrastructure exists yet for anyone. This is structurally the same shape as F248: a spec's dependency list reads as complete while a real, later-owned prerequisite goes unnamed.

**Closed by founder-delegated decision, 24 September 2026, on F248's own Partial-forward-dependency precedent.** G06 already scopes the sweep correctly as pure product logic — "The sweep writes nothing. It is a read query" — and that is exactly what Stage 16 builds: `conflictResolution.sweepOvercommitted` ships as a complete, directly callable, fully tested read query now. What Stage 16 does not build is the periodic BullMQ trigger that calls it every four hours; that belongs to `VPS-A006`'s own not-yet-built `services/jobs` decision, shared with `VRS-F012` and six other named features, and gating Stage 16 on it would mean building unrelated platform infrastructure inside a Core feature's stage. `VRS-F008`'s Depends-On section gains a Partial forward dependency line naming `VPS-A006`, mirroring F248's own line for `VRS-F007`/`VRS-F028` exactly, and the safety-net sweep's own prose gains a note that the read query is complete and callable on demand from launch, with periodic scheduling deferred to whichever stage builds `VPS-A006`'s job queue.

**Status: closed.** Stage 16 is unblocked; the sweep's own scheduling is deferred as a named, non-blocking gap rather than built or silently ignored.
