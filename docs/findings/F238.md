### F238 — the k-anonymity disclosure-control mechanism VRS-F005 depends on has never been built

Raised 23 September 2026 while briefing Stage 13 (`VRS-F005`), checking `VPS-A004`'s "Aggregate disclosure control" section against the actual codebase before writing the brief.

**The gap.** `VRS-F005`'s own Security Considerations require "aggregate utilization passes through `VPS-A004`'s disclosure control, including the differencing protection," and four of its ten acceptance criteria depend on a below-threshold cohort being suppressed. `VPS-A004` specifies the mechanism in full: a cohort below `k_anonymity_minimum` (default 5) or `k_anonymity_minimum_sensitive` (default 8, Tier 3-derived aggregates) is suppressed rather than approximated; a filter reducing a displayed cohort by fewer than `k` members returns the unfiltered aggregate instead of a new, smaller-cohort one; and a sequence of aggregate queries against overlapping cohorts is recorded in `VPS-F004`'s Silent Audit Log. A repository-wide search (`k_anonymity`, `kAnonymity`, `Suppressed`) found no implementation anywhere — the mechanism has never been built, by any stage. The two threshold values are documented as workspace settings owned by `VPS-F005_Workspace_Configuration_Console` (Privacy and data section, with a hard floor of 3), and that feature is not built either — there is no configuration surface, and no Workspace field currently holds either value.

**Why this cannot be deferred like a partial forward dependency.** `VRS-F006`/`VRS-F007` (Rate Card, Ghost Resources) are explicitly non-blocking per the spec's own "Partial forward dependencies" line — assignment cost and Ghost rows simply render degraded until those features land. Aggregate suppression is different: it is this feature's own acceptance criteria, not a forward-looking allowance, and a founder who filters the Bench Forecast to a three-person cohort and sees a real percentage instead of the required restricted state is exactly the disclosure failure `VPS-A004` exists to prevent.

**Closed by founder-delegated decision, 23 September 2026.**
1. **Settings, not UI.** `k_anonymity_minimum` (default 5) and `k_anonymity_minimum_sensitive` (default 8) are added directly to `Workspace`'s own schema now, with the documented floor of 3 enforced wherever they are read. No settings screen is built — `VPS-F005_Workspace_Configuration_Console` still owns editing them later, exactly the "data field now, dedicated editing surface later" split F222 already used for the founding Entity's placeholder defaults and F227 used for the Global/IN/SG calendar template.
2. **One shared mechanism, not a bespoke check.** A single function — e.g. `applyDisclosureControl(cohort, aggregateFn, threshold)` in `packages/schema`'s policy module, alongside `MATRIX_OVERRIDES` — implements exactly `VPS-A004`'s two enforceable rules: suppress below `k`; on a filter that would reduce an already-displayed cohort by fewer than `k` members, return the unfiltered aggregate with an indication the filter wasn't applied to the figure, rather than compute a new one. `VRS-F005`'s `benchForecast.get` is its first caller, built generally enough (cohort in, aggregate function in, threshold in) that a later feature (`VRS-F048`, `VRS-F058`, `VRS-F059`, `VRS-F060`, `VRS-F071`, `VRS-F072`, `VRS-F011`) calls the same function rather than reimplementing it, per `VPS-A004`'s own explicit intent that "every aggregate in this product passes through one mechanism."
3. **The differencing-attempt audit trail is deferred, recorded rather than silently dropped.** `VPS-F004`'s `AuditEntry.event_type` is a closed, access/denial-focused enum (F206, F221, F225's precedent) with no category for an ordinary aggregate read, successful or suppressed. Extending it to log every aggregate query for pattern-of-differencing detection is a `VPS-F004` schema change with its own tradeoffs (query volume, retention), not a one-line addition inside this feature. Stage 13 builds and tests rules 1 and 2 above; the audit trail is a named follow-up, owned by whichever stage next extends `VPS-F004`'s event taxonomy or builds a dedicated aggregate-access log.

`VPS-A002`'s `Workspace` node schema and `VRS-F005`'s Security Considerations are corrected to record the two new fields and point at the shared mechanism; `VPS-F005_Workspace_Configuration_Console` is unaffected — it still owns the settings screen when it is eventually built.

**Status: closed.** Stage 13 is unblocked; it builds the mechanism for real rather than special-casing it, and records the deferred audit trail rather than skipping it silently.
