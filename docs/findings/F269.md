### F269 — F268's `TimesheetAnomalyFlag` branch read a Tier 2 node's own field through a channel that doesn't carry it

Raised 24 September 2026 by Codex, resuming Stage 18 from `65c172a` after applying F267's fix (`77839f5`). F268 ruled a third `rowScopeSatisfied` branch: for `TimesheetEntry` or `TimesheetAnomalyFlag`, read the row via the already-imported `getNode`, and take `subjectEmployeeId` from `node.record.employee_id`. Codex correctly declined to implement this for `TimesheetAnomalyFlag` and stopped to report it, rather than shipping a check that fails closed for every caller — exactly the escalate-and-wait discipline the founder ruled standing practice after Stage 17. `TimesheetAnomalyFlag` is registered `fixedProtection("Manager-restricted", 2)` (`packages/schema/src/registry/nodes.ts`) — the same tier as `BurnoutAlert`. `services/api/src/protected/schema.ts` documents `graph_protected_fragments` as holding "Tier 1 and Tier 2 content, and nothing else" (A003-T55), AES-256-GCM-encrypted, keyed by `(ownerKind, ownerId, schemaPartition)`, with its own `protected_data_keys` wrapping hierarchy — content `getNode`'s plain `graph_nodes.record` read never touches. `store.ts`'s own comment on `findNodeByRecordField` confirms it directly: a field read off `record` is "never a protected one, because the record holds Tier 0 only." `TimesheetAnomalyFlag`'s `employee_id` is Tier 2 content; `node.record.employee_id` would be `undefined` for it, and F268's ruled branch would fail closed for every Manager against every direct report's flag — the exact defect Codex reported.

`TimesheetEntry` does not share this problem. It is registered `fixedProtection("Standard", 0)` — Tier 0, the one tier `graph_protected_fragments` never stores — so its `employee_id` genuinely is a plain field in `graph_nodes.record`, and F268's branch for it was correct as ruled.

This was a ruling error, not a build-time surprise the spec left ambiguous: `packages/schema/src/registry/edges.ts` already registers `["TimesheetAnomalyFlag", "Employee"]` in the same `triggered_by` `edgeGroup` as `["BurnoutAlert", "Employee"]` (its owner list already includes `VRS-F010`, alongside `VRS-F052`/`VRS-F053`/`VRS-F012`) — the exact edge `rowScopeSatisfied`'s existing `BurnoutAlert` branch already traverses, and `BurnoutAlert` carries the identical `Manager-restricted`/Tier 2 protection, so that branch is already proven to work for a Tier 2 node. F268's own text considered only the node schema's direct `employee_id` field, correctly, for G04's reason ("a Pitch entry has no Assignment to traverse through at all") — but did not separately check whether `TimesheetAnomalyFlag` also carried a registered edge to Employee. It does, and unlike `TimesheetEntry`'s conditional `logged_against`, `TimesheetAnomalyFlag`'s `triggered_by` edge is unconditional: every flag has exactly one triggering Employee, always reachable the same way `BurnoutAlert`'s already is.

**Closed, traced directly to `BurnoutAlert`'s own precedent — no founder consultation needed. Corrects F268's `TimesheetAnomalyFlag` resolution, leaves its `TimesheetEntry` resolution unchanged.** `rowScopeSatisfied` keeps two branches where F268 ruled one: `row.nodeType === "BurnoutAlert" || row.nodeType === "TimesheetAnomalyFlag"` follows the registered `triggered_by` edge exactly as the existing `BurnoutAlert` code already does (`outgoing(tx, principal.workspaceId, nodeId, "triggered_by", asOf)`); `row.nodeType === "TimesheetEntry"` alone keeps F268's `getNode`/`record.employee_id` read, since Tier 0 content genuinely is there. No new grant type, no new edge type, no change to `own`/`direct-reports`/`own-plus-team` evaluation. Since no creation mutation for `TimesheetAnomalyFlag` exists before Stage 18, `timesheetAnomaly.evaluate` must write the `triggered_by` edge to the flagged Employee in the same transaction as the flag itself — without it, this corrected branch has nothing to traverse and fails closed exactly as before. `docs/Vulto_Specs/VRS-F010_Timesheet_Speed-Run.md`, `docs/Claude_Code_Build_Prompt.md`'s Stage 18 section and `docs/Reviewer_Handoff.md`'s section 19 are corrected to match.

**Status: closed.**
