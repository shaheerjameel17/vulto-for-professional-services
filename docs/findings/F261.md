### F261 — F260 defines `InitPayload.roles` but no production caller can supply it

Raised 24 September 2026 while tracing F260's ruled role plumbing from `MutatorContext` back to the real graph-client bootstrap, before product code was written.

**The gap.** F260 rules that `MutatorContext.roles` is threaded through `InitPayload` the same way `userId` is. `GraphClientOptions` extends `InitPayload`, so making that field real requires every `createGraphClient` caller to supply it. Neither production caller has such a value:

1. `apps/roster-web/src/components/shell-bootstrap.tsx` reads `data.user.id` and `data.session.activeOrganizationId` from Better Auth, constructs `{ workspaceId, userId }`, and calls `createGraphClient({ workspaceId, userId, apiOrigin })`. The session value exposes no membership roles, and the shell never calls `principal.current`.
2. `apps/roster-web/src/app/sync-harness/sync-harness-client.tsx` receives only `workspaceId` and `userId` query parameters, then makes the same three-field call.
3. Stage 16 Do item 11 says no file under `apps/` may change, and the Done criteria require that absence in the diff. Even if app changes were permitted, the corrected brief never defines whether the shell should extend Better Auth's session shape, call `principal.current`, read a role from the local graph, or persist a last-known role outside the graph client.

The alternatives produce materially different offline behavior. Making `roles` optional or defaulting it to `[]` lets the code compile but rejects every valid Owner override locally. Calling the existing server-side `principal.current` route during `createGraphClient` gives a current answer online, but a cold offline boot — explicitly supported by the Stage 9 shell and required by F259's fully-offline override — cannot initialize the ruled Owner check. Reading `WorkspaceMembership` from the device cache could preserve offline behavior, but F260 explicitly selected `InitPayload.roles` as an ambient session fact and forbade adding enumeration to `OptimisticCache`; the worker also needs its init payload before the engine is constructed, so that is a different bootstrap contract rather than an implementation detail.

A ruling must name the authoritative source and lifecycle for the roles supplied to `InitPayload`, including cold offline boot and role revocation, and must reconcile any required shell/harness edit with Stage 16's no-`apps/` acceptance criterion. Until then, implementing `roles` would either break compilation, silently deny Owners, or discard the ruled offline guarantee.

**Closed by founder-delegated decision, 24 September 2026.** The premise was wrong, not just the delivery: `InitPayload` never needed a `roles` field at all, because the fact it exists to carry — the caller's own workspace role — is already sitting in the device cache as a plain field on an already-Tier-0, already-replicated node, reachable the same way F260's own Manager check already reaches a `managed_by` edge.

`services/api/src/graph/membership-changes.ts`'s `projectMemberAdmission`/`projectRoleChange` write `WorkspaceMembership.record.role` as `canonicalRoles(roles)` — a comma-joined, sorted `WorkspaceRole` string, the exact format `parseWorkspaceRoles` (`packages/schema/src/auth.ts`, already exported from `@vulto/schema`) decodes back to `WorkspaceRole[]`. `WorkspaceMembership` is Tier 0, Standard protection (F260), so this field is already on every device that has ever synced. The same node carries a `membership_of` edge to the caller's own `User` node (`from_node_id: membershipId, to_node_id: userId`) — the identical shape `managed_by` already has for Manager, just pointed the other way (`edgesTo`, not `edgesFrom`).

Ruled: `InitPayload`/`GraphClientOptions`/`MutatorContext` gain nothing. `overrideAndProceed`'s optimistic handler resolves Owner status with operations `OptimisticCache` already exposes — `context.cache.edgesTo(context.userId, "membership_of")` for the caller's own live membership edge, `context.cache.getNode(edge.fromNodeId)` for the `WorkspaceMembership` node, `parseWorkspaceRoles(node.record.role as string)` then `deriveEffectiveRoles(...).includes("owner")` — no enumeration, no network call, no `apps/` file, and both production `createGraphClient` callers (the shell, the sync harness) are untouched, closing F261's own named concern directly. `conflictCheck.evaluate`'s local query does the identical lookup over `localNodes`/`localEdges` once `WorkspaceMembership` and `membership_of` are added to its already-read node/edge type lists (item 4) — its `input` needs only `callerUserId`, not a separately supplied `callerRoles`, since the roles are derived from the same local cache the rest of the function already reads.

This supersedes F260's `InitPayload.roles`/`MutatorContext.roles` design (F260's own detail section is annotated to point here) without reopening F255–F259: the Owner and Manager checks stay purely advisory locally, and the server re-verifies both gates authoritatively inside `overrideAndProceed` exactly as already ruled.

**Status: closed.** Stage 16 is unblocked; `codex/stage-16-capacity-conflict-resolution` resumes on the corrected brief — no branch restart.
